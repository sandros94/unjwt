# Adapters

> Cookie sessions for H3 and Elysia, where the session is a signed or encrypted JWT that the server issues and reads back.

::note
**ELI5.** A session is how a server remembers you between requests. Many servers keep that memory in a database and hand the browser a random ID. These adapters keep the memory inside the cookie itself. The server writes your data into a JWT, signs or encrypts it with a key only the server holds, and sets it as a cookie. On the next request the browser sends the cookie back, the server checks the signature (or decrypts it), and the data is there again. Nobody can change the data without the key. With an encrypted session, nobody can read it without the key either.
::

## How they fit together

```ts
import { H3 } from "h3";
import { generateJWK, useJWSSession } from "unjwt/adapters/h3v2";

const key = await generateJWK("HS256"); // load a persisted key in production

export const app = new H3()
  .post("/login", async (event) => {
    const session = await useJWSSession(event, { key, maxAge: "1h" });
    session.id; // undefined
    await session.update({ userId: "u_123", role: "admin", jti: "mine", exp: 1 });
    return { id: session.id }; // { id: "ea346d56-…" }
  })
  .get("/me", async (event) => {
    const session = await useJWSSession(event, { key, maxAge: "1h" });
    return { id: session.id, data: session.data };
  });
```

`POST /login` answers with one cookie:

```http
Set-Cookie: h3-jws=eyJraWQiOiJyczF1aDBx…; Path=/; Expires=Thu, 15 Oct 2026 13:47:02 GMT; Secure; SameSite=Lax
```

The cookie value is a compact JWS. Decoded, it carries:

```ts
// protected header
{ kid: "rs1uh0qjoT…", typ: "session+jwt", alg: "HS256" }
// payload
{ userId: "u_123", role: "admin", jti: "ea346d56-…", iat: 1792068422, exp: 1792072022 }
```

The `jti: "mine"` and `exp: 1` passed to `update()` are gone: the adapter owns those claims. Sending that cookie to `GET /me` returns `{ id: "ea346d56-…", data: { userId: "u_123", role: "admin" } }`.

## The session object

Every adapter hands out the same session manager.

| Member                        | Type                      | What it holds                                                             |
| ----------------------------- | ------------------------- | ------------------------------------------------------------------------- |
| `id`                          | `string \| undefined`     | The token's `jti`. `undefined` until a token exists.                      |
| `createdAt`                   | `number`                  | The token's `iat`, in milliseconds.                                       |
| `expiresAt`                   | `number \| undefined`     | The token's `exp`, in milliseconds. Always a number when `maxAge` is set. |
| `data`                        | `SessionData<T>`          | The payload without `jti`, `iat`, `exp` and `nbf`.                        |
| `token`                       | `string \| undefined`     | The compact token this request carries or issued.                         |
| `update(data?, { maxAge? }?)` | `Promise<SessionManager>` | Merges `data`, issues a new token, writes the cookie.                     |
| `clear()`                     | `Promise<SessionManager>` | Expires the cookie and empties the session for the rest of the request.   |

Sessions are lazy. Opening a session reads the incoming token if there is one and writes nothing, unless that token has expired. A visitor without a cookie gets an empty session whose `id` is `undefined`, and no `Set-Cookie` goes out until `update()` runs.

Every `update()` issues a new token with a fresh `jti`, `iat` and `exp`, so `id` changes on each update. `maxAge` counts from the latest update.

## Reserved claims

`jti`, `iat`, `exp` and `nbf` belong to the adapter. It mints `jti` (with `crypto.randomUUID()` or your `generateId`), `iat` and `exp` on every issue and never writes `nbf`. The four are stripped from every `update()` payload and never appear in `session.data`.

Update data must be a plain object. An array, a string, or a `__proto__`, `constructor` or `prototype` key throws `ERR_INVALID_OPTION`. Data travels as JSON, so the next request sees the JSON round trip of what you stored: a `Date` comes back as an ISO string, `NaN` as `null`, and `undefined` members are dropped.

## Explicit typing

Every session token carries `typ: "session+jwt"` in its protected header, and an incoming token must carry it too. This is the explicit typing that [RFC 8725 §3.11](https://www.rfc-editor.org/rfc/rfc8725#section-3.11) recommends. Without it, any other JWT signed or encrypted with the same key (an API token, an email link) would read as a valid session. The comparison is case-insensitive and accepts an `application/` prefix. Set another value through `jws.signOptions.protectedHeader.typ` or `jwe.encryptOptions.protectedHeader.typ`.

A token with another `typ` is refused as `ERR_SESSION_TOKEN_INVALID` and reaches [`onError`](/adapters/hooks), whose `cause` reads `"typ" (Type) Header Parameter mismatch. Expected "session+jwt", got "JWT".`

## Lifetime

`maxAge` (a number of seconds or a string such as `"15m"`, `"1h"`, `"7D"`) sets `exp = iat + maxAge` on every issue. With `maxAge` set, an incoming token must carry `exp`. The token's `exp` alone decides when it expires, so `session.update(data, { maxAge: "5m" })` gives one token a lifetime of its own. Without any `maxAge` the token never expires.

The cookie follows the token. A token with an `exp` sets the cookie's `Expires` to that instant and drops a configured `cookie.maxAge`, because `Max-Age` would win over `Expires` ([RFC 6265 §5.3](https://www.rfc-editor.org/rfc/rfc6265#section-5.3)). A token without `exp` writes the cookie options as configured.

`rolling` moves `exp` forward with activity: `rolling: true` reissues the token on every request, `rolling: "15m"` once less than that remains. See [rolling expiry](/adapters/hooks#rolling-expiry).

An expired token fires [`onExpire`](/adapters/hooks#onexpire), expires the cookie, and leaves an empty session.

## Where the token comes from

The adapter reads the cookie first. When the cookie carries no token, it reads the session header, by default `x-<name>-session` with any `__Host-` or `__Secure-` prefix removed from the name (`"__Host-app"` reads `x-app-session`). Set `sessionHeader` to another header name, or to `false` to read cookies only. Set `cookie: false` to read the header only. Disabling both throws `ERR_SESSION_CONFIG_INVALID`.

The header holds the bare token or `Bearer <token>`, with the scheme matched case-insensitively. Any other value (`Basic …`, a lone `Bearer`, blanks) carries no token. It never hides the cookie and never reaches `onError`.

Prefer a `__Host-` cookie name such as `"__Host-session"`. Each adapter reads the first cookie of a name, and the prefix stops a sibling subdomain from planting a cookie that shadows the session ([RFC 6265bis §4.1.3](https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-rfc6265bis#section-4.1.3)). The default cookie options (`Secure`, `Path=/`, no `Domain`) already satisfy it.

## Chunked cookies

Browsers cap a cookie at about 4 KB. A token longer than `cookie.chunkMaxLength` (default 4000) is split. The base cookie holds `__chunked__N` and the parts go to `<name>.1` through `<name>.N`:

```http
Set-Cookie: __Host-app=__chunked__4; Path=/; Secure; SameSite=Lax
Set-Cookie: __Host-app.1=eyJraWQiOiJkd0VnVzRO…; Path=/; Secure; SameSite=Lax
Set-Cookie: __Host-app.2=4eHh4eHh4eHh4eHh4eHh…; Path=/; Secure; SameSite=Lax
Set-Cookie: __Host-app.3=4eHh4eHh4eHh4eHh4eHh…; Path=/; Secure; SameSite=Lax
Set-Cookie: __Host-app.4=xNzkyMDY4NDU5fQ.yFfD…; Path=/; Secure; SameSite=Lax
```

A token is split into at most 16 chunks. A longer one throws `ERR_SESSION_CONFIG_INVALID` (`Session token requires 93 cookie chunks, exceeding the limit of 16.`). When a new token needs fewer chunks than the old one, the surplus chunks are expired in the same response. Because a session name ending in a dot and digits (`app.1`) would spell another session's chunk, such a name throws `ERR_SESSION_CONFIG_INVALID`. All three adapters write the same layout, so a cookie written by one reads in the others.

## Clearing

`clear()` and an expired read write `Max-Age=0` plus an epoch `Expires` on the base cookie and on every chunk:

```http
Set-Cookie: h3-jws=; Max-Age=0; Path=/; Expires=Thu, 01 Jan 1970 00:00:00 GMT; Secure; SameSite=Lax
```

## JWS or JWE sessions

|                | JWS session                                             | JWE session                                         |
| -------------- | ------------------------------------------------------- | --------------------------------------------------- |
| Token          | Signed. Anyone holding the cookie can read the payload. | Encrypted. Only the server can read the payload.    |
| Default cookie | `Path=/`, `Secure`, `SameSite=Lax`, readable by scripts | `Path=/`, `Secure`, `SameSite=Lax`, `HttpOnly`      |
| Use it for     | Data the browser may read: display name, role, theme.   | Anything private: user IDs, emails, refresh grants. |

A JWS session cookie is readable by scripts on purpose, because its payload is public anyway. Set `cookie: { httpOnly: true }` if your front end has no use for it.

## Keys

The `key` option takes key material, never a password. A string throws `ERR_SESSION_KEY_INVALID`:

```text
[unjwt/h3] Session "key" must be a JWK or a CryptoKey, not a password string. Derive one once with deriveJWKFromPassword() and pass the result.
```

| Session | Accepted `key`                                                                                                                                                                                                                                                                    |
| ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| JWS     | An HMAC `oct` JWK (`HS256`, `HS384`, `HS512`). A `{ privateKey, publicKey }` pair (`RS*`, `PS*`, `ES*`, `Ed25519`), where `publicKey` may be one public JWK, a list, or a JWK Set. A `CryptoKey`.                                                                                 |
| JWE     | A symmetric `oct` JWK, such as one from `generateJWK("A256GCM")` (sealed with `dir`), `generateJWK("A256KW")` or `deriveJWKFromPassword()`. A `{ privateKey, publicKey }` pair (`RSA-OAEP-*`, `ECDH-ES*`), where the public half seals and the private half opens. A `CryptoKey`. |

Use [`generateJWK()`](/jwk/generate) for a new key or [`deriveJWKFromPassword()`](/jwk/password) to turn a secret into one, once, at startup. Each adapter entry re-exports both. A `CryptoKey` carries no algorithm, so it also needs `jws.signOptions.alg` (or `jwe.encryptOptions.alg` and `enc`), else `ERR_SESSION_CONFIG_INVALID`. A configured JWK is imported once per key object when the first session opens. One the session cannot use, such as a `k` that does not decode or a pair half on the wrong side, throws `ERR_SESSION_KEY_INVALID` from that call instead of turning every request into an `onError`.

Pin the algorithm in production with `jws.signOptions.alg` or `jwe.encryptOptions.alg` and `enc`. Issuing then uses it and reading accepts nothing else.

## Errors

Every error an adapter throws is a [`JWTError`](/errors). Check it with `isJWTError(err, code)`, imported from `unjwt` (the adapter entries do not re-export it).

| Code                         | When                                                                                                                                                             |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ERR_SESSION_KEY_INVALID`    | `key` is missing, a string, the wrong shape, or cannot be imported.                                                                                              |
| `ERR_SESSION_CONFIG_INVALID` | A bad `name` or `sessionHeader`, no token source, an unpinned `CryptoKey`, more than 16 chunks, or one name used by a JWS and a JWE session on the same request. |
| `ERR_SESSION_TOKEN_INVALID`  | An incoming token failed to verify or decrypt. Delivered to `onError` with the failure as `cause`, never thrown on read.                                         |
| `ERR_SESSION_READONLY_EVENT` | `update()` or `clear()` after the response was sent (h3 only).                                                                                                   |
| `ERR_INVALID_OPTION`         | `update()` data that is not a plain object, or a `__proto__`-like key.                                                                                           |
| `ERR_JWT_EXPIRED`            | A session token past its `exp`. Delivered to `onExpire`, never thrown.                                                                                           |
