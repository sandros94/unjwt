# Hooks

> Callbacks on `config.hooks` that run when a session is read, issued, cleared, expires or fails, plus two hooks that pick the key for an incoming token.

```ts
import { useJWSSession, type SessionConfigJWS } from "unjwt/adapters/h3v2";

const config = {
  key,
  maxAge: "1h",
  hooks: {
    onUpdate: ({ session }) => audit.log("issued", session.id),
    onClear: ({ oldSession }) => audit.log("signed out", oldSession?.id),
    onExpire: ({ session }) => audit.log("expired", session.id),
  },
} satisfies SessionConfigJWS;

const session = await useJWSSession(event, config);
```

These are unjwt session hooks. They are unrelated to Elysia's request lifecycle hooks (`onRequest`, `beforeHandle`, …) and to Nitro's runtime hooks.

## Signatures

Each hook receives one object. On h3 the request travels as `event`, on Elysia as `context`. `config` is the session config the hook was registered on. Every hook may return a promise, and the adapter awaits it.

```ts
interface SessionHooks<TSession, TCarrier /* { event } or { context } */, TConfig> {
  onRead?(
    args: TCarrier & { session: TSession & { id: string; token: string }; config: TConfig },
  ): void | Promise<void>;
  onUpdate?(
    args: TCarrier & {
      session: TSession & { id: string; token: string };
      oldSession: TSession;
      config: TConfig;
    },
  ): void | Promise<void>;
  onClear?(
    args: TCarrier & { oldSession: TSession | undefined; config: TConfig },
  ): void | Promise<void>;
  onExpire?(
    args: TCarrier & {
      session: {
        id: string | undefined;
        createdAt: number | undefined;
        expiresAt: number | undefined;
        token: string;
      };
      error: Error;
      config: TConfig;
    },
  ): void | Promise<void>;
  onError?(
    args: TCarrier & { session: TSession; error: any; config: TConfig },
  ): void | Promise<void>;

  // JWS sessions only
  onVerifyKeyLookup?(
    args: TCarrier & { header: JWKLookupFunctionHeader; config: TConfig },
  ): JWKSet | JWSVerifyJWK | Promise<JWKSet | JWSVerifyJWK>;
  // JWE sessions only
  onUnsealKeyLookup?(
    args: TCarrier & { header: JWEHeaderParameters; config: TConfig },
  ): JWEDecryptJWK | Promise<JWEDecryptJWK>;
}
```

`TSession` is the session state: `id`, `createdAt`, `expiresAt`, `data` and `token`.

## When each hook fires

| Hook                                      | Fires                                                                                   | Can it change the outcome?                                      |
| ----------------------------------------- | --------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| `onRead`                                  | On every read of a session that holds a token, including repeated reads in one request. | No. A throw rejects the read.                                   |
| `onUpdate`                                | After a new token is issued and its cookie written.                                     | A throw rejects `update()`, and the new session stays in place. |
| `onClear`                                 | After `clear()` empties the session and expires the cookie.                             | A throw rejects `clear()`. The cookie is already expired.       |
| `onExpire`                                | When the incoming session token is past its `exp`, after the cookie is expired.         | No. The session is already empty.                               |
| `onError`                                 | When an incoming token fails for any other reason, and when issuing a token fails.      | No. On the write path the error is thrown again after the hook. |
| `onVerifyKeyLookup` / `onUnsealKeyLookup` | Before an incoming token is verified or decrypted.                                      | It chooses the key.                                             |

For one incoming token exactly one of `onRead`, `onExpire` and `onError` fires. `onClear` only follows an explicit `clear()`, never expiry.

## Ordering

This run logs every hook across a sign-in, a request that reads the session twice, an update, a sign-out, an expired token and a tampered one:

```text
login             onUpdate undefined -> ce4c06b8 data={"user":"alice"} old={}
read twice        onRead id=ce4c06b8
                  onRead id=ce4c06b8
update(fn)        onRead id=ce4c06b8
                  onUpdate ce4c06b8 -> 22b79a80 data={"user":"alice","visits":1} old={"user":"alice"}
logout            onRead id=22b79a80
                  onClear old=22b79a80
expired token     onExpire id=6993738c exp=1792064879000 created=1792061279000 ERR_JWT_EXPIRED
tampered token    onError ERR_SESSION_TOKEN_INVALID cause=ERR_JWS_SIGNATURE_INVALID
```

Opening the session is a read, so `onRead` comes before `onUpdate` or `onClear` in the same request. Every hook runs after the session state has settled, so a hook may open the same session again without waiting on itself.

## onRead

`onRead` repeats on every read, so dedupe on `session.id` when you want once per request. Use it for activity tracking or sliding expiration. Inside `onRead`, reissue with the lower-level [`updateJWSSession()`](/adapters/h3/lower-level) (or `updateJWESession()`). Calling `useJWSSession()` there is another read, which fires `onRead` again and recurses.

```ts
import { updateJWSSession, type SessionConfigJWS } from "unjwt/adapters/h3v2";

const config: SessionConfigJWS = {
  key,
  maxAge: "20m",
  hooks: {
    async onRead({ event, session, config }) {
      if (session.expiresAt! - Date.now() < 15 * 60_000) {
        await updateJWSSession(event, config); // new jti, iat and exp, same data
      }
    },
  },
};
// a token with 599 s left: onRead, then onUpdate d30cf255 -> 7c6306b4, and a fresh Set-Cookie
```

## onUpdate

`oldSession` is a deep copy taken before the update, so it keeps the previous `id`, `data` and `token`. On a first sign-in its `id` is `undefined`. A throwing `onUpdate` makes `update()` reject with that error. The new token and cookie stay, because they were already written:

```ts
hooks: {
  onUpdate: () => {
    throw new Error("db down");
  };
}
// await session.update({ a: 1 }) rejects with "db down"
// session.id: "bb9f88d5-…", session.data: { a: 1 }, Set-Cookie sent
```

## onClear

`oldSession` is the session before the clear, or `undefined` when there was no session to clear. Use it for explicit sign-out bookkeeping, such as revoking `oldSession.id` in a deny list.

## onExpire

The adapter expires the cookie, replaces the session with an empty one, then calls `onExpire`. `session` carries what the expired token held: `id` is its `jti`, and `createdAt` and `expiresAt` are its `iat` and `exp` in milliseconds. `error` is the `ERR_JWT_EXPIRED` [`JWTError`](/errors):

```text
JWT "exp" (Expiration Time) Claim validation failed: Token has expired (exp: 2026-10-15T11:47:59.000Z)
```

Only a token that is otherwise a valid session reaches `onExpire`. An expired token with a bad signature or another `typ` goes to `onError`.

## onError

On the read path `error` is always an `ERR_SESSION_TOKEN_INVALID` `JWTError` whose `cause` is the failure underneath (`ERR_JWS_SIGNATURE_INVALID`, `ERR_JWE_DECRYPTION_FAILED`, a `typ` mismatch, …). The session stays empty. The adapter does not expire the cookie of a token it could not read. Call `clear()` from the handler if you want it gone.

On the write path `error` is whatever issuing threw, such as `ERR_SESSION_CONFIG_INVALID` for a token that needs more than 16 chunks. `session` is rolled back to its state before the update, and `update()` throws the same error after the hook returns.

Key problems never reach `onError`. A `key` the session cannot use throws `ERR_SESSION_KEY_INVALID` from the call that opened the session.

## Key lookup hooks

`onVerifyKeyLookup` (JWS) and `onUnsealKeyLookup` (JWE) receive the incoming token's protected header and return the key to check it with. They replace the configured key for reading. Issuing still uses `key`. They also run for [`verifyJWSSession()`](/adapters/h3/lower-level) and `unsealJWESession()`.

Rotate keys by tagging each with a `kid` and keeping the old ones until their tokens expire:

```ts
import { generateJWK, useJWSSession, type SessionConfigJWS } from "unjwt/adapters/h3v2";

const previous = await generateJWK("HS256", { kid: "2026-09" });
const current = await generateJWK("HS256", { kid: "2026-10" });
const ring = new Map([
  [previous.kid, previous],
  [current.kid, current],
]);

const config = {
  key: current,
  jws: { signOptions: { alg: "HS256" } },
  hooks: {
    onVerifyKeyLookup: ({ header }) => ring.get(header.kid!) ?? current,
  },
} satisfies SessionConfigJWS;
// a cookie signed with "2026-09" still opens; new tokens are signed with "2026-10"
```

Returning a JWK Set works for asymmetric public keys. A set of symmetric keys is refused by [`verify()`](/jwt/jws/verify) unless `jws.verifyOptions.allowSymmetricJWKSet` is `true` and `jws.signOptions.alg` is pinned. Without the pin the adapter cannot infer which algorithms a set allows, and the token fails with `Cannot infer allowed algorithms from this key; pass "options.algorithms" explicitly.` The same lookup on a JWE session returns one decryption key:

```ts
hooks: {
  onUnsealKeyLookup: ({ header }) => ring.get(header.kid!);
}
// header.kid: "enc-1", header.alg: "dir", header.enc: "A256GCM"
```
