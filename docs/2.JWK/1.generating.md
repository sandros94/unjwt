# Generating keys

unjwt gives you two functions for creating keys:

- [`generateJWK`](#generatejwk) — returns a JWK (or a pair of JWKs). Best for 99% of cases.
- [`generateKey`](#generatekey) — returns a `CryptoKey` (or pair, or raw bytes). Use when you need a non-extractable `CryptoKey` or raw byte output.

Both are in `unjwt/jwk`.

## `generateJWK`

```ts
generateJWK(alg, options?)
```

Always returns a JWK (or pair) with `alg` and `kid` set. The `kid` is the key's [thumbprint](#thumbprints) unless you provide one — a name derived from the key material itself, identical for the two halves of a pair.

```ts [examples.ts]
import { generateJWK } from "unjwt/jwk";

// Symmetric → single JWK
const hmac = await generateJWK("HS256");
// { kty: "oct", k: "...", alg: "HS256", kid: "NzbLsXh8uDCcd-6MNwXF4W_7noWXFZAfHkxZsRGC9Xs" }

// Asymmetric → keypair
const { privateKey, publicKey } = await generateJWK("RS256");

// Custom kid
const ec = await generateJWK("ES256", { kid: "ec-signing-2025" });

// Custom RSA modulus
const rsa = await generateJWK("RS256", { modulusLength: 4096, use: "sig" });

// Custom EC curve
const ecdh = await generateJWK("ECDH-ES+A256KW", { namedCurve: "X25519" });

// EdDSA explicit
const ed = await generateJWK("Ed25519");
```

### Options

| Option           | Applies to | Default                               |
| ---------------- | ---------- | ------------------------------------- |
| `kid`            | Any        | The key's RFC 7638 thumbprint         |
| `use`            | Any        | —                                     |
| `keyUsage`       | Any        | Derived from `alg`                    |
| `modulusLength`  | RSA only   | `2048` (also the minimum)             |
| `publicExponent` | RSA only   | `0x010001` (65537) — big-endian bytes |
| `namedCurve`     | EC / OKP   | Derived from `alg` (see below)        |
| Any JWK metadata | Any        | Merged into the result (`x5c`, etc.)  |

`alg`, `kty`, `key_ops`, and `ext` are **managed by the library** and cannot be overridden via options — they must match the key material. Passing one of them throws `ERR_INVALID_OPTION`.

`extractable` is not a JWK member and `generateJWK` takes no such option: a JWK carries its material in plain JavaScript by definition. Use `generateKey(alg, { extractable: false })` when the key should never leave the runtime — it returns a `CryptoKey` instead.

`keyUsage` narrows the usages an algorithm derives, and a key pair splits them between its halves — private takes `sign` / `decrypt` / `unwrapKey` / `deriveBits` / `deriveKey`, public takes `verify` / `encrypt` / `wrapKey`. A narrowing that leaves a half the algorithm would have populated with nothing throws `ERR_INVALID_OPTION`: `generateJWK("ES256", { keyUsage: ["sign"] })` would otherwise emit a public JWK with `key_ops: []`, which no verification accepts. (`ECDH-ES*` is complete with its private half alone — ECDH public keys carry no usage at all.)

`modulusLength` below `2048` bits throws `ERR_INVALID_OPTION`: RFC 7518 §3.3 / §3.5 set 2048 as the floor for `RS*`, `PS*` and `RSA-OAEP*`, and a key the library would refuse to sign with is not worth generating.

::warning
PBES2 algorithms (`PBES2-*`) aren't generation-time algorithms — they're **key-derivation** algorithms. Passing `"PBES2-HS256+A128KW"` to `generateJWK()` throws. Use [`deriveJWKFromPassword`](/jwk/password-derivation) instead.
::

### Algorithm → output shape

| Algorithm                                         | Returns                                                                  |
| ------------------------------------------------- | ------------------------------------------------------------------------ |
| `HS*`, `A*KW`, `A*GCM`, `A*GCMKW`                 | `JWK_oct<Alg>`                                                           |
| `A128CBC-HS256`, `A192CBC-HS384`, `A256CBC-HS512` | `JWK_oct<Alg>` (composite AES+HMAC bytes serialized as one key)          |
| `RS*`, `PS*`, `RSA-OAEP*`                         | `{ privateKey: JWK_RSA_Private<Alg>; publicKey: JWK_RSA_Public<Alg> }`   |
| `ES*`                                             | `{ privateKey: JWK_EC_Private<Alg>; publicKey: JWK_EC_Public<Alg> }`     |
| `Ed25519`, `EdDSA`                                | `{ privateKey: JWK_OKP_Private<Alg>; publicKey: JWK_OKP_Public<Alg> }`   |
| `ECDH-ES*`                                        | EC pair (default curves) **or** OKP pair (for `X25519`) — see `JWK_Pair` |

The literal algorithm is preserved in the return type — `generateJWK("HS256")` is `JWK_oct<"HS256">`, `generateJWK("RS256")` is `{ publicKey: JWK_RSA_Public<"RS256">; privateKey: JWK_RSA_Private<"RS256"> }`. This narrowing flows through into [`sign`](/jwt/jws/signing) / [`verify`](/jwt/jws/verifying) / [`encrypt`](/jwt/jwe/encrypting) / [`decrypt`](/jwt/jwe/decrypting), which reject JWKs whose `alg` points at the wrong algorithm family at the type level. For generic variables, `JWK_Pair<Alg>` picks the right pair shape per algorithm (e.g. `JWK_Pair<"ECDH-ES+A256KW">` is an EC pair _or_ an OKP pair — whichever the runtime curve produces).

### Curve defaults

For EC/OKP algorithms, the `namedCurve` defaults follow the JOSE registry:

| Algorithm         | Default curve | Allowed curves                      |
| ----------------- | ------------- | ----------------------------------- |
| `ES256`           | `P-256`       | `P-256` only                        |
| `ES384`           | `P-384`       | `P-384` only                        |
| `ES512`           | `P-521`       | `P-521` only                        |
| `Ed25519`/`EdDSA` | `Ed25519`     | `Ed25519`, `Ed448` _(experimental)_ |
| `ECDH-ES*`        | `P-256`       | `P-256`, `P-384`, `P-521`, `X25519` |

`ES*` and `Ed25519` each name exactly one curve, so a `namedCurve` that contradicts the table throws `ERR_INVALID_OPTION` — `generateJWK("ES256", { namedCurve: "P-384" })` asks for a key `ES256` cannot be used with. `EdDSA` and `ECDH-ES*` choose among the curves listed for them.

::tip
For new ECDH-ES key pairs, `X25519` is the modern choice — constant-time, compact, and not subject to the NIST-curve "is this a valid point?" validation overhead.
::

## Thumbprints

```ts
thumbprint(jwk, options?)
```

The JWK Thumbprint of RFC 7638: the base64url digest of the key's required members alone — `crv`/`kty`/`x`/`y` for EC, `e`/`kty`/`n` for RSA, `crv`/`kty`/`x` for OKP, `k`/`kty` for `oct` — as JSON with no whitespace and its member names in lexicographic order.

```ts [thumbprint.ts]
import { generateJWK, thumbprint } from "unjwt/jwk";

const { privateKey, publicKey } = await generateJWK("ES256");

await thumbprint(publicKey); // "NzbLsXh8..."
await thumbprint(privateKey); // the same string
await thumbprint(publicKey, { hash: "SHA-512" }); // a longer digest
```

`kid`, `use`, `alg`, `key_ops` and the private members take no part in the digest, so:

- a public key and its private counterpart share one thumbprint;
- two structurally identical keys carry the same name however they are labelled;
- two _different_ keys never do — which is what makes a thumbprint a safe cache key where a `kid` is not, once the cache key also records which half of the pair it holds (see the [JWK cache](/jwk/cache)).

`hash` accepts `"SHA-256"` (the default), `"SHA-384"` or `"SHA-512"`. A key missing a required member, or one whose `kty` the specification defines no members for, throws `ERR_JWK_INVALID`.

## `generateKey`

```ts
generateKey(alg, options?)
```

Returns a `CryptoKey`, `CryptoKeyPair`, or `Uint8Array` depending on the algorithm — **without** wrapping it as a JWK. The exact return type is narrowed by `alg` and by `options.toJWK`:

| Algorithm family                                  | `toJWK: false` (default)                             | `toJWK: true`                         |
| ------------------------------------------------- | ---------------------------------------------------- | ------------------------------------- |
| `HS*`, `A*KW`, `A*GCM`, `A*GCMKW`                 | `CryptoKey`                                          | `JWK_oct`                             |
| `A128CBC-HS256`, `A192CBC-HS384`, `A256CBC-HS512` | `Uint8Array<ArrayBuffer>` (composite AES+HMAC bytes) | `JWK_oct`                             |
| `RS*`, `PS*`, `RSA-OAEP*`                         | `CryptoKeyPair`                                      | `{ privateKey: JWK, publicKey: JWK }` |
| `ES*`, `Ed25519`, `EdDSA`, `ECDH-ES*`             | `CryptoKeyPair`                                      | Same pair shape                       |

### When to use `generateKey`

- **Non-extractable keys** — call `generateKey("HS256", { extractable: false })` to keep the key material inside Web Crypto only. Handy for server-side session-signing keys that shouldn't be exported.
- **Raw bytes for `dir` / AES-CBC-HS\*** — `generateKey("A256GCM")` returns a `CryptoKey` directly usable as a CEK for `alg: "dir"`.
- **Composite AES+HMAC bytes** — `generateKey("A256CBC-HS512")` gives you the 64-byte composite buffer ready for use with `encrypt()` (`alg: "dir"`).

```ts [non-extractable.ts]
import { generateKey } from "unjwt/jwk";

// A CryptoKey that can never be exported as JWK
const sessionKey = await generateKey("HS256", { extractable: false });

// sign() can still use it
await sign({ sub: "u1" }, sessionKey, { alg: "HS256" });
```

### `toJWK: true` vs `generateJWK`

`generateKey("HS256", { toJWK: true })` and `generateJWK("HS256")` both return a `JWK_oct`, but `generateJWK` is the ergonomic path for JWK output: it always sets `kid` — the thumbprint, unless you name one — and accepts JWK metadata fields in its options. Use `generateKey({ toJWK: true })` only when you need a specific non-extractable setup that happens to serialize as JWK — rare.
