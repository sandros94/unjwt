# Importing & exporting

unjwt functions accept keys in many shapes — `JWK`, `CryptoKey`, `Uint8Array`. Internally, everything is normalized through `importKey()`. (A JWE password is the one `string` JOSE has a use for, and it goes to PBKDF2 rather than through `importKey()`.)

Import:

```ts
import { importKey, exportKey } from "unjwt/jwk";
```

## `importKey`

```ts
importKey(key, algOrOptions?)
```

Takes any supported input shape and returns a `CryptoKey` (for asymmetric JWKs) or a `Uint8Array` (for symmetric material, by default).

### Input shapes

| Input                                     | Output (default)        | Notes                                                |
| ----------------------------------------- | ----------------------- | ---------------------------------------------------- |
| `Uint8Array`                              | Same `Uint8Array`       | Returned as-is.                                      |
| `CryptoKey`                               | Same `CryptoKey`        | Returned as-is (subject to `expect` validation).     |
| `JWK_oct`                                 | `Uint8Array` (from `k`) | Bytes — pass `asCryptoKey: true` to get a CryptoKey. |
| `JWK_Public` / `JWK_Private` (asymmetric) | `CryptoKey`             | Requires `alg` (from the JWK or explicit option).    |

### Strings are not key material

`importKey("…")` throws:

```
JWTError: String keys are not accepted: pass an oct JWK or a Uint8Array secret,
or import PEM text with importPEM().  // ERR_JWK_INVALID
```

Every text shape has its own door, and taking the wrong one used to be silent: PEM armour UTF-8 encoded into an HMAC secret verifies a token nobody signed with a key nobody holds.

| You have        | Use                                                                                                         |
| --------------- | ----------------------------------------------------------------------------------------------------------- |
| PEM text        | [`importPEM(pem, alg)`](/jwk/pem)                                                                           |
| A shared secret | `generateJWK("HS256")`, an `oct` JWK, or a `Uint8Array`                                                     |
| A password      | [`deriveJWKFromPassword()`](/jwk/password-derivation), or pass it straight to `encrypt`/`decrypt` for PBES2 |

### The JWK's `alg` is authoritative

A JWK's `alg` ([RFC 7517 §4.4](https://www.rfc-editor.org/rfc/rfc7517#section-4.4)) identifies the algorithm the key is for. Asking for a different one throws rather than picking a winner between the two:

```ts [alg-authority.ts]
await importKey(ecdhJwk, "ES256");
// JWTError: JWK "alg" is "ECDH-ES" but the operation requires "ES256".  // ERR_JWK_INVALID
```

The one exception is the JWE symmetric role mapping: an `oct` JWK whose `alg` is a content encryption algorithm (`A*GCM`, `A*CBC-HS*`) is the CEK that `alg: "dir"` consumes, and decryption additionally requires the token's `enc` to be that same algorithm. See [symmetric key roles](/jwt/jwe/decrypting#symmetric-key-roles).

An `oct` JWK's length is always checked against the algorithm of the operation, never against whichever `alg` happens to be on the key.

### `key_ops` and `ext`

`key_ops` narrows the usages the operation asks for; it never widens them. A JWK whose `key_ops` permits none of them is refused with `ERR_JWK_INVALID` (`JWK "key_ops" does not permit sign.`) instead of producing a `CryptoKey` that fails deep inside Web Crypto.

`ext` works the same way: private key material imports non-extractable unless the caller asks otherwise with `extractable: true`, and a JWK's `ext: false` can lower extractability but never raise it.

### The `expect` option

`expect: "public" | "private"` validates the caller's intent **before** the import runs. If the key type doesn't match, `importKey()` throws `ERR_JWK_INVALID` instead of silently succeeding:

```ts [expect.ts]
import { importKey } from "unjwt/jwk";

// Good: recipient public JWK passed with expect: "public"
const pubKey = await importKey(recipientJwk, { alg: "RSA-OAEP-256", expect: "public" });

// Will throw if somebody accidentally passed a private JWK here
```

`expect` is a no-op for symmetric JWKs and `"secret"`-type CryptoKeys — they have no public/private distinction.

::note
`verify()` passes `expect: "public"` and `decrypt()` passes `expect: "private"` automatically. You only need `expect` when calling `importKey()` directly — which is rare; you'd typically just pass the JWK straight to `sign`/`verify`/`encrypt`/`decrypt`.
::

### `asCryptoKey: true` for `JWK_oct`

By default, a `JWK_oct` imports as raw bytes. Opt in to a non-extractable `CryptoKey`:

```ts [as-cryptokey.ts]
const aesCryptoKey = await importKey(symJwk, {
  asCryptoKey: true,
  algorithm: { name: "AES-GCM", length: 256 },
  usage: ["encrypt", "decrypt"],
  extractable: false, // default
});
```

Handy when you want the bytes to stay inside Web Crypto and never be retrievable.

### Full options

```ts
// For JWK_oct
interface ImportOctOptions {
  asCryptoKey: true;
  algorithm: AlgorithmIdentifier | HmacImportParams | AesDerivedKeyParams;
  usage: KeyUsage[];
  extractable?: boolean; // default false for asCryptoKey: true
}

// For asymmetric JWK
interface ImportAsymmetricOptions {
  alg?: JWSAlgorithm | KeyManagementAlgorithm; // required if JWK.alg is missing
  expect?: "public" | "private";
  extractable?: boolean; // default: false for private key material, true for public
}
```

## `exportKey`

```ts
exportKey(key, jwkParams?)
```

Exports a `CryptoKey` as a JWK. Optionally merges metadata fields into the result.

```ts [export.ts]
import { exportKey } from "unjwt/jwk";

const cryptoKey = await crypto.subtle.generateKey(/* ... */);
const jwk = await exportKey(cryptoKey, { kid: "legacy-1", use: "sig" });
// { kty, alg, key_ops, ext, ...actual key fields, kid: "legacy-1", use: "sig" }
```

The authoritative fields come from Web Crypto's export and **cannot be overridden** via `jwkParams`. Only additive metadata (`kid`, `use`, `x5c`, `x5t`, `x5u`, custom fields) is merged — passing `kty`, `alg`, `key_ops`, `ext`, or any key-material member (`k`, `d`, `n`, `e`, `p`, `q`, `dp`, `dq`, `qi`, `x`, `y`, `crv`) throws `ERR_INVALID_OPTION` naming the offending members, rather than producing a JWK that misdescribes its own bytes.

### The exported `alg` is Web Crypto's, not the JOSE role

`exportKey()` reports the algorithm Web Crypto holds for the key, and Web Crypto does not model JOSE roles. An AES-GCM key generated for `A128GCMKW` — key wrapping — exports as `alg: "A128GCM"`, the content-encryption role, because the two are the same Web Crypto algorithm. `importKey(jwk, { alg: "A128GCMKW" })` then refuses it: a JWK's `alg` is authoritative, and that one says the key is a CEK.

```ts
const kek = await generateKey("A128GCMKW"); // CryptoKey
const jwk = await exportKey(kek); // { alg: "A128GCM", ... }
await importKey(jwk, { alg: "A128GCMKW" }); // throws ERR_JWK_INVALID
```

Mint key-wrapping keys as JWKs instead — [`generateJWK("A128GCMKW")`](/jwk/generating) or `generateKey("A128GCMKW", { toJWK: true })` — which stamp the `alg` that was asked for.

::tip
Most of the time you won't call `exportKey()` directly — the output of `generateJWK()` is already a JWK. You'd use `exportKey()` when you've received or imported a `CryptoKey` from an external source (Web Crypto directly, another library) and need to serialize it.
::
