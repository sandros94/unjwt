# JWK Sets

A **JWK Set** ([RFC 7517 §5](https://www.rfc-editor.org/rfc/rfc7517#section-5)) is a JSON object with a `keys` array. It's the canonical way to publish multiple keys together — one for signing, several for rotation, a mix of algorithms — and to consume them as a single entity.

```json
{
  "keys": [
    { "kty": "RSA", "kid": "2025-q1", "alg": "RS256", "n": "...", "e": "AQAB" },
    { "kty": "RSA", "kid": "2025-q2", "alg": "RS256", "n": "...", "e": "AQAB" }
  ]
}
```

This is the format OAuth/OIDC providers publish at `/.well-known/jwks.json`. It's also how you'd persist your own rotating signing keys in a config file or database.

## Consuming a set

Pass a JWK Set to `verify()` or `decrypt()` and the library handles the selection for you:

```ts [from-endpoint.ts]
const jwks = await fetch("https://auth.example.com/.well-known/jwks.json").then((r) => r.json());

const { payload } = await verify(tokenFromProvider, jwks);
// ↑ unjwt picks the right key from the set based on the token's `kid`
```

### Selection rules

When a JWKSet is passed (directly or returned from a [lookup function](/jwt/jws/verifying#dynamic-key-resolution-jwklookupfunction)), an entry is a candidate only when all of these hold:

- It **is a JWK** — `null`, strings and junk objects in `keys` are ignored.
- It is **not symmetric**. A set is public-key material; see [Symmetric entries](#symmetric-entries) below.
- Its `kid` equals the token's `kid`, or the token carries none.
- Its `alg` equals the token's `alg`, or it declares none.
- Its `use` is absent or matches the operation (`"sig"` for `verify`, `"enc"` for `decrypt`).
- Its `key_ops` is absent or permits the operation (`verify` for `verify`; `unwrapKey`, `decrypt`, `deriveBits` or `deriveKey` for `decrypt`).

Candidates are tried in order and the first that works wins. A candidate that cannot work — a key the token was not signed with, key material WebCrypto rejects — only means "try the next one"; when none works, the resulting `ERR_JWS_SIGNATURE_INVALID` / `ERR_JWE_DECRYPTION_FAILED` carries the per-candidate reasons as its `cause` array. When no entry is a candidate at all, `JWTError("ERR_JWK_KEY_NOT_FOUND")` is thrown **before any crypto runs**.

This is the mechanism behind transparent key rotation: add a new key to the set, retire the old one after a grace period, and your verification code never changes.

### How many candidates are tried

At most **8** by default: a set that still leaves more candidates after the filtering above is `ERR_JWK_KEY_NOT_FOUND` before the first key is imported, because each surviving candidate costs a signature check or an unwrap. Give your keys a `kid` and your tokens the matching header and the count is 1 whatever the set's size; raise the cap per call when a set really is meant to be tried wide:

```ts [wide-set.ts]
const { payload } = await verify(token, jwks, { limits: { keyCandidates: 32 } });
```

See [Bounded work per call](/jwt/jws/verifying#bounded-work-per-call).

### `kid` and thumbprints

A `kid` is a free-form label, and nothing stops two keys from carrying the same one. The natural `kid` is therefore the key's own [thumbprint](/jwk/generating#thumbprints) (RFC 7638) — it is derived from the key material, so it names one key and no other, and both halves of a pair agree on it. `generateJWK` uses it as the default `kid` for exactly that reason, and a JWKS built from generated keys needs no naming scheme of its own.

### Symmetric entries

A JWK Set is public-key material. Its `oct` entries are **ignored**, and they do not contribute to the algorithms inferred from the set either — so appending `{"kty":"oct","alg":"HS256","k":"…"}` to a published set cannot turn into a shared secret your tokens are then checked against.

For a set your own application controls — an HMAC key-rotation set you store yourself — opt back in per call:

```ts [hmac-rotation.ts]
const { payload } = await verify(token, myHmacSet, { allowSymmetricJWKSet: true });
```

::warning
Never pass `allowSymmetricJWKSet: true` for a set fetched from a `jwks_uri` or any other party: whoever can add an entry to that set can then mint tokens you accept.
::

The option is available on `verify`, `verifyMulti`, `verifyMultiAll`, `decrypt` and `decryptMulti`.

## `getJWKsFromSet`

```ts
getJWKsFromSet(jwkSet, filter?)
```

Returns an array of JWKs from a set, optionally narrowed by a predicate. Entries that are not JWKs are dropped — `keys` arrives over the wire and may hold anything:

```ts [filter.ts]
import { getJWKsFromSet } from "unjwt/jwk";

const all = getJWKsFromSet(jwkSet);
// → all keys as JWK[]

const hmacOnly = getJWKsFromSet(jwkSet, (k) => k.kty === "oct");
// → only symmetric keys

const current = getJWKsFromSet(jwkSet, (k) => k.kid?.startsWith("2025-") ?? false);
// → only keys whose kid matches a prefix
```

Useful for:

- Picking the current signing key from a set that contains historical keys too.
- Building a multi-recipient JWE targeted at a specific subset of keyholders.
- Debugging — inspecting what's actually in a JWK Set.

## Key rotation — a complete pattern

1. **Issue with key A**, which carries `kid: "2025-q1"`. Publish your JWKS containing just A.
2. **Generate key B** (`kid: "2025-q2"`). Publish JWKS containing both A and B. Don't sign with B yet — verifiers need time to refresh their cache.
3. **Cutover**: start signing with B. Keep publishing both A and B so tokens still in flight validate.
4. **Retire A**: once A's longest-lived token has expired, remove A from JWKS. Only B remains.
5. Repeat.

On the verifier side, the same `verify(token, jwks)` call works through every step — no code changes. That's the whole point of JWK Sets.

## Publishing a JWKS endpoint

If you're on the signing side and want downstream consumers to verify your tokens:

```ts [jwks-endpoint.ts]
import { exportKey, thumbprint } from "unjwt/jwk";

// Keep private keys server-side only.
// Expose the PUBLIC half of each:
app.get("/.well-known/jwks.json", async () => {
  return {
    keys: [
      await exportKey(currentPublicCryptoKey, {
        kid: await thumbprint(currentPublicJwk),
        use: "sig",
      }),
      await exportKey(previousPublicCryptoKey, {
        kid: await thumbprint(previousPublicJwk),
        use: "sig",
      }),
    ],
  };
});
```

In most apps you'd keep the JWK objects themselves in memory or a config store and hand them back — exporting from `CryptoKey` is only needed when you generated with `generateKey()` (non-JWK output) or imported opaquely.

Full example: [Consuming a JWKS endpoint →](/examples/jwks-endpoint).

## Dynamic resolution — when you need more than a static set

If the set is large, changing frequently, or fetched per-request, use a [`JWKLookupFunction`](/jwt/jws/verifying#dynamic-key-resolution-jwklookupfunction) instead:

```ts [dynamic.ts]
const { payload } = await verify(
  token,
  async (header) => {
    const jwks = await jwksCache.get(header.iss); // cached fetch per issuer
    return jwks; // return the whole set — library handles selection
  },
  { algorithms: ["RS256", "ES256"] },
);
```
