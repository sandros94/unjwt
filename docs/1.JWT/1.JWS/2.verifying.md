# Verifying

```ts
verify(token, key, options?)
```

Checks a compact JWS, validates its claims, and returns `{ payload, protectedHeader }`.

## Parameters

| Name                      | Type                                                                                                                          |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `token`                   | `string` — the compact JWS                                                                                                    |
| `key`                     | `CryptoKey \| JWKSet \| JWSVerifyJWK \| Uint8Array \| JWKLookupFunction`                                                      |
| `options.algorithms`      | `JWSAlgorithm[]` — allowlist                                                                                                  |
| `options.payload`         | `"json" \| "string" \| "bytes"` — what the payload is. Defaults to `"json"`                                                   |
| `options.validateClaims`  | `boolean` — force-skip claim validation                                                                                       |
| `options.forceUint8Array` | `boolean` — deprecated alias of `payload: "bytes"`                                                                            |
| `options.limits`          | `{ keyCandidates?: number }` — JWK Set candidates tried per token. Defaults to `8`                                            |
| Claim options             | `audience`, `issuer`, `subject`, `maxTokenAge`, `clockTolerance`, `typ`, `currentDate`, `requiredClaims`, `recognizedHeaders` |

`JWSVerifyJWK` is the public counterpart of [`JWSSignJWK`](/jwt/jws/signing) — `JWK_oct<JWK_HMAC>` or a public asymmetric JWK with a signing `alg`. `JWKSet` stays fully permissive (`JWK[]`); wire JWKS are heterogeneous and the runtime filters candidates per header.

Verification imports the key as a public one, so an asymmetric JWK that still carries its private `d` is refused with `ERR_JWK_INVALID` rather than quietly imported. Strip `d` (and the RSA CRT members) yourself — nothing is dropped on your behalf, so a private key can never reach a verifier by accident.

Returns `Promise<{ payload: T, protectedHeader: JWSProtectedHeader }>`.

## The simple case

```ts
const { payload, protectedHeader } = await verify(token, key);
```

If `key` is a JWK with an `alg` field (as every key produced by `generateJWK()` is), unjwt:

1. decodes the protected header,
2. checks the token's `alg` is in the allowlist inferred from the key,
3. verifies the signature,
4. decodes the payload under `options.payload` (`"json"` by default),
5. runs claim validation.

## Dynamic key resolution — `JWKLookupFunction`

For OIDC/OAuth providers or anywhere the verifier picks a key based on the token's `kid`, pass a lookup function:

```ts [lookup.ts]
const { payload } = await verify(
  token,
  async (header, _rawToken) => {
    // fetch the JWK for the given kid — typically from a cache or a JWKS endpoint
    return await fetchKeyByKid(header.kid!);
  },
  { algorithms: ["RS256"] }, // required — the function returns unknowable shapes
);
```

The lookup function receives:

- `header` — the protected header (`kid`, `alg`, `typ`, `crit`, and any custom fields).
- `rawToken` — the original token string (useful for structured logging).

It can return any of: `JWK`, `JWKSet`, `CryptoKey` or `Uint8Array`. Async is allowed. A `string` is **not** key material for JWS — a lookup that returns one fails with `ERR_JWK_INVALID`; see [string keys](#string-keys-are-not-jws-keys).

::tip
Always pass `algorithms` explicitly when using a lookup function — the library can't infer an allowlist from a function's return type. Leaving it out means no default guard against `alg` confusion attacks.
::

## JWKSet — automatic key rotation

A **JWKSet** is any object with a `keys: JWK[]` array. When you pass a set — directly, or returned from a lookup function — unjwt selects candidate keys like this:

1. **Token has a `kid`** — only keys in the set with that exact `kid` are candidates. Typically one key, no retry.
2. **Token has no `kid`** — every key whose `alg` field matches the token is a candidate, and so is every key that declares no `alg` at all, tried in order until one succeeds.
3. **No candidates at all** — throws `JWTError("ERR_JWK_KEY_NOT_FOUND")` **before** any crypto attempt.

A set is public-key material: entries that are not JWKs, `oct` entries, and entries whose `use`/`key_ops` do not permit verification are never candidates. A candidate that turns out to be unusable only means "try the next one", and the final `ERR_JWS_SIGNATURE_INVALID` carries one error per tried key in its `cause`. To verify against a symmetric set your own application owns, pass `allowSymmetricJWKSet: true` — see [JWK Sets → Symmetric entries](/jwk/jwk-sets#symmetric-entries).

```ts [jwks-endpoint.ts]
const jwks = await fetch("https://auth.example.com/.well-known/jwks.json").then((r) => r.json());

// With kid: O(1) selection
const { payload } = await verify(tokenFromProvider, jwks);

// Rotating set, no kid yet on old tokens — all compatible keys are tried
const rotatingSet = { keys: [newKey, legacyKey] };
const { payload: p } = await verify(oldToken, rotatingSet);
```

This is how transparent key rotation works without any retry code in userland. See the [JWKS endpoint example](/examples/jwks-endpoint) for a full walkthrough.

## Algorithm allowlist

`options.algorithms` constrains which `alg` values are acceptable. Omitting it is **safe when the key has metadata** — unjwt calls [`inferJWSAllowedAlgorithms`](/utilities#inferjwsallowedalgorithms) to derive a narrow allowlist from the key shape (a key with `alg: "HS256"` yields `["HS256"]`, an RSA public key yields both `RS*` and `PS*` variants).

When inference is impossible, unjwt throws `ERR_JWS_ALG_NOT_ALLOWED` ("Cannot infer allowed algorithms from this key; pass `options.algorithms` explicitly.") before attempting verification. Inference returns `undefined` for:

- Raw `Uint8Array` keys.
- JWKs without an `alg` field (and whose `kty`/`crv` doesn't unambiguously pin the signing alg — e.g. an RSA JWK without `alg`).
- Lookup functions that resolve to such shapes.
- JWK Sets in which no entry contributes — an entry that cannot be inferred is skipped rather than voiding the whole set.

For these cases, pass `algorithms` explicitly:

```ts
const { payload } = await verify(token, lookupFn, {
  algorithms: ["RS256", "PS256"], // only these will be considered
});
```

::warning
**The "`alg: none`" attack** — a classic JWT pitfall. unjwt rejects `alg: "none"` outright, but an overly permissive allowlist (e.g. accepting both `HS256` and `RS256` against a key that could be interpreted either way) opens the door to other confusion attacks. Keep the allowlist as narrow as the key allows.
::

## Claim validation options

These all come from the shared [`JWTClaimValidationOptions`](/utilities#validatejwtclaims) interface:

| Option              | Effect                                                                                       |
| ------------------- | -------------------------------------------------------------------------------------------- |
| `audience`          | Must match (or be included in) the token's `aud`. Checked only when configured.              |
| `issuer`            | Must match (or be one of) the token's `iss`.                                                 |
| `subject`           | Must match the token's `sub`.                                                                |
| `maxTokenAge`       | `iat` must be within this duration of `currentDate`.                                         |
| `clockTolerance`    | Slack for `exp`/`nbf`/`iat` comparisons — seconds or a `Duration` (`"5m"`). Defaults to `0`. |
| `typ`               | Must match the token's `typ` header (RFC 7515 §4.1.9 media-type comparison).                 |
| `requiredClaims`    | Array of claim names that must be present.                                                   |
| `currentDate`       | Override "now" for comparisons.                                                              |
| `recognizedHeaders` | Critical-header allowlist (for RFC 7515 §4.1.11 `crit`).                                     |

::warning
The `aud` claim is checked **only when `audience` is configured**. A token carrying `aud: "other-service"` is accepted by a verifier that sets no `audience` — the claim is read, not enforced. Configure `audience` wherever a token is meant for this recipient alone; that is what enforces [RFC 7519 §4.1.3](https://www.rfc-editor.org/rfc/rfc7519#section-4.1.3).
::

`validateClaims` has three states:

- **`undefined`** (default) — validate the claims of a `payload: "json"` verification.
- **`true`** — same as `undefined`. Combined with `payload: "string"` or `"bytes"` it is `ERR_INVALID_OPTION`: there is no payload to validate claims on, and the option must not look like it ran.
- **`false`** — skip validation entirely.

## Payload typing

`options.payload` declares what the signed content is. The signed bytes never decide their own shape, so a token cannot change how it is read by how it happens to look.

| `payload`  | Result                    | Rejected when                                       |
| ---------- | ------------------------- | --------------------------------------------------- |
| `"json"`   | the generic `T` (default) | not UTF-8 JSON naming an object → `ERR_JWS_INVALID` |
| `"string"` | `string`                  | not valid UTF-8 → `ERR_JWS_INVALID`                 |
| `"bytes"`  | `Uint8Array<ArrayBuffer>` | never                                               |

Pass a generic to type the JSON case:

```ts [typed.ts]
interface MyClaims {
  sub: string;
  role: "admin" | "user";
  org: string;
}

const { payload } = await verify<MyClaims>(token, key);
payload.role; // "admin" | "user"
```

A payload that is not a JSON object must say so:

```ts
const { payload: text } = await verify(token, key, { payload: "string" });
typeof text; // "string" — even when the string happens to be `{"sub":"admin"}`

const { payload: bytes } = await verify(token, key, { payload: "bytes" });
bytes instanceof Uint8Array; // true
```

Under RFC 7797 `b64: false` the unencoded payload segment is the content and the same three modes apply to it — an expired claims token signed that way is still rejected.

::warning
`forceUint8Array` is a deprecated alias of `payload: "bytes"` (removed in v0.9.0). Passing both with conflicting values is `ERR_INVALID_OPTION`.
::

## String keys are not JWS keys

A `string` is never a JWS key. `sign()`, `verify()`, `signMulti()`, `verifyMulti()` and `verifyMultiAll()` reject one with:

```
JWTError: String keys are not accepted: pass an oct JWK or a Uint8Array secret,
or import PEM text with importPEM().  // ERR_JWK_INVALID
```

This holds for keys a lookup function or a JWK Set produces, too. Without it, `verify(token, pemText)` would quietly HMAC over the PEM armour instead of verifying an RSA signature.

```ts
// ✗ HMAC over the armour text, not an RSA verification
await verify(token, pemText as any);

// ✓ parse the PEM into a JWK first
const jwk = await importPEM(pemText, "RS256");
await verify(token, jwk);

// ✓ a shared secret is an oct JWK or raw bytes
const secret = await generateJWK("HS256");
await verify(token, secret);
```

## Critical header handling

Headers listed in the token's `crit` field must be understood by the verifier, per [RFC 7515 §4.1.11](https://www.rfc-editor.org/rfc/rfc7515#section-4.1.11). unjwt recognizes `b64` natively; anything else in `crit` must be listed in `options.recognizedHeaders` or verification fails:

```ts
await verify(token, key, {
  recognizedHeaders: ["my-custom-crit-header"],
});
```

`crit` itself is validated first:

- it must be a **non-empty array of strings**, otherwise `ERR_JWS_INVALID`;
- it must list **extensions only** — a parameter registered by RFC 7515/7516/7518 (`alg`, `enc`, `zip`, `jku`, `jwk`, `kid`, `x5u`, `x5c`, `x5t`, `x5t#S256`, `typ`, `cty`, `crit`, `epk`, `apu`, `apv`, `iv`, `tag`, `p2s`, `p2c`) is rejected and `recognizedHeaders` cannot opt back into it. `b64` is an RFC 7797 extension, so it stays allowed;
- every name it lists must be **present** in the protected header — `b64` included, so `crit: ["b64"]` with no `b64` member is `ERR_JWS_INVALID`;
- in the JSON serializations (`verifyMulti` / `verifyMultiAll`), a `crit` found in an **unprotected** header is rejected — `crit` is only meaningful when integrity protected.

## Header checks before key work

`verify()` settles the header before touching key material:

- the protected header must decode to a JSON **object** — `null`, arrays and JSON scalars are `ERR_JWS_INVALID`;
- `alg: "none"` and any `alg` outside the supported set are rejected with `ERR_JWS_ALG_NOT_ALLOWED`, so a forged `alg` never reaches WebCrypto;
- `b64` must be a boolean (RFC 7797 §3), and `b64: false` requires `"b64"` in `crit` (RFC 7797 §6);
- `typ` is compared case-insensitively with an optional `application/` prefix on either side, so `typ: "at+jwt"` matches `"application/AT+JWT"`; a protected header without `typ` fails `options.typ` with `ERR_JWS_INVALID`;
- a key that cannot serve the declared `alg` surfaces as `JWTError("Key is not usable for <alg>.", "ERR_JWK_INVALID")` with the underlying WebCrypto/codec failure as `cause` — never as a raw `TypeError` or `DOMException`.

## Bounded work per call

A JWK Set decides how many keys one token is tried against, and each surviving candidate costs a signature check. After the `kid`/`alg`/`use` filtering of [JWK Sets](/jwk/jwk-sets#selection-rules), at most **8** candidates are tried; a wider set is `ERR_JWK_KEY_NOT_FOUND` before the first key is imported:

```
JWTError: 12 candidate keys exceed the limit of 8; narrow the JWK Set with a "kid".
```

Raise or lower the cap per call:

```ts
await verify(token, jwks, { limits: { keyCandidates: 32 } });
```

Each limit must be a positive integer; anything else is `ERR_INVALID_OPTION`. The defaults are exported as `DEFAULT_JOSE_LIMITS`:

```ts
import { DEFAULT_JOSE_LIMITS } from "unjwt/jws";
// { signatures: 16, recipients: 16, keyCandidates: 8, pbes2Iterations: 2_400_000 }
```

`verifyMulti` / `verifyMultiAll` add the [`signatures`](/jwt/jws/multi-signature#bounded-work-per-call) cap; `decrypt` / `decryptMulti` add [`recipients` and `pbes2Iterations`](/jwt/jwe/decrypting#bounded-work-per-call).

## Errors

Every failure in `verify()` is a `JWTError` — a single `instanceof` (or `isJWTError`) is enough to tell a library error from anything else. When the root cause is one of the bundled [`unsecure`](https://github.com/sandros94/unsecure) primitives — the base64url codec or the JSON parser — the original is preserved as `cause`:

```ts [errors.ts]
import { verify, isJWTError, isUnsecureError } from "unjwt/jws";

const error = await verify(token, key).catch((e) => e);

if (isJWTError(error, "ERR_JWS_INVALID") && isUnsecureError(error.cause, "MALFORMED")) {
  // a segment of the token is not canonical base64url — reject as a bad request
}
```

::note
`unsecure` is inlined into unjwt's dist, so the `UnsecureError` from a consumer-installed `unsecure` is a **different class** and `instanceof` against it always fails. Use the `UnsecureError` / `isUnsecureError` that unjwt re-exports (available from `unjwt`, `unjwt/jws`, `unjwt/jwe`, `unjwt/jwk` and `unjwt/utils`). The `unjwt/utils` primitives themselves still throw `UnsecureError` directly — only the JOSE operations wrap.
::

## Full signature

```ts
interface JWSVerifyOptions extends JWTClaimValidationOptions {
  algorithms?: JWSAlgorithm[];
  /** Admit the `oct` entries of a JWK Set, which are otherwise skipped. */
  allowSymmetricJWKSet?: boolean;
  /** Bounded work for this call — see [Limits](/jwt/limits). */
  limits?: JOSELimits;
  payload?: "json" | "string" | "bytes";
  /** @deprecated Use `payload: "bytes"`. Removed in v0.9.0 */
  forceUint8Array?: boolean;
  validateClaims?: boolean;
}

interface JWSVerifyResult<T> {
  payload: T;
  protectedHeader: JWSProtectedHeader;
}
```
