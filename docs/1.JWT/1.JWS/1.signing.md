# Signing

```ts
sign(payload, key, options?)
```

Produces a **compact JWS** — the familiar dotted three-part string.

## Parameters

| Name                      | Type                                              | Required?                    |
| ------------------------- | ------------------------------------------------- | ---------------------------- |
| `payload`                 | `string \| Uint8Array \| Record<string, unknown>` | Yes                          |
| `key`                     | `CryptoKey \| JWSSignJWK \| Uint8Array`           | Yes                          |
| `options.alg`             | `JWSAlgorithm`                                    | When `key` has no `alg` hint |
| `options.protectedHeader` | `JWSHeaderParameters` (extra fields)              | No                           |
| `options.expiresIn`       | `number \| string` — e.g. `"1h"`, `"7D"`, `3600`  | No                           |
| `options.currentDate`     | `Date`                                            | No                           |

`JWSSignJWK` narrows the JWK by family: `JWK_oct<JWK_HMAC>` for HMAC, or an asymmetric _private_ JWK whose `alg` is in the matching signing family (`RS*`/`PS*` for RSA, `ES*` for ECDSA, `Ed25519`/`EdDSA` for OKP). A JWK whose `alg` points at a non-signing family (`"RSA-OAEP"`, `"A256KW"`, `"ECDH-ES"`, …) is rejected at the type level.

Returns `Promise<string>` — the compact JWS.

## Algorithm inference

When the key is a **JWK** with an `alg` field set, unjwt reads it and uses that algorithm. `generateJWK()` always sets `alg` for you, so in practice you rarely specify it by hand:

```ts [inferred.ts]
const key = await generateJWK("HS256"); // key.alg === "HS256"
const token = await sign({ sub: "u1" }, key); // uses HS256 automatically
```

You must pass `options.alg` **explicitly** in three cases:

- The key is a raw `Uint8Array` (no metadata to infer from).
- The key is a `CryptoKey` without algorithm context (rare — `generateKey()` sets the algorithm internally).
- The JWK has no `alg` field.

```ts [explicit.ts]
import { base64UrlParse } from "unjwt/utils";

const rawKey = base64UrlParse("dW5qd3QtZG9jcy1leGFtcGxlLWhzMjU2LWtleS0zMmI", {
  returnAs: "uint8array",
});
const token = await sign({ sub: "u1" }, rawKey, { alg: "HS256" });
```

## `expiresIn` — setting `exp` declaratively

Sets the `exp` claim relative to `iat`:

```ts
await sign({ sub: "u1" }, key, { expiresIn: "1h" }); // exp = iat + 3600
await sign({ sub: "u1" }, key, { expiresIn: 30 }); // exp = iat + 30
await sign({ sub: "u1" }, key, { expiresIn: "7days" }); // exp = iat + 604800
```

Accepted forms: `"30s"`, `"10m"`, `"2h"`, `"7D"`, `"1W"`, `"3M"`, `"1Y"` and the long forms (`"seconds"`, `"minutes"`, `"hours"`, `"days"`, `"weeks"`, `"months"`, `"years"`).

If your payload already has an `iat`, it's preserved; otherwise the current time is used. Use `currentDate` to override "now" in tests.

::note
`expiresIn` is a signer-side option. On the verifier side, pass `maxTokenAge` or rely on the `exp` claim that's already baked into the token.
::

## Custom header parameters

Anything passed in `protectedHeader` is merged into the JWS header. `alg` is reserved — it's always derived from the top-level `alg` option (or inferred from the key) and can't be overridden here. `b64` is user-settable: set it to `false` to opt into the RFC 7797 unencoded-payload mode (see below).

```ts [custom-header.ts]
const token = await sign({ sub: "u1" }, key, {
  protectedHeader: {
    kid: "legacy-2024", // overrides key.kid if set
    typ: "access+jwt", // RFC 8725 guidance — custom type name
  },
});
```

An object payload gets `typ: "JWT"` when you set none. No `cty` is ever added: [RFC 7519 §5.2](https://www.rfc-editor.org/rfc/rfc7519#section-5.2) reserves it for nested JWTs, where it is `"JWT"`. A `cty` you set here is kept as given.

### `kid` fallback

If the key is a JWK with a `kid` field and you don't set `protectedHeader.kid`, unjwt adds `kid` to the header automatically. This is the "make tokens carry their key identity" behavior — essential for JWKS endpoints and key rotation. An explicit `protectedHeader.kid` always wins.

### `crit` is validated as it is written

A `crit` you pass is held to the rules the verifier applies ([RFC 7515 §4.1.11](https://www.rfc-editor.org/rfc/rfc7515#section-4.1.11)): a non-empty array of strings, listing extensions only — never a parameter the JOSE specs register — and naming parameters the protected header actually carries — `"b64"` included. `b64: true` is the default and is normally dropped from the header, but it is kept when your `crit` lists `"b64"`; a `crit: ["b64"]` with no `b64` member at all is refused with `ERR_INVALID_OPTION`.

```ts
// Throws ERR_INVALID_OPTION: "app" is critical but the header does not carry it.
await sign(payload, key, { protectedHeader: { crit: ["app"] } });

// Fine — verifiers must then be told they understand "app".
await sign(payload, key, { protectedHeader: { crit: ["app"], app: "web" } });
```

`b64` is a boolean ([RFC 7797 §3](https://www.rfc-editor.org/rfc/rfc7797#section-3)); any other value is refused with `ERR_INVALID_OPTION`. So is a `typ` that is not a string.

The same applies to each signer's `protectedHeader` in [`signMulti`](/jwt/jws/multi-signature). A protected header that is not an object, or that cannot be serialized to JSON — one carrying a `BigInt` or a circular reference — is `ERR_INVALID_OPTION` too.

## `b64: false` — RFC 7797 unencoded payload

[RFC 7797](https://www.rfc-editor.org/rfc/rfc7797) defines a variant where the JWS payload is signed over **raw bytes** rather than the base64url-encoded form. Useful when:

- The payload is already a large or structured document (XML, JSON-LD) that consumers want to read without base64 decoding.
- The payload contains binary data and base64url overhead matters.

```ts [unencoded.ts]
const token = await sign("important document bytes", key, {
  protectedHeader: { b64: false },
});
// Result: "eyJhbGc...crit...b64...".<raw payload>.<signature>
// (note the payload is literally in the middle)
```

`b64: false` must be integrity protected ([RFC 7797 §6](https://www.rfc-editor.org/rfc/rfc7797#section-6)), so `sign()` adds `"b64"` to `crit` for you — creating `crit` when absent and never duplicating an entry you already wrote. Verifiers that don't recognize the parameter then reject the token instead of mis-validating it, and `verify()` refuses a `b64: false` header whose `crit` omits it.

::warning
With `b64: false` the payload sits verbatim between the dots, so a payload containing `"."` would split the compact serialization. `sign()` rejects it with `ERR_JWS_INVALID` ([RFC 7797 §5.2](https://www.rfc-editor.org/rfc/rfc7797#section-5.2)) — use the JSON serialization (`signMulti`) for such payloads. The payload also travels as text, so `Uint8Array` bytes that are not valid UTF-8 are rejected with `ERR_JWS_INVALID` by `sign()` and `signMulti()` alike, rather than signed in a substituted form.
::

::warning
All signers of a multi-signature JWS must agree on `b64`. See [Multi-signature](/jwt/jws/multi-signature).
::

## Payload types

`sign()` accepts three payload shapes:

| Shape                     | Behavior                                                               |
| ------------------------- | ---------------------------------------------------------------------- |
| `Record<string, unknown>` | Serialized to JSON. `typ: "JWT"` added automatically if not set.       |
| `string`                  | UTF-8 encoded as-is. No `typ` defaulting — you're not producing a JWT. |
| `Uint8Array`              | Used as-is. No `typ` defaulting.                                       |

The verifier reads the payload back under the shape **it** declares — [`options.payload`](/jwt/jws/verifying#payload-typing), `"json"` by default. Signing a `string` or `Uint8Array` therefore pairs with `payload: "string"` / `payload: "bytes"` on `verify()`; a JSON object needs nothing.

::note
The key is never a `string`. Pass an `oct` JWK (from `generateJWK("HS256")`), a `Uint8Array` secret, a `CryptoKey`, or an asymmetric JWK — PEM text goes through [`importPEM()`](/jwk/pem) first. See [string keys](/jwt/jws/verifying#string-keys-are-not-jws-keys).
::

## Full signature

```ts
interface JWSSignOptions {
  alg?: JWSAlgorithm;
  protectedHeader?: StrictOmit<JWSHeaderParameters, "alg"> & { alg?: never };
  currentDate?: Date;
  expiresIn?: ExpiresIn;
  expiresAt?: Date;
  notBeforeIn?: ExpiresIn;
  notBeforeAt?: Date;
}
```

`expiresIn` and `expiresAt` are mutually exclusive; `notBeforeIn` and `notBeforeAt` are likewise mutually exclusive. `notBeforeIn: 0` is allowed and sets `nbf = iat` (an explicit temporal floor at sign time).
