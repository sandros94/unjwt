# Decrypting

```ts
decrypt(token, key, options?)
```

Parses a compact JWE, validates header allowlists, decrypts the payload, and validates JWT claims (when the decrypted payload is an object).

## Parameters

| Name                           | Type                                                                                |
| ------------------------------ | ----------------------------------------------------------------------------------- |
| `token`                        | `string` — the compact JWE                                                          |
| `key`                          | `CryptoKey \| JWKSet \| JWEDecryptJWK \| string \| Uint8Array \| JWKLookupFunction` |
| `options.algorithms`           | `KeyManagementAlgorithm[]` — allowlist for `alg`                                    |
| `options.encryptionAlgorithms` | `ContentEncryptionAlgorithm[]` — allowlist for `enc`                                |
| `options.payload`              | `"json" \| "string" \| "bytes"` — what the payload is. Defaults to `"json"`         |
| `options.validateClaims`       | `boolean` — force-skip claim validation                                             |
| `options.forceUint8Array`      | `boolean` — deprecated alias of `payload: "bytes"`                                  |
| `options.returnCek`            | `boolean` — include `cek` and `aad` in the result                                   |
| `options.minIterations`        | `number` — PBES2 `p2c` floor (default `1000` per RFC 7518)                          |
| `options.maxIterations`        | `number` — PBES2 `p2c` ceiling (default `1_000_000`)                                |
| `options.limits`               | `{ keyCandidates?, pbes2Iterations? }` — bounded work per call                      |
| Claim options                  | Same as `verify()` — `audience`, `issuer`, `subject`, `maxTokenAge`, etc.           |

`JWEDecryptJWK` is the private-side counterpart of [`JWEEncryptJWK`](/jwt/jwe/encrypting) — an `oct` JWK with a JWE symmetric `alg`, or a _private_ asymmetric JWK whose `alg` is RSA-OAEP or ECDH-ES. `JWKSet` stays fully permissive (`JWK[]`); wire JWKS are heterogeneous and the runtime filters candidates per header.

Returns `Promise<{ payload, protectedHeader, cek?, aad? }>`.

## The simple case

```ts
const { payload, protectedHeader } = await decrypt(token, key);
```

If the key is a JWK with an `alg` field (as `generateJWK()` produces), that `alg` is the one role the key holds and unjwt proceeds with it. A password `string` infers the three PBES2 variants plus `dir`. Raw `Uint8Array` bytes declare nothing at all, so the reading side names the algorithm the writing side used:

```ts [raw-bytes.ts]
const jwe = await encrypt(payload, rawBytes, { alg: "A256KW", enc: "A256GCM" });
const { payload: back } = await decrypt(jwe, rawBytes, { algorithms: ["A256KW"] });
```

::note
A `string` key is a **PBES2 password and nothing else**. Under any other `alg` it fails with `ERR_JWK_INVALID` (`"String keys are not accepted: …"`) rather than being silently used as raw key bytes — a password is low-entropy text, not a 256-bit key. To use one as a key, derive it once with [`deriveJWKFromPassword()`](/jwk/password-derivation).
::

## Algorithm allowlists

Two allowlists protect the decryptor:

- **`algorithms`** — which key-management (`alg`) values are acceptable.
- **`encryptionAlgorithms`** — which content-encryption (`enc`) values are acceptable.

When omitted, unjwt calls [`inferJWEAllowedAlgorithms`](/utilities#inferjweallowedalgorithms) to derive an `alg` allowlist from the key shape:

- `string` password → `["PBES2-HS256+A128KW", "PBES2-HS384+A192KW", "PBES2-HS512+A256KW", "dir"]`
- Raw `Uint8Array` → nothing; pass `algorithms` yourself
- Symmetric JWK → the one role its `alg` names; see [symmetric roles](#symmetric-key-roles)
- RSA private JWK → the matching `RSA-OAEP*` variants
- EC/OKP private JWK → the matching `ECDH-ES*` variants
- JWK Set → the union of its non-`oct` entries; see [JWK Sets](/jwk/jwk-sets#symmetric-entries)

If inference fails (lookup function, ambiguous key), pass explicitly:

```ts [explicit-allowlist.ts]
const { payload } = await decrypt(token, lookupFn, {
  algorithms: ["RSA-OAEP-256"],
  encryptionAlgorithms: ["A256GCM"],
});
```

### Symmetric key roles

An `oct` JWK's `alg` names the single role it holds, and roles do not alias:

| JWK `alg`                               | Serves                                                   |
| --------------------------------------- | -------------------------------------------------------- |
| `A128KW` / `A192KW` / `A256KW`          | that key wrapping alg only                               |
| `A128GCMKW` / `A192GCMKW` / `A256GCMKW` | that key wrapping alg only                               |
| `A*GCM`, `A*CBC-HS*`                    | `dir`, and only for a token whose `enc` is that same alg |
| `dir`                                   | `dir`, for any `enc` whose CEK length matches the key    |
| `PBES2-HS*+A*KW`                        | that PBES2 alg only                                      |

A key minted for `A256GCM` is a Content Encryption Key: it opens a `dir` token encrypted with `A256GCM`, and is refused both as an `A256GCMKW` wrapping key and as the CEK of a token whose `enc` is something else. A wrapping key is never accepted as a CEK. An algorithm outside the key's role is `ERR_JWE_ALG_NOT_ALLOWED` on decrypt and `ERR_JWK_INVALID` on encrypt; a `dir` key whose `enc` does not match is `ERR_JWK_INVALID` on both sides.

::tip
Setting `encryptionAlgorithms` is always a good idea — it's the only protection against a malicious token using a weaker-than-intended content cipher. `["A256GCM"]` is a strong default.
::

## Dynamic key resolution

Same as `verify()` — pass a function that receives the header:

```ts [lookup.ts]
const { payload } = await decrypt(
  token,
  async (header, _rawToken) => {
    return await keyStore.get(header.kid!);
  },
  { algorithms: ["ECDH-ES+A256KW"], encryptionAlgorithms: ["A256GCM"] },
);
```

A `JWKLookupFunction` can return a single key or a `JWKSet`; if it returns a set, the per-kid / per-alg retry logic applies.

## JWKSet — rotation and multi-key decryption

When you pass a `JWKSet` (directly or returned from a lookup), unjwt selects candidates like it does on the sign side:

1. Token's header has `kid` — only keys with that `kid` are tried.
2. No `kid` — all keys whose `alg` matches the token's `alg` are candidates, tried in order.
3. No candidates — throws `ERR_JWK_KEY_NOT_FOUND` before any crypto runs.
4. More than 8 candidates after filtering — also `ERR_JWK_KEY_NOT_FOUND`, before the first import. See [Bounded work per call](#bounded-work-per-call).

Useful when you rotate encryption keys: the new key wraps future tokens, but older tokens (wrapped with the previous key) still decrypt because both keys live in the set.

## Header and segment validation

Everything the protected header alone decides is settled before a key is resolved or imported — a malformed token never reaches key management:

| Check                 | Behaviour                                                                                                                                     |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `alg`                 | `"none"` and anything outside the key-management table → `ERR_JWE_ALG_NOT_ALLOWED`, before the `algorithms` allowlist                         |
| `enc`                 | outside the content-encryption table → `ERR_JWE_INVALID`                                                                                      |
| `zip`                 | compression is not implemented; a token carrying `zip` → `ERR_JWE_INVALID` (and `zip` in `protectedHeader` on encrypt → `ERR_INVALID_OPTION`) |
| `crit`                | validated on the protected header before key management, so a violation is `ERR_JWE_INVALID` whether or not the key would have worked         |
| `typ`                 | compared under RFC 7515 §4.1.9 media-type rules — `typ: "at+jwt"` matches a header carrying `"application/AT+JWT"`                            |
| Encrypted key         | `dir` and bare `ECDH-ES` carry no wrapped CEK, so a non-empty encrypted-key segment → `ERR_JWE_INVALID` instead of ignored bytes              |
| IV / tag length       | both fixed by `enc` and checked before the AEAD runs, so `ciphertext ‖ tag` cannot be re-split and a truncated tag is never compared          |
| `epk` / `apu` / `apv` | ECDH-ES ephemeral key validated against the recipient's curve with forged members stripped; `apu`/`apv` bounded at 1024 bytes each            |

## PBES2 DoS protection

The PBES2 `p2c` (iteration count) header field is **attacker-controlled** — a malicious sender could craft a token with `p2c: 1_000_000_000` to burn your CPU on decryption. unjwt guards against this by default:

```ts
minIterations: 1000; // RFC 7518 §4.8.1.2 mandated floor
maxIterations: 1_000_000; // sane ceiling
```

Any token outside this range is rejected with `ERR_JWE_INVALID` before PBKDF2 runs. These two bound a single unwrap; the whole call is bounded by the `pbes2Iterations` budget below. Override cautiously:

```ts
const { payload } = await decrypt(token, "password", {
  minIterations: 100_000, // require at least this many iterations
  maxIterations: 2_000_000, // allow stronger-than-default tokens
});
```

## Bounded work per call

A token names how much work it asks for — how many recipients to try, and at what PBKDF2 cost — and a JWK Set names how many keys to try it against. `limits` bounds all three, so an attacker holding no key cannot turn one request into unbounded CPU:

| Limit             | Default     | Exceeded                                                                        |
| ----------------- | ----------- | ------------------------------------------------------------------------------- |
| `recipients`      | `16`        | `ERR_JWE_INVALID`, before any recipient is read (`decryptMulti`)                |
| `keyCandidates`   | `8`         | `ERR_JWK_KEY_NOT_FOUND`, before the first key is imported                       |
| `pbes2Iterations` | `1_000_000` | `ERR_JWE_INVALID`, and the derivation that no longer fits the budget is not run |

`pbes2Iterations` is a budget for the **whole call**, summed across every PBES2 attempt — the single unwrap of a compact token, and one per recipient and per JWK Set candidate. 200 injected PBES2 recipients at `p2c: 1_000_000` therefore cost one budget, not two hundred:

```
JWTError: PBES2 iteration budget of 1000000 exhausted.
```

An attempt whose `p2c` no longer fits is skipped without spending anything, so a recipient you do hold the key for is still tried on what remains.

```ts
const { payload } = await decrypt(token, "password", {
  limits: { pbes2Iterations: 600_000, keyCandidates: 2 },
});
```

Each limit must be a positive integer; anything else is `ERR_INVALID_OPTION`. The defaults are exported as `DEFAULT_JOSE_LIMITS`:

```ts
import { DEFAULT_JOSE_LIMITS } from "unjwt/jwe";
// { signatures: 16, recipients: 16, keyCandidates: 8, pbes2Iterations: 1_000_000 }
```

## Returning the CEK

For custom verification flows (integrity checks over `aad`, manual key extraction), pass `returnCek: true`:

```ts
const { payload, cek, aad } = await decrypt(token, key, { returnCek: true });
// cek: Uint8Array — the derived Content Encryption Key
// aad: Uint8Array — the authenticated additional data (protected header bytes)
```

Most callers never need this.

## Claim validation

Identical to [JWS verify](/jwt/jws/verifying#claim-validation-options): under `payload: "json"` (the default), `exp`, `nbf` and `iat` are validated automatically, plus any of `audience` / `issuer` / `subject` / `maxTokenAge` / `requiredClaims` / `typ` you pass.

::warning
The `aud` claim is checked **only when `audience` is configured**. A token carrying `aud: "other-service"` is accepted by a decryptor that sets no `audience`. Configure `audience` wherever a token is meant for this recipient alone; that is what enforces [RFC 7519 §4.1.3](https://www.rfc-editor.org/rfc/rfc7519#section-4.1.3).
::

Pass `validateClaims: false` to opt out. `validateClaims: true` alongside `payload: "string"` or `"bytes"` is `ERR_INVALID_OPTION` — there is nothing to validate claims on, and the option must not look like it ran.

## Payload typing

`options.payload` declares what the encrypted content is. The decrypted bytes never decide their own shape, and the `typ` / `cty` headers — attacker-supplied like everything else on the wire — never pick it either.

| `payload`  | Result                    | Rejected when                                       |
| ---------- | ------------------------- | --------------------------------------------------- |
| `"json"`   | the generic `T` (default) | not UTF-8 JSON naming an object → `ERR_JWE_INVALID` |
| `"string"` | `string`                  | not valid UTF-8 → `ERR_JWE_INVALID`                 |
| `"bytes"`  | `Uint8Array<ArrayBuffer>` | never                                               |

```ts [typed.ts]
interface Session {
  userId: string;
  role: "admin" | "user";
}

const { payload } = await decrypt<Session>(token, key);
payload.role; // "admin" | "user"
```

Anything that is not a JSON object must say so:

```ts
const { payload: text } = await decrypt(token, key, { payload: "string" });
const { payload: bytes } = await decrypt(token, key, { payload: "bytes" });
bytes instanceof Uint8Array; // true
```

::warning
`forceUint8Array` is a deprecated alias of `payload: "bytes"` (removed in v0.9.0). Passing both with conflicting values is `ERR_INVALID_OPTION`.
::

## Full signature

```ts
interface JWEDecryptOptions extends JWTClaimValidationOptions {
  algorithms?: KeyManagementAlgorithm[];
  encryptionAlgorithms?: ContentEncryptionAlgorithm[];
  unwrappedKeyAlgorithm?: Parameters<typeof crypto.subtle.importKey>[2];
  keyUsage?: KeyUsage[];
  extractable?: boolean;
  payload?: "json" | "string" | "bytes";
  /** @deprecated Use `payload: "bytes"`. Removed in v0.9.0 */
  forceUint8Array?: boolean;
  validateClaims?: boolean;
  returnCek?: boolean;
  minIterations?: number;
  maxIterations?: number;
  limits?: { keyCandidates?: number; pbes2Iterations?: number };
}

interface JWEDecryptResult<T> {
  payload: T;
  protectedHeader: JWEProtectedHeader; // alg and enc required
  cek?: Uint8Array; // only when returnCek: true
  aad?: Uint8Array; // only when returnCek: true
}
```
