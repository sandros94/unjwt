# Multi-recipient

When a single encrypted payload needs to reach more than one recipient — a team document, a broadcast message, a fanned-out webhook — the compact serialization isn't enough. It can only carry one encrypted CEK.

[RFC 7516 §7.2](https://www.rfc-editor.org/rfc/rfc7516#section-7.2) defines the **General JSON Serialization**:

```json
{
  "protected": "<base64url of shared protected header>",
  "unprotected": { "kid-root": "2025-q1" },
  "recipients": [
    { "header": { "alg": "RSA-OAEP-256", "kid": "alice" }, "encrypted_key": "..." },
    { "header": { "alg": "ECDH-ES+A256KW", "kid": "bob", "epk": {...} }, "encrypted_key": "..." }
  ],
  "iv": "...",
  "ciphertext": "...",
  "tag": "..."
}
```

**One shared CEK** encrypts the payload once. The CEK is then **wrapped per recipient** with their own key and `alg`. Each recipient unwraps their own entry; the shared ciphertext is the same for everyone.

unjwt exposes two functions for this:

- [`encryptMulti()`](#encryptmulti) — produce the General serialization.
- [`decryptMulti()`](#decryptmulti) — unwrap using one recipient's key, return the shared payload.

Both importable from `unjwt/jwe` (or `unjwt`).

## `encryptMulti`

```ts [encrypt-multi.ts]
import { encryptMulti } from "unjwt/jwe";

const jwe = await encryptMulti(
  { doc: "quarterly numbers", quarter: "Q1" },
  [
    { key: aliceRsaPublicJwk }, // alg inferred → RSA-OAEP-256
    { key: bobEcdhPublicJwk }, // alg inferred → ECDH-ES+A256KW
    { key: sharedAesKwJwk, header: { "x-route": "eu" } }, // alg → A256KW, extra per-recipient header
  ],
  {
    enc: "A256GCM",
    expiresIn: "1h",
    sharedUnprotectedHeader: { "kid-set": "2025-q1" }, // top-level `unprotected`
    aad: new TextEncoder().encode("doc-id:42"), // external AAD binding (optional)
  },
);
```

The returned value is a plain JSON object — stringify it before sending over the wire.

### Per-recipient fields

| Field             | Role                                                                |
| ----------------- | ------------------------------------------------------------------- |
| `key`             | Recipient's key. **`key.alg` is required.**                         |
| `header`          | Fields in the per-recipient `header`. Cannot set `alg`/`enc`/`zip`. |
| `ecdh`            | ECDH-ES overrides (ephemeral key, partyUInfo, partyVInfo).          |
| `p2s`, `p2c`      | PBES2 parameters — only meaningful for a PBES2-keyed recipient.     |
| `keyManagementIV` | AES-GCMKW IV override.                                              |

### Forbidden algorithms

`dir` and bare `ECDH-ES` (without `+A*KW`) are **forbidden** in a multi-recipient envelope. Both require the recipient's key to _be_ the CEK — which can't be shared across multiple recipients without collapsing their security. Attempting either throws `ERR_JWE_ALG_FORBIDDEN_IN_MULTI`.

The fix is to use the key-wrap variants instead:

- `ECDH-ES+A128KW` / `+A192KW` / `+A256KW` — derives a KEK per recipient, wraps the shared CEK with it.

### Three header tiers

A multi-recipient JWE has **three** places a header field can live:

1. **`protected`** — shared, signed-over (part of AAD). Contains `enc`, `typ` (`"JWT"` by default for an object payload), and any custom fields you pass in `options.protectedHeader`.
2. **`unprotected`** — shared, _not_ part of AAD. Contains fields from `options.sharedUnprotectedHeader` (metadata that doesn't need cryptographic binding).
3. **Per-recipient `header`** — unshared, not part of AAD. Contains `alg`, `kid`, `epk`, `p2s`/`p2c`, and anything you pass in a recipient's `header`.

[RFC 7516 §7.2.1](https://www.rfc-editor.org/rfc/rfc7516#section-7.2.1) mandates **disjointness**: a parameter name cannot appear in more than one tier per recipient. Violations throw `ERR_JWE_HEADER_PARAMS_NOT_DISJOINT`.

Where a member may sit on decrypt:

| Member                 | Where                                                                                                                                                                                                                                                                                              |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `crit`                 | **Protected only** ([RFC 7516 §4.1.13](https://www.rfc-editor.org/rfc/rfc7516#section-4.1.13)). In the shared unprotected header it rejects the token; in a per-recipient header it skips that recipient.                                                                                          |
| names listed in `crit` | **Protected**, and present — a `crit` entry naming a member the protected header does not carry is `ERR_JWE_INVALID`.                                                                                                                                                                              |
| `enc`                  | **Protected or shared unprotected.** It is shared by every recipient, so a per-recipient header is never a place for it; absent from both shared tiers, the token is `ERR_JWE_INVALID`. `encryptionAlgorithms` applies to it wherever it sits. `encryptMulti` always protects it.                  |
| `alg`                  | Any tier — usually the per-recipient header, which is where `encryptMulti` writes it.                                                                                                                                                                                                              |
| `typ`                  | **Protected, for `options.typ`.** The expected `typ` is matched against the protected header alone, so a `typ` carried only in an unprotected tier never satisfies it — a type gate anyone could move would gate nothing. A protected header without `typ` is `ERR_JWE_INVALID`.                   |
| `kid`                  | **Any tier.** The key lookup function receives the merged header, so the `kid` it reads may come from an unprotected tier, which anyone can rewrite. It only chooses which key is tried: the recipient must still unwrap and the content must still authenticate under the key the lookup returns. |

The result's `protectedHeader` holds exactly what was integrity protected. A recipient's `alg` is read from `recipientHeader`, and an `enc` carried unprotected from `sharedUnprotectedHeader` — neither is copied into `protectedHeader`.

`encryptMulti` holds the same producer-side gates as [`encrypt`](/jwt/jwe/encrypting#custom-protected-header): a `crit` in `options.protectedHeader` must be a non-empty array of strings listing extensions the header itself carries — and a `crit` in `options.sharedUnprotectedHeader` or in a recipient's `header` is refused outright, since a consumer rejects it there — a `cek` or `contentEncryptionIV` must be the length `enc` fixes, `ecdh.partyUInfo` / `partyVInfo` must be `Uint8Array`s of at most 1024 bytes, every recipient entry and every header option must be an object, and a header that will not serialize to JSON is refused. Each is `ERR_INVALID_OPTION`.

### External AAD

`options.aad` binds the ciphertext to context that isn't part of the envelope — a document hash, a request URL, a transaction ID. The content cipher's AAD becomes `BASE64URL(protected) || '.' || BASE64URL(aad)`, so tampering with _either_ side (protected header or external AAD) fails authentication on decrypt. It is a `string` (UTF-8 encoded) or a `Uint8Array`; anything else is `ERR_INVALID_OPTION`. An empty `aad` is no AAD at all, so the `aad` member is left out ([RFC 7516 §7.2.1](https://www.rfc-editor.org/rfc/rfc7516#section-7.2.1)); `decryptMulti` still opens a token whose `aad` member is present but empty, authenticating `BASE64URL(protected) || '.'`.

## `decryptMulti`

```ts [decrypt-multi.ts]
import { decryptMulti } from "unjwt/jwe";

const { payload, recipientIndex, recipientHeader } = await decryptMulti(
  jweFromWire, // parsed JSON object — not the stringified form
  bobEcdhPrivateJwk,
);
```

`decryptMulti` tries each recipient entry until one unwrap succeeds, then decrypts the shared ciphertext with the unwrapped CEK. Compact tokens go through `decrypt()`; multi-recipient tokens always come through here.

### Recipient isolation

`recipients[]` sits outside the AAD — anyone holding the envelope can append an entry or rewrite an existing one, and the content ciphertext still authenticates. So a failure scoped to one recipient never ends the whole decryption: an entry that isn't a JSON object (or whose `header` isn't one), a header-tier overlap, a `crit` or `zip` in a recipient header, missing PBES2 `p2s`/`p2c`, a missing `epk`, missing AES-GCMKW `iv`/`tag`, an unsupported `alg`, or a failed unwrap all mean "try the next recipient". Only if no recipient works does the last such failure surface.

Verdicts on the token as a whole still throw immediately: the protected header (`zip`, `crit`, `typ`), `enc` (from the protected or shared unprotected header), a shared unprotected header that isn't a JSON object or carries `crit`, an overlap between the two shared tiers, the IV/tag/ciphertext segments, and — after a successful decryption — JWT claim validation.

### Bounded work per call

`recipients[]` is attacker-extendable, so the count and the work each entry asks for are bounded per call. At most **16** recipients are accepted — a token carrying more is `ERR_JWE_INVALID` before any of them is read — and every PBES2 attempt draws on one `pbes2Iterations` budget for the whole call, so injected PBES2 recipients cost one budget between them rather than one each:

```ts
await decryptMulti(jwe, myKey, {
  limits: { recipients: 4, keyCandidates: 2, pbes2Iterations: 600_000 },
});
```

A recipient whose `p2c` no longer fits the remaining budget is skipped without spending anything, so the recipient you hold a key for is still tried. See [Bounded work per call](/jwt/jwe/decrypting#bounded-work-per-call).

The two defaults are set to each other: `encryptMulti` mints each PBES2 recipient at `p2c: 600_000`, and the default `pbes2Iterations` budget of `2_400_000` covers four such attempts — so an envelope written entirely at the defaults is openable by its fourth PBES2 recipient without the caller raising anything. Past that, a holder of recipient five names a bigger budget, or the producer lowers `p2c` per recipient:

```ts
const jwe = await encryptMulti(payload, recipients, {}); // p2c: 600_000 each
await decryptMulti(jwe, myPassword); // budget: 2_400_000 — four attempts
```

### Header and segment validation

Everything listed under [compact decryption](/jwt/jwe/decrypting#header-and-segment-validation) applies here too, on the shared protected header and the shared content segments, with the per-recipient header supplying `alg`, `epk`, `p2s`/`p2c` and `iv`/`tag`. `crit` is only honoured when integrity protected ([RFC 7516 §4.1.13](https://www.rfc-editor.org/rfc/rfc7516#section-4.1.13)): in the shared unprotected header it rejects the token, in a per-recipient header it skips that recipient.

### Accepted serializations

Both **General** and **Flattened** are accepted — Flattened is auto-normalized to a single-recipient General envelope in memory before processing. An object without `recipients` is read as Flattened, whose `header` and `encrypted_key` are both optional ([RFC 7516 §7.2.2](https://www.rfc-editor.org/rfc/rfc7516#section-7.2.2)) — a Flattened `dir` or `ECDH-ES` token carries neither. An object that carries `recipients` together with a top-level `header` or `encrypted_key` is ambiguous and throws `ERR_JWE_INVALID_SERIALIZATION`.

### Key inputs

Same shape as `decrypt()`: a single key, a `JWKSet`, a lookup function, or a password string (PBES2 recipients only — any other `alg` rejects a `string` with `ERR_JWK_INVALID`).

### Payload typing

`options.payload` works exactly as it does on [`decrypt()`](/jwt/jwe/decrypting#payload-typing) — `"json"` (default), `"string"` or `"bytes"` — and applies to the shared plaintext:

```ts
const { payload } = await decryptMulti(jwe, bobPrivateJwk, { payload: "string" });
```

Return types follow the option, as on [`decrypt()`](/jwt/jwe/decrypting#return-types-follow-the-option): `payload` is `PayloadOf<Mode>` read off `JOSEPayloadTypeMap` — `string` here, `Uint8Array<ArrayBuffer>` for `"bytes"`, the claims for `"json"` (`decryptMulti<MyClaims>(jwe, key)`).

### Strict matching

`strictRecipientMatch: true` attempts a recipient only when the key material could plausibly open it, and throws `ERR_JWE_NO_MATCHING_RECIPIENT` when none can — no trial-and-error fallback.

A recipient is skipped only on a **definite** mismatch:

- both sides carry a `kid` and they differ;
- the key's `kty` / curve / length cannot serve the recipient's `alg` (an AES-KW key against an `RSA-OAEP-256` recipient, say);
- the recipient's `epk` is on a different curve than the key.

Key material with no identity of its own — a `CryptoKey`, raw bytes, a password — is **unknown, not mismatched**: a `kid` in the recipient header does not rule it out, and the compatibility check decides instead.

```ts
await decryptMulti(jwe, bobEcdhPrivateJwk, { strictRecipientMatch: true });
```

### Result fields

Extends the compact `decrypt` result with:

- `recipientIndex: number` — which entry of `recipients` unwrapped.
- `recipientHeader?` — the `header` field from that recipient entry.
- `sharedUnprotectedHeader?` — the top-level `unprotected` header, if present.

Its `protectedHeader` is the decoded `protected` member alone — `{}` when the serialization has none. Unlike compact `decrypt`, it carries `alg` and `enc` only when the producer protected them.

## Flattened form

For consumers that strictly expect **Flattened** serialization (single recipient, JSON shape):

```ts [flattened.ts]
import { encryptMulti, generalToFlattened } from "unjwt/jwe";

const general = await encryptMulti(payload, [singleRecipient], opts);
const flattened = generalToFlattened(general);
// { protected, unprotected?, header?, encrypted_key?, iv, ciphertext, tag, aad? }
```

Throws `ERR_JWE_INVALID_SERIALIZATION` if the input has zero or multiple recipients — Flattened is strictly single-recipient.

## Use cases

- **Team documents.** One encrypted file, unlocked by any authorized team member's private key.
- **Broadcast messages.** Encrypt once, fan out to N recipients — bandwidth proportional to N wraps, not N ciphertexts.
- **Revocable membership.** Re-encrypt when the recipient set changes — anyone removed from `recipients[]` can no longer decrypt future messages.
- **Hybrid public-key delivery.** Some recipients hold RSA keys, others EC — mix freely with different `alg` per recipient.

## How JWE multi-recipient differs from JWS multi-signature

They look similar but have substantively different shapes — see the matching [JWS multi-signature page](/jwt/jws/multi-signature) for the other angle. Highlights:

- **Shared protected header vs. per-signer.** JWE has one shared `protected` header (with `enc`, `typ`, etc., part of AAD) and per-recipient `header`. JWS has per-signer protected headers; nothing is shared.
- **Three header tiers vs. two.** JWE adds the `unprotected` (shared, non-authenticated) tier that JWS lacks.
- **Shared CEK.** One random CEK is used for content encryption, and each recipient gets their own wrapped copy. This is why `dir` and bare `ECDH-ES` can't appear in multi.
- **External AAD.** JWE binds to out-of-band context via `aad`. JWS has no analog — signatures already cover the whole payload.
- **"First recipient wins" semantics.** Decryption terminates as soon as one wrap succeeds. JWS signatures can all be checked independently.
