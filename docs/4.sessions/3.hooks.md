# Hooks

> Run your own code when a session is read, issued, cleared, expires or fails, and choose the key an incoming token is checked with.

Hooks are functions in the session config that the session calls at fixed moments: when it reads a token, issues one, clears itself, finds a token expired or finds one it cannot open. One more picks the key a token is checked with, for keys you fetch as tokens arrive. A hook gets the session as it stands at that moment, so it can log, refuse or change it. Each hook may return a promise, and the session waits for it.

## Before you start

- Hooks go in `hooks` of the config you pass to `defineJWSSession` or `defineJWESession`, described in [Configure a session](/sessions/configure).
- Every hook receives one object with `config`, the session's config, and `event`, what you passed to `use()`.
- A hook that throws makes the call that ran it reject. [What a throw does](#what-a-throw-does) lists each case.

## When each hook fires

| Hook          | Fires                                                                                            | Receives                                                                              | Can change the outcome                                                    |
| ------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `onRead`      | Once per request, when a valid token is read.                                                    | `session`, the live session                                                           | Yes: `session.clear()` or `session.update()` in the hook.                 |
| `onUpdate`    | After `update()` or `rolling` issued a token and, on a cookie session, wrote the cookie.         | `session`, `oldSession`, `trigger`                                                    | No, the token is out.                                                     |
| `onClear`     | After `clear()` emptied the session and, on a cookie session, expired the cookie.                | `oldSession`, or `undefined` without a session                                        | No.                                                                       |
| `onExpire`    | When the incoming session token is past its expiry, after a cookie session's cookie was expired. | `session` with the old `id`, `createdAt`, `expiresAt`, `token`, and `source`; `error` | No, the session is already empty.                                         |
| `onError`     | When an incoming token cannot be opened, and when issuing a token fails.                         | `session`, the live session; `error`                                                  | No.                                                                       |
| `onKeyLookup` | Before a session token is verified or decrypted, in `use()` and `open()`.                        | `header`, the token's protected header                                                | It picks the key that opens the token: a JWK, a `CryptoKey` or a JWK Set. |

- **One of three**: for each incoming token exactly one of `onRead`, `onExpire` and `onError` fires.
- **`oldSession`**: a copy of the session before the change, with its `id`, `createdAt`, `expiresAt`, `data`, `token` and `source`. On a first sign-in its `id` is `undefined`.
- **`source`**: every `session` and `oldSession` a hook receives carries `source`, `"cookie"`, `"header"` or `"token"`, the place this request's token came from. [Read, update and clear](/sessions/use#where-the-token-came-from) says what `update()` and `clear()` reach for each.
- **`trigger`**: `"update"` for a call to `update()`, `"rolling"` for a reissue by [`rolling`](/sessions/configure#set-the-lifetime).
- **`onExpire` error**: an `ERR_JWT_EXPIRED` [`JWTError`](/safety/errors). Only a token that is otherwise a valid session reaches `onExpire`; an expired token with a bad signature or another type goes to `onError`.
- **`onError` error**: on a read, an `ERR_SESSION_TOKEN_INVALID` `JWTError` whose `cause` is the reason, such as `ERR_JWS_SIGNATURE_INVALID`. On an `update()`, whatever issuing threw, such as `ERR_SESSION_CONFIG_INVALID` for a token too long for its cookies.
- **Not hooks**: a key the session cannot use is a configuration error and reaches no hook. Defining the session throws `ERR_SESSION_KEY_INVALID`, or, for a key of the right kind that doesn't import, the first `use()` does.

## Refuse a revoked session

Tokens carry their own expiry, so a session you want to end early has to be refused when it is read. `onRead` is the place, and `session.clear()` in it ends the session for this request. On a cookie session it also expires the cookie; a client that sent the token in the header or in hand keeps it and may send it again, so this hook records those:

<!-- automd:region src="../../examples/sessions/revocation.ts" -->

```ts [revocation.ts]
import { type SessionSource, defineJWESession } from "unjwt/session";

// const key = the "oct" JWK from SESSION_KEY (see Configure a session)

const THIRTY_DAYS = 30 * 24 * 60 * 60 * 1000;

export interface AppSession {
  userId: string;
  /** Set at sign-in and kept by every later update. */
  signedInAt: number;
}

export const appSession = defineJWESession<AppSession, "7D">({
  key,
  maxAge: "7D",
  rolling: "1D",
  sessionHeader: true,
  hooks: {
    async onRead({ session }) {
      const { userId, signedInAt } = session.data;
      const signedOut = await signedOutEverywhereAt(userId);
      const tooOld = Date.now() - signedInAt > THIRTY_DAYS;
      if ((signedOut === undefined || signedInAt > signedOut) && !tooOld) return;
      if (session.source !== "cookie") await reportRevokedToken(userId, session.source);
      await session.clear();
    },
  },
});

/** "Sign out of all devices": every session signed in until now stops opening. */
export async function signOutEverywhere(userId: string) {
  await saveSignedOutEverywhereAt(userId, Date.now());
}
```

<!-- /automd -->

- **Sign-in time in the data**: every `update()` issues a token with a new `id` and `createdAt`, so neither identifies a sign-in. `signedInAt` is written once and kept through every update, so it does.
- **Sign out everywhere**: one timestamp per user refuses every session signed in before it, on every device, at its next request.
- **An absolute limit**: `rolling` keeps an active cookie session alive forever. The 30-day check signs people out however active they are.
- **The handler sees the result**: after a `clear()` in `onRead`, the handler gets an empty session, as if the request had carried no token, whatever its source.
- **`sessionHeader: true`**: apps may also send the token in `x-unjwt-jwe-session`, so a token can arrive from the cookie, the header or your hand.
- **Branch on `source`**: `clear()` refuses the session on every source, but only a cookie can be taken back. A token from the header or in hand stays with its client until it expires, so the hook reports it, for a client to follow up or a stolen token to trace.

Sign-in writes the timestamp along with the user:

<!-- automd:region src="../../examples/sessions/revocation.ts" name="sign-in" -->

```ts [revocation.ts]
export async function signIn(req: Request, userId: string) {
  const headers = new Headers();
  const session = await appSession.use({ req, res: { headers } });
  await session.update({ userId, signedInAt: Date.now() });
  return new Response(null, { status: 204, headers });
}
```

## Record what happens

The other hooks suit an audit trail. Each one fires once for what it reports:

<!-- automd:region src="../../examples/sessions/audit-hooks.ts" -->

```ts [audit-hooks.ts]
import { defineJWSSession } from "unjwt/session";

// const key = an HS256 JWK loaded at start-up (see Configure a session)

export const appSession = defineJWSSession<{ userId: string }, "1h">({
  key,
  maxAge: "1h",
  hooks: {
    onRead: ({ session }) => audit("read", session.id),
    onUpdate: ({ session, oldSession, trigger }) =>
      audit(trigger === "rolling" ? "rolled" : "issued", session.id, oldSession.id),
    onClear: ({ oldSession }) => audit("signed out", oldSession?.id),
    onExpire: ({ session }) => audit("expired", session.id),
    onError: ({ error }) => audit("refused", undefined, error.code),
  },
});
```

<!-- /automd -->

With `audit` appending each call to `auditLog`, a sign-in, then a request that calls `use()` twice, updates the session and signs out, records this:

```ts
auditLog;
// [
//   ["issued", "0d6ffa5e-…", "-"],           sign-in: no session before
//   ["read", "0d6ffa5e-…"],                  the next request, however often it calls use()
//   ["issued", "8c41e2b7-…", "0d6ffa5e-…"],  update(): a new id, the old one from oldSession
//   ["signed out", "8c41e2b7-…"],            clear()
// ]
```

- **Read once**: the token is read on the first `use()` of a request, and later calls get that session back, so `onRead` fires once.
- **Read first**: getting the session is a read, so `onRead` comes before any `onUpdate` or `onClear` in the same request.
- **Then rolling**: a reissue by `rolling` runs after `onRead`, on a cookie session alone, and only when `onRead` left the session as it found it.
- **Settled state**: every hook runs after the session state is settled. A hook may call `use(event)` on the same event, such as `onExpire` opening another session to issue a new one, and gets the same session back without firing `onRead` again.

## Rotate keys

Give every key a `kid` and pass them to `key` as one [JWK Set](/jwk/sets), newest key first. The first key issues every token and writes its `kid` into the header; every key in the set opens tokens, and the token's `kid` picks the one to try:

<!-- automd:region src="../../examples/sessions/key-rotation.ts" name="jwe" -->

```ts [key-rotation.ts]
import { type JWKSet, type JWK_oct, defineJWESession, defineJWSSession } from "unjwt/session";

// A JWK Set as JSON, newest key first: { "keys": [{ "kid": "2026-10", … }, { "kid": "2026-09", … }] }
const sealing = process.env.SESSION_KEYS;
if (!sealing) throw new Error("SESSION_KEYS is not set");
const sessionKeys: JWKSet<JWK_oct<"A256KW">[]> = JSON.parse(sealing);

export const appSession = defineJWESession<{ userId: string }, "7D">({
  key: sessionKeys,
  maxAge: "7D",
});
```

<!-- /automd -->

- **Rotating**: add the new key at the front of the set and deploy. New tokens carry the new `kid`; tokens of the older keys still open.
- **Retiring**: once `maxAge` has passed since the deploy, drop the oldest key. A token whose `kid` names no key in the set fails like a tampered one: `onError` gets `ERR_SESSION_TOKEN_INVALID` with `ERR_JWK_KEY_NOT_FOUND` as `cause`, and the session is empty.
- **Checked at start-up**: each key in the set is checked as a lone `key` would be. An empty set, or an entry that isn't an `oct` JWK, a `CryptoKey` included, makes defining the session throw `ERR_SESSION_KEY_INVALID`. A pinned algorithm applies to the first key alone, and must be one it serves.
- **Keys without `kid`**: a token without `kid` is tried against every key of its algorithm and every key without `alg`, in order. The tokens of a key without `kid` carry none, so defining the session throws `ERR_SESSION_CONFIG_INVALID` when they would be tried against more keys than `limits.keyCandidates` in `jwe.decryptOptions` or `jws.verifyOptions`, 8 by default. Give every key a `kid` and the limit never applies.

### Rotate with onKeyLookup

Some keys can't sit in a set you load at start-up, such as keys you fetch from a secret manager as tokens arrive, so that a key added or removed there takes effect without a restart. `onKeyLookup` receives the token's protected header and returns the key that opens it, in the shapes `key` takes: a JWK, a `CryptoKey` or a JWK Set. `key` still issues every token:

<!-- automd:region src="../../examples/sessions/key-lookup.ts" -->

```ts [key-lookup.ts]
import { type JWESessionOctJWK, defineJWESession } from "unjwt/session";

// const secrets = your secret manager: get(name) resolves the secret stored under that name

// The kid of the key that issues, set at deploy. Every session key stays in the secret manager under its kid
const currentKid = process.env.SESSION_KEY_ID;
if (!currentKid) throw new Error("SESSION_KEY_ID is not set");
const current = await sessionKey(currentKid);
if (!current) throw new Error(`No session key "${currentKid}" in the secret manager`);

export const appSession = defineJWESession<{ userId: string }, "7D">({
  key: current,
  maxAge: "7D",
  hooks: {
    async onKeyLookup({ header }) {
      const key = header.kid ? await sessionKey(header.kid) : undefined;
      return { keys: key ? [key] : [] };
    },
  },
});

async function sessionKey(kid: string): Promise<JWESessionOctJWK | undefined> {
  const json = await secrets.get(`session-keys/${kid}`);
  return json ? JSON.parse(json) : undefined;
}
```

<!-- /automd -->

::warning
Return the key that issues tokens too. With `onKeyLookup` set, what it returns alone opens tokens, so a lookup that misses `key` refuses every fresh token and signs each visitor out at their next request.
::

- **An unknown `kid`**: an empty set fails the token like a tampered one, with `ERR_JWK_KEY_NOT_FOUND` as `cause`, and a cookie session's cookie is expired.
- **A secret manager that fails**: a lookup that throws fails the token too but keeps the cookie, as [What a throw does](#what-a-throw-does) describes.
- **A returned set**: the token's `kid` picks its keys, and a token without `kid` is tried against each key of its algorithm in order, up to `limits.keyCandidates`. Past that the token is refused, with `ERR_JWK_KEY_NOT_FOUND` as `cause`.
- **Algorithms**: a token opens only under an algorithm `key` serves or `algorithms` lists. With `onKeyLookup` set, `algorithms` may list ones that only the keys it returns serve.
- **A `CryptoKey` in a rotation**: export it to a JWK with [`exportJWK`](/jwk/import-export#export-a-cryptokey-as-a-jwk) and put it in the JWK Set you pass to `key`, as in [Rotate keys](#rotate-keys), so the session checks it when it is defined.
- **A `CryptoKey` from your own lookup**: nothing checks what `onKeyLookup` returns when the session is defined, and a `CryptoKey` names no algorithm, so list the ones it serves in `algorithms`. Without them its tokens fail with `ERR_JWS_ALG_NOT_ALLOWED` or `ERR_JWE_ALG_NOT_ALLOWED` as `cause`.
- **Lookups and `open()`**: `onKeyLookup` also runs for `open()`, which has no request, so `event` is optional there.

### Change the algorithm

A signed session with HMAC keys rotates with a set too, and the newest key may use another algorithm, such as HS512 after HS256:

<!-- automd:region src="../../examples/sessions/key-rotation.ts" name="jws" -->

```ts [key-rotation.ts]
// The same layout for HMAC keys, here while moving from HS256 to HS512: the newest key signs HS512
const signing = process.env.SIGNING_KEYS;
if (!signing) throw new Error("SIGNING_KEYS is not set");
const signingKeys: JWKSet<JWK_oct<"HS256" | "HS512">[]> = JSON.parse(signing);

export const signedSession = defineJWSSession<{ userId: string }, "1h">({
  key: signingKeys,
  maxAge: "1h",
});
```

<!-- /automd -->

- **Each key serves its own `alg`**: the HS512 key signs, and the HS256 keys behind it still verify their tokens, with no `algorithms` list. Once the last HS256 key is dropped, HS256 tokens are refused.
- **A key without `alg`**: it serves only what its material carries among the algorithms `jws.verifyOptions.algorithms` or `jwe.decryptOptions.algorithms` lists, or, for the first key, the pin. Defining the session throws `ERR_SESSION_CONFIG_INVALID` when neither names one. Keep `alg` on every key and you need no list.
- **Encrypted sessions**: an older `A128KW` key opens its tokens under a newest `A256KW` one. The content encryption, `enc`, needs nothing either: a key-wrapping key opens tokens of every `enc`, a `dir` key only its own.

### Rotate a key pair

A key pair rotates through `publicKey`, which takes a list or a JWK Set. Sign with the new private key, and verify with its public half and the public halves of the keys before it:

<!-- automd:region src="../../examples/sessions/key-pair-rotation.ts" -->

```ts [key-pair-rotation.ts]
import {
  type JWKSet,
  type JWK_EC_Private,
  type JWK_EC_Public,
  defineJWSSession,
  toPublicJWK,
} from "unjwt/session";

// The private ES256 JWK that signs from now on, as JSON
const json = process.env.SESSION_SIGNING_KEY;
if (!json) throw new Error("SESSION_SIGNING_KEY is not set");
const privateKey: JWK_EC_Private<"ES256"> = JSON.parse(json);

// The public halves of the keys that signed before it, as a JWK Set: { "keys": [{ "kid": "2026-09", … }] }
const earlier: JWKSet<JWK_EC_Public<"ES256" | "ES384" | "ES512">[]> = JSON.parse(
  process.env.SESSION_EARLIER_KEYS ?? '{ "keys": [] }',
);

export const signedSession = defineJWSSession<{ userId: string }, "1h">({
  key: { privateKey, publicKey: [toPublicJWK(privateKey), ...earlier.keys] },
  maxAge: "1h",
});
```

<!-- /automd -->

- **The new public half stays in the list**: it verifies every token the new key signs.
- **Older algorithms**: each public JWK in the list serves its own `alg`, so an earlier ES384 key verifies its tokens without `algorithms`. A JWK without `alg`, other than an EC or OKP key whose curve names its algorithm, needs that algorithm in `jws.verifyOptions.algorithms`, or defining the session throws `ERR_SESSION_CONFIG_INVALID`.
- **Retiring**: drop a public half from `SESSION_EARLIER_KEYS` once its last token has expired. Its tokens then fail with `ERR_JWK_KEY_NOT_FOUND` as `cause`.

## What a throw does

| Hook throws                     | Result                                                                                                                                                                                        |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `onRead`                        | `use()` rejects with your error.                                                                                                                                                              |
| `onExpire`, `onError` on a read | `use()` rejects with your error. The session is already empty and a cookie session's cookie expired.                                                                                          |
| `onUpdate`                      | `update()` rejects with your error. The new token and its cookie stay.                                                                                                                        |
| `onClear`                       | `clear()` rejects with your error. The session is already empty and a cookie session's cookie expired.                                                                                        |
| `onError` after a failed issue  | Runs after the session was put back as it was; `update()` then rejects.                                                                                                                       |
| a key lookup                    | The token fails: `onError` gets `ERR_SESSION_TOKEN_INVALID` whose `cause` is `ERR_JWK_KEY_NOT_FOUND`, with your error as its own `cause`, and the session is empty. `open()` throws the same. |

A failing key lookup is the one token failure that keeps the cookie: a key store that is down says nothing about the token, and dropping cookies then would sign everyone out.

::warning
When `onRead` throws, `use()` rejects and the session is left empty for the rest of the request: a later `use()` in the same request returns that empty session and does not run `onRead` again. The cookie stays where it is, because a hook that fails says nothing about the token. Let a revocation check that cannot answer end the request with an error instead of catching it and carrying on.
::
