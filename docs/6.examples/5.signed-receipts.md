# Sign receipts

> Several parties sign the same payload, and each verifier decides which signatures it needs.

## The job

A bank transfer needs three signatures on one record: the **user** who authorized it, the **service** that executed it, and a **notary** that witnessed it. Each signs with its own key and algorithm, at its own time. Later an auditor checks the record and asks a policy question: did all three sign? did the notary sign? did two of three approvers sign?

A compact JWS has one signature slot. The JWS JSON serialization ([RFC 7515 §7.2](https://www.rfc-editor.org/rfc/rfc7515#section-7.2)) carries one payload and a `signatures[]` array, and leaves the policy to the application. [`signMulti()`](/jwt/jws/multi) writes it and [`verifyMultiAll()`](/jwt/jws/multi) reports on every signature without throwing.

## Sign and check

```ts [receipts.ts]
import {
  signMulti,
  verifyMultiAll,
  type JWSGeneralSerialization,
  type JWSSignJWK,
} from "unjwt/jws";
import type { JWK, JWKLookupFunction } from "unjwt/jwk";

export const RECEIPT_TYP = "receipt+jwt";

export type Signer = { role: string; publicKey: JWK };
export const signers = new Map<string, Signer>(); // kid -> signer

export type ReceiptClaims = {
  iss: string;
  sub: string;
  jti: string;
  iat: number;
  exp: number;
  transfer: { to: string; amount: string; currency: string };
};

export async function countersign(
  claims: ReceiptClaims,
  key: JWSSignJWK,
  receipt?: JWSGeneralSerialization,
): Promise<JWSGeneralSerialization> {
  const signed = await signMulti(claims, [{ key, protectedHeader: { typ: RECEIPT_TYP } }]);
  if (!receipt) return signed;
  if (signed.payload !== receipt.payload) throw new Error("Receipt payload differs");
  return { payload: receipt.payload, signatures: [...receipt.signatures, ...signed.signatures] };
}

export async function checkReceipt(receipt: JWSGeneralSerialization, required: string[]) {
  const outcomes = await verifyMultiAll<ReceiptClaims>(receipt, lookupSigner, {
    algorithms: ["ES256", "Ed25519", "PS256"],
    typ: RECEIPT_TYP,
    issuer: "https://transfers.example.com",
    requiredClaims: ["jti", "exp"],
  });

  const signedBy = new Set<string>();
  let claims: ReceiptClaims | undefined;
  for (const outcome of outcomes) {
    if (!outcome.verified) continue;
    const signer = signers.get(outcome.protectedHeader.kid ?? "");
    if (signer) signedBy.add(signer.role);
    claims = outcome.payload;
  }

  const missing = required.filter((role) => !signedBy.has(role));
  return { valid: missing.length === 0, claims, signedBy: [...signedBy], missing, outcomes };
}

const lookupSigner: JWKLookupFunction<JWK> = (header) => {
  const signer = header.kid ? signers.get(header.kid) : undefined;
  if (!signer) throw new Error(`Unknown signer: ${header.kid}`);
  return signer.publicKey;
};
```

The user's device fixes the claims, `iat` and `exp` included, and every party signs that exact object. `countersign` refuses to merge a signature over different bytes. Each party runs it with its own key and passes the envelope on:

```ts
// user: ES256, service: Ed25519, notary: PS256; each public key registered in `signers`
let receipt = await countersign(claims, user.privateKey);
receipt = await countersign(claims, service.privateKey, receipt);
receipt = await countersign(claims, notary.privateKey, receipt);
// 3 signatures, 1241 bytes as JSON
// signatures[2] protected header: { kid: "fdb6rtHgCS7f…", typ: "receipt+jwt", alg: "PS256" }

await checkReceipt(receipt, ["user", "service", "notary"]);
// valid: true, signedBy: ["user", "service", "notary"], missing: []
// claims.transfer: { to: "IT60X0542811101000000123456", amount: "500.00", currency: "EUR" }
```

## Other policies

The outcomes array is the raw material. A quorum counts distinct signers, so one signature copied twice counts once:

```ts
const { outcomes } = await checkReceipt(approval, []);
const approvedBy = new Set(
  outcomes
    .filter((o) => o.verified && signers.get(o.protectedHeader.kid ?? "")?.role === "approver")
    .map((o) => o.protectedHeader.kid),
);
const quorum = approvedBy.size >= 2;
// two approvers signed:      2, true
// one approver's signature twice: 1, false
```

An audit log keeps every outcome, verified or not: `o.signerIndex`, `o.protectedHeader?.kid`, and `o.verified ? "ok" : o.error.code`. When any one trusted signature is enough, [`verifyMulti()`](/jwt/jws/multi) returns the first that verifies and throws when none does.

## What to store

- **Each signer:** its private key. The service and the notary keep theirs server side; the user's lives on the device.
- **The verifier:** the signer registry, `kid` to role and public key. This is the trust decision: a key that is not in it does not count, whatever it signed.
- **The receipt:** the JSON envelope as received, byte for byte, next to the transfer it covers. Re-serializing the claims would change the payload and break every signature.

## When it fails

`verifyMultiAll` throws only when the envelope itself is unusable. Everything else lands in the outcome for that signature:

| Case                                 | Outcome                                                          | `message`                                                                          |
| ------------------------------------ | ---------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| One signature altered                | `2: ERR_JWS_SIGNATURE_INVALID`, others ok; `missing: ["notary"]` | `JWS signature[2] verification failed.`                                            |
| Amount changed in the payload        | every signature `ERR_JWS_SIGNATURE_INVALID`                      |                                                                                    |
| A stranger appended a signature      | `3: ERR_JWK_KEY_NOT_FOUND`, others ok; still `valid`             | `Key lookup failed for signature[3].` with `cause` `Unknown signer: 4akxiOAQRsT3…` |
| Only the user signed                 | `valid: false`, `missing: ["notary"]`                            |                                                                                    |
| Checked after `exp`                  | every signature `ERR_JWT_EXPIRED`                                |                                                                                    |
| Not an envelope (`{ payload: "x" }`) | thrown: `ERR_JWS_INVALID_SERIALIZATION`                          | `Invalid JWS JSON Serialization: missing "signatures" or "signature".`             |

Treat `valid: false` as a refusal of the receipt, and log the per-signature codes. A stranger's signature is noise: the policy only looks at roles from the registry, so it neither helps nor blocks.

## Why these choices

- **The application owns the policy.** [RFC 7515 §7.2](https://www.rfc-editor.org/rfc/rfc7515#section-7.2) leaves to the application which signatures must validate. `verifyMultiAll` reports, `checkReceipt` decides.
- **Signers named by `kid`, trusted by registry.** `kid` selects the key ([RFC 7515 §4.1.4](https://www.rfc-editor.org/rfc/rfc7515#section-4.1.4)); the registry decides whether that key's owner matters. The resolver throws for an unknown `kid`, which becomes that signature's outcome.
- **An allow-list across signers.** `algorithms` names the three algorithms the registry's keys use; anything else is refused per signature ([RFC 8725 §3.1](https://www.rfc-editor.org/rfc/rfc8725#section-3.1)).
- **`typ` in each protected header.** `typ: "receipt+jwt"` is matched against the protected header only, so a signature over some other document type by the same key does not count ([RFC 8725 §3.11](https://www.rfc-editor.org/rfc/rfc8725#section-3.11)).
- **`exp` on a receipt.** A receipt is a bounded claim: after 30 days the verifier refuses it, and a long-term archive verifies with `currentDate` set to the time of the dispute.
