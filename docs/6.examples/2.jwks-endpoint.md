# Publish and consume a JWKS

> An issuer serves its public keys at a URL, and every API that trusts it verifies tokens against that set.

## The job

An authorization server signs tokens with a private key and publishes the matching public keys as a JWK Set ([RFC 7517 §5](https://www.rfc-editor.org/rfc/rfc7517#section-5)), usually at `/.well-known/jwks.json`. Any API can then verify those tokens without being able to mint them. The `kid` in each token's header says which key in the set signed it.

This recipe writes both halves: the issuer that serves the set, and the API that fetches, caches and refreshes it. The second half is the same code you would write against an external provider.

## The issuer

```ts [issuer.ts]
import { H3 } from "h3";
import { sign } from "unjwt/jws";
import { generateJWK, type JWKSet } from "unjwt/jwk";

// In production both pairs come from your secret store, never from a fresh boot.
const current = await generateJWK("ES256", { use: "sig" });
const previous = await generateJWK("ES256", { use: "sig" });

const jwks: JWKSet = { keys: [current.publicKey, previous.publicKey] };

export const app = new H3();

app.get("/.well-known/jwks.json", (event) => {
  event.res.headers.set("cache-control", "public, max-age=300");
  return jwks;
});

export function issueAccessToken(userId: string, audience: string): Promise<string> {
  return sign({ sub: userId, iss: "https://auth.example.com", aud: audience }, current.privateKey, {
    expiresIn: "10m",
    protectedHeader: { typ: "at+jwt" },
  });
}
```

[`generateJWK()`](/jwk/generate) returns a pair whose `kid` is the [RFC 7638](https://www.rfc-editor.org/rfc/rfc7638) thumbprint of the public key, so both halves share it. Only `publicKey` goes into the set; it carries no `d`. One entry as served:

```ts
// GET /.well-known/jwks.json -> 200, cache-control: public, max-age=300
// { use: "sig", kty: "EC", crv: "P-256",
//   x: "UhVDXSa7d9te…", y: "L92Sac2ZfEPm…", alg: "ES256", kid: "vRoctiNLt12l…" }
```

## The verifier

```ts [verifier.ts]
import { verify } from "unjwt/jws";
import type { JWKLookupFunction, JWKSet } from "unjwt/jwk";
import { isJWKSet, safeJsonParse } from "unjwt/utils";

const ISSUER = "https://auth.example.com";
const JWKS_URL = `${ISSUER}/.well-known/jwks.json`;
const CACHE_TTL_MS = 10 * 60_000;
const MIN_REFETCH_MS = 30_000;

let cached: { set: JWKSet; fetchedAt: number } | undefined;
let inflight: Promise<JWKSet> | undefined;

export function verifyAccessToken(token: string) {
  return verify(token, lookupIssuerKey, {
    algorithms: ["ES256"],
    typ: "at+jwt",
    issuer: ISSUER,
    audience: "https://api.example.com",
    requiredClaims: ["sub", "exp"],
  });
}

const lookupIssuerKey: JWKLookupFunction<JWKSet> = async (header) => {
  const set = await getJWKS();
  const known = set.keys.some((key) => key.kid === header.kid);
  return known ? set : getJWKS({ refresh: true });
};

async function getJWKS(options: { refresh?: boolean } = {}): Promise<JWKSet> {
  const age = cached ? Date.now() - cached.fetchedAt : Infinity;
  const due = age > CACHE_TTL_MS || (options.refresh && age > MIN_REFETCH_MS);
  if (cached && !due) return cached.set;
  inflight ??= fetchJWKS().finally(() => (inflight = undefined));
  return inflight;
}

async function fetchJWKS(): Promise<JWKSet> {
  const response = await fetch(JWKS_URL, { headers: { accept: "application/json" } });
  if (!response.ok) throw new Error(`JWKS fetch failed with ${response.status}`);
  const body: unknown = safeJsonParse(await response.text());
  if (!isJWKSet(body)) throw new Error("JWKS response is not a JWK Set");
  cached = { set: body, fetchedAt: Date.now() };
  return body;
}
```

[`verify()`](/jwt/jws/verify) calls the lookup with the decoded header and tries the returned [JWK Set](/jwk/sets): the header `kid` selects the candidate, and a token with no `kid` is tried against every entry up to the `limits.keyCandidates` cap (8). The run, with the issuer above served through `toWebHandler`:

```ts
await verifyAccessToken(tokenFromCurrent); // ok, user_42, kid vRoctiNL…   fetches: 1
await verifyAccessToken(tokenFromPrevious); // ok, user_7,  kid 0vPsu_0M…   fetches: 1
// three verifications in parallel on a cold cache                         fetches: 1
```

## What to store

- **Issuer:** the private half of every key still signing or still inside the lifetime of tokens it signed. The set publishes the public halves of the same list, a store that holds only the private halves alone can get them from [`toPublicJWK()`](/jwk/generate#storing-the-private-key-alone).
- **Verifier:** the fetched set and the time it was fetched, in memory. Nothing per token. `inflight` makes concurrent cold requests share one fetch.
- **Rotation, in order:** publish the new public key, wait one cache lifetime so every verifier has seen it, start signing with it, then remove the old key once the last token it signed has expired (10 minutes here).

```ts
// the issuer now signs with `next`; the verifier's cache predates it
await verifyAccessToken(tokenFromNext); // ok, kid gCGFL2Kq…   fetches: 2 (unknown kid, refetched)
await verifyAccessToken(tokenFromStranger); // ERR_JWK_KEY_NOT_FOUND   fetches: 2 (refetch floor)
```

## When it fails

| Case | `code` | `message` |
| --- | --- | --- |
| `kid` not in the set, even after a refetch | `ERR_JWK_KEY_NOT_FOUND` | `No key found in JWK Set with kid "5HQWFJP7ATQf…".` |
| The lookup threw (endpoint down) | `ERR_JWK_KEY_NOT_FOUND` | `Key lookup failed for the JWS.`, with `cause` the thrown error: `JWKS fetch failed with 503` |
| Token for another API | `ERR_JWT_CLAIM_INVALID` | `Invalid JWT "aud": expected https://api.example.com, got https://billing.example.com` |
| An `oct` key slipped into the set signed the token | `ERR_JWS_ALG_NOT_ALLOWED` | `Algorithm not allowed: HS256` |

Answer all of them with a 401, as in [Authenticate requests](/examples/authentication-basics). Separate the endpoint-down case in your logs: when `isJWTError(error, "ERR_JWK_KEY_NOT_FOUND")` carries a `cause`, the fault is on your side of the network and deserves an alert rather than a quiet 401.

::warning Refetch on an unknown `kid`, and rate-limit that refetch. Without the floor, anyone can send tokens with random `kid` values and make your API hammer the issuer. ::

## Why these choices

- **`algorithms: ["ES256"]`.** The provider documents what it signs with; accept that and nothing else ([RFC 8725 §3.1](https://www.rfc-editor.org/rfc/rfc8725#section-3.1)). A set fetched from the network can contain anything, and inferring the allow-list from it would hand the choice to the network.
- **Symmetric entries are ignored.** An `oct` key in a public set would let anyone who reads the set mint HMAC tokens. `verify` skips `oct` entries of a set unless `allowSymmetricJWKSet` is set, which you never set for a fetched set.
- **`kid` as the selector.** [RFC 7515 §4.1.4](https://www.rfc-editor.org/rfc/rfc7515#section-4.1.4) defines `kid` as a hint for choosing the key. It selects candidates; the signature still has to verify under the selected key.
- **`typ`, `iss`, `aud`.** One issuer usually signs ID tokens, access tokens and more with the same key. `typ: "at+jwt"` ([RFC 9068 §2.1](https://www.rfc-editor.org/rfc/rfc9068#section-2.1)) keeps an ID token out of your API, and `aud` keeps a token minted for another API out ([RFC 8725 §3.9](https://www.rfc-editor.org/rfc/rfc8725#section-3.9)). Check what your provider actually puts in `typ` before pinning it.
- **`safeJsonParse` and `isJWKSet`.** The response body is untrusted input. [`safeJsonParse`](/utils) strips prototype-pollution keys, and the [guard](/utils/guards) refuses a body that is not a set before it reaches `verify`.
- **Import cache.** Key imports are cached per JWK object, so replacing the set on refetch imports the new keys once; see [the JWK cache](/jwk/cache).
