# Rotate refresh tokens

> A short-lived access token for every request, a long-lived refresh token to replace it, and a new refresh token each time one is used.

## The job

An access token that lives 15 minutes limits the damage of a stolen copy, but nobody wants to log in every 15 minutes. A refresh token bridges the gap: it lives for days and its only use is minting the next access token. Because it lives so long, each use replaces it with a new one, and presenting a replaced token is treated as theft ([RFC 9700 §4.14.2](https://www.rfc-editor.org/rfc/rfc9700#section-4.14.2)).

On H3 both tokens are cookie sessions from [`unjwt/adapters/h3v2`](/adapters/h3). The access token is a signed (JWS) session; the refresh token is an encrypted (JWE) session, so the client cannot read the bookkeeping inside it.

## Sessions

```ts [sessions.ts]
import type { H3Event } from "h3";
import { defineJWESession, defineJWSSession, generateJWK } from "unjwt/adapters/h3v2";
import { rotateFamily, revokeFamily } from "./store";
import { findUser } from "./users";

// Load both from your secret store; generating them at boot signs everyone out on deploy.
const accessKeys = await generateJWK("ES256");
const refreshKey = await generateJWK("A256KW");

export type AccessData = { sub: string; roles: string[] };
export type RefreshData = { sub: string; family: string; gen: number };

export const accessSession = defineJWSSession<AccessData, "15m">({
  key: accessKeys,
  name: "__Host-access",
  maxAge: "15m",
  cookie: { httpOnly: true },
  jws: { signOptions: { alg: "ES256" } },
});

export const refreshSession = defineJWESession<RefreshData, "7D">({
  key: refreshKey,
  name: "__Host-refresh",
  maxAge: "7D",
  jwe: { encryptOptions: { alg: "A256KW", enc: "A256GCM" } },
  hooks: {
    onClear({ oldSession }) {
      if (oldSession?.data.family) revokeFamily(oldSession.data.family);
    },
    onError({ error }) {
      console.warn("refresh token refused", error.code, error.cause?.code);
    },
  },
});

export async function authenticate(event: H3Event): Promise<AccessData | undefined> {
  const access = await accessSession.use(event);
  if (access.id) return access.data;

  const refresh = await refreshSession.use(event);
  if (!refresh.id) return undefined;

  const { sub, family, gen } = refresh.data;
  const user = findUser(sub);
  const verdict = rotateFamily(family, gen);
  if (!user || verdict === "reused") {
    await refresh.clear();
    return undefined;
  }

  if (verdict === "rotated") await refresh.update({ gen: gen + 1 });
  await access.update({ sub, roles: user.roles });
  return access.data;
}
```

`authenticate` refreshes whenever the access session is empty. That covers both ways an access token ends: a browser drops the cookie at its `Expires` (the adapter sets it to the token's `exp`), and a client that still sends an expired cookie gets `onExpire` and an empty session. Roles are read from the user record at each refresh, so a role change lands within 15 minutes.

## The family store

Every login starts a _family_. The store keeps one generation counter per family; the refresh token carries the generation it was issued at.

```ts [store.ts]
type FamilyState = { gen: number; rotatedAt: number };

const families = new Map<string, FamilyState>();
const ROTATION_GRACE_MS = 10_000;

export function startFamily(): string {
  const family = crypto.randomUUID();
  families.set(family, { gen: 0, rotatedAt: Date.now() });
  return family;
}

export function rotateFamily(family: string, gen: number): "rotated" | "raced" | "reused" {
  const state = families.get(family);
  if (state?.gen === gen) {
    state.gen = gen + 1;
    state.rotatedAt = Date.now();
    return "rotated";
  }
  if (state?.gen === gen + 1 && Date.now() - state.rotatedAt < ROTATION_GRACE_MS) {
    return "raced";
  }
  return "reused";
}

export function revokeFamily(family: string): void {
  families.delete(family);
}
```

`rotateFamily` is a compare-and-swap. In a database it is one statement, `UPDATE families SET gen = gen + 1 … WHERE id = ? AND gen = ?`, and one updated row means you won. A request that loses by a few seconds is a parallel request from the same browser (`raced`): it gets a new access token and leaves the refresh cookie to the winner. Anything older is a replay (`reused`), and clearing it fires `onClear`, which revokes the whole family.

## Routes

`findUser` and `checkCredentials` live in your user module (`./users`); the run used an in-memory map with one user.

```ts [app.ts]
import { H3, HTTPError, readBody } from "h3";
import { accessSession, authenticate, refreshSession } from "./sessions";
import { startFamily } from "./store";
import { checkCredentials } from "./users";

export const app = new H3();

app.post("/login", async (event) => {
  const body = await readBody<{ username?: string; password?: string }>(event);
  const user = checkCredentials(body?.username, body?.password);
  if (!user) throw new HTTPError({ status: 401, message: "Invalid credentials" });

  const refresh = await refreshSession.use(event);
  const access = await accessSession.use(event);
  await refresh.update({ sub: user.id, family: startFamily(), gen: 0 });
  await access.update({ sub: user.id, roles: user.roles });
  return { sub: user.id, expiresAt: access.expiresAt };
});

app.get("/me", async (event) => {
  const user = await authenticate(event);
  if (!user) throw new HTTPError({ status: 401, message: "Not authenticated" });
  return user;
});

app.post("/logout", async (event) => {
  const access = await accessSession.use(event);
  const refresh = await refreshSession.use(event);
  await access.clear();
  await refresh.clear();
  return { ok: true };
});
```

Driven through `toWebHandler(app)` with a cookie jar and a moving clock:


## What to store

- **Server:** the two keys, and one row per family: `{ gen, rotatedAt }`. Give each row a time-to-live equal to the refresh `maxAge` (7 days). `onExpire` only receives the expired token's `jti` and times, not its data, so an expired family is cleaned up by the TTL rather than by a hook.
- **Client:** two `httpOnly` cookies. The browser holds them; your frontend code never touches a token.
- **Nothing per access token.** A revoked family stops refreshing at once, but an access token already issued stays valid until its `exp`.

## When it fails

Session reads do not throw on a bad token. They leave the session empty and report through [hooks](/adapters/hooks):

| Case                                                                       | Where it surfaces                                                                                                                      | What the code does                                     |
| -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| Access or refresh token past `exp`                                         | `onExpire`; cookie cleared with `Max-Age=0`                                                                                            | Falls through to the refresh, or to 401                |
| Edited, foreign or undecryptable token                                     | `onError` with `ERR_SESSION_TOKEN_INVALID`; `cause` is the underlying error, for a tampered refresh cookie `ERR_JWE_DECRYPTION_FAILED` | Treated as no session                                  |
| Replayed refresh token                                                     | `rotateFamily` returns `reused`                                                                                                        | Clears it; `onClear` revokes the family                |
| Key is a string, or not importable                                         | Thrown from `refreshSession.use()` / `accessSession.use()`: `ERR_SESSION_KEY_INVALID`                                                  | A deploy bug: let it reach your error handler as a 500 |
| `update()` or `clear()` after the response was sent (h3 v1, h3 v2 on Node) | Thrown: `ERR_SESSION_READONLY_EVENT`                                                                                                   | Move the call before the response                      |

For a string key the run printed `[unjwt/h3] Session "key" must be a JWK or a CryptoKey, not a password string. Derive one once with deriveJWKFromPassword() and pass the result.`

## Why these choices

- **Rotation with reuse detection.** A refresh token is a long-lived bearer credential. [RFC 9700 §4.14.2](https://www.rfc-editor.org/rfc/rfc9700#section-4.14.2) asks for rotation, so a stolen token is only good until either party uses it, and for revoking the family when an old one comes back, because one of the two holders is an attacker.
- **JWE for the refresh token.** Its contents are server bookkeeping. Encryption keeps `family` and `gen` from the client, and AES-GCM still authenticates them, so an edited cookie fails to decrypt.
- **Pinned algorithms.** `signOptions.alg` and `encryptOptions.alg`/`enc` set what the session issues and the only thing it accepts ([RFC 8725 §3.1](https://www.rfc-editor.org/rfc/rfc8725#section-3.1)).
- **`typ: "session+jwt"`.** The adapters stamp every session token with this type and refuse tokens without it ([RFC 8725 §3.11](https://www.rfc-editor.org/rfc/rfc8725#section-3.11)), so an API token signed with the same key never passes as a session.
- **`__Host-` cookie names.** The prefix requires `Secure`, `Path=/` and no `Domain`, so a sibling subdomain cannot plant a cookie that shadows the session ([RFC 6265bis §4.1.3.2](https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-rfc6265bis#section-4.1.3.2)). The adapter defaults already satisfy it.
- **Adapter-owned `exp`.** The lifetime comes from `maxAge`; a `jti`, `iat`, `exp` or `nbf` passed to `update()` is dropped, so request data can never extend a session.
