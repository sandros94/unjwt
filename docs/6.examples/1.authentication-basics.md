# Authenticate requests

> One service issues a token at login and checks it on every request that follows.

## The job

After a user proves who they are (password, passkey, magic link), the server hands the client an access token. The client sends it back in `Authorization: Bearer <token>` on every API call, and the server checks the token instead of looking up a session row.

Here the same service signs and verifies, so one shared secret is enough: HMAC with SHA-256 (`HS256`). If other services must verify your tokens without being able to mint them, use an asymmetric key and publish it instead, as in [Publish and consume a JWKS](/examples/jwks-endpoint).

## Create the key once

Generate the key with [`generateJWK()`](/jwk/generate), store the output in your secret manager as `JWT_SIGNING_KEY`, and load it at boot. A key generated at boot signs every user out on each deploy.

```ts [keys.ts]
import { generateJWK } from "unjwt/jwk";

const jwk = await generateJWK("HS256");
console.log(JSON.stringify(jwk));
// {"alg":"HS256","ext":true,"k":"ivVH54Z9ak2B…","key_ops":["sign","verify"],"kty":"oct","kid":"Bb2W02Nylc-Y…"}
```

The `k` member is 64 random bytes. The `kid` is the key's [RFC 7638](https://www.rfc-editor.org/rfc/rfc7638) thumbprint, which becomes useful when you rotate.

## Issue and verify

```ts [tokens.ts]
import { sign, verify } from "unjwt/jws";
import type { JWK_oct } from "unjwt/jwk";
import { isSymmetricJWK } from "unjwt/utils";

const ISSUER = "https://api.example.com";
const AUDIENCE = "https://api.example.com";
const TOKEN_TYPE = "at+jwt";

export type AccessClaims = {
  sub: string;
  roles: string[];
};

const signingKey = loadSigningKey();

export function issueAccessToken(userId: string, roles: string[]): Promise<string> {
  return sign({ sub: userId, roles, iss: ISSUER, aud: AUDIENCE }, signingKey, {
    expiresIn: "15m",
    protectedHeader: { typ: TOKEN_TYPE },
  });
}

export function verifyAccessToken(token: string) {
  return verify<AccessClaims>(token, signingKey, {
    algorithms: ["HS256"],
    typ: TOKEN_TYPE,
    issuer: ISSUER,
    audience: AUDIENCE,
    requiredClaims: ["sub", "exp"],
  });
}

function loadSigningKey(): JWK_oct<"HS256"> {
  const raw = process.env.JWT_SIGNING_KEY;
  if (!raw) throw new Error("JWT_SIGNING_KEY is not set");
  const jwk: unknown = JSON.parse(raw);
  if (!isSymmetricJWK(jwk) || jwk.alg !== "HS256") {
    throw new Error("JWT_SIGNING_KEY must be an HS256 oct JWK");
  }
  return { kty: "oct", alg: "HS256", k: jwk.k, kid: jwk.kid };
}
```

[`sign()`](/jwt/jws/sign) copies the key's `kid` into the header and adds `iat` and `exp`. Decoded, a token issued for `user_42` reads:

```ts
// header:  { kid: "Bb2W02Nylc-Y…", typ: "at+jwt", alg: "HS256" }
// payload: { sub: "user_42", roles: ["reader"], iss: "https://api.example.com",
//            aud: "https://api.example.com", iat: 1792068818, exp: 1792069718 }
```

The loader rebuilds the key from the members it expects, so the type is `JWK_oct<"HS256">` without a cast. The [guard](/utils/guards) refuses anything else at boot.

## Protect a route

```ts [http.ts]
import { isJWTError } from "unjwt/jws";
import { verifyAccessToken, type AccessClaims } from "./tokens";

export async function requireUser(request: Request): Promise<AccessClaims | Response> {
  const match = /^Bearer ([\w-]+\.[\w-]+\.[\w-]+)$/i.exec(
    request.headers.get("authorization") ?? "",
  );
  if (!match) return unauthorized();
  try {
    const { payload } = await verifyAccessToken(match[1]);
    return payload;
  } catch (error) {
    if (isJWTError(error, "ERR_JWT_EXPIRED")) return unauthorized("token expired");
    if (isJWTError(error)) return unauthorized("invalid token");
    throw error;
  }
}

export async function getProfile(request: Request): Promise<Response> {
  const user = await requireUser(request);
  if (user instanceof Response) return user;
  return Response.json({ userId: user.sub, roles: user.roles });
}

function unauthorized(description?: string): Response {
  const challenge = description
    ? `Bearer error="invalid_token", error_description="${description}"`
    : "Bearer";
  return new Response(null, { status: 401, headers: { "www-authenticate": challenge } });
}
```

```ts
await getProfile(new Request(url, { headers: { authorization: `Bearer ${token}` } }));
// 200 { userId: "user_42", roles: ["reader"] }
await getProfile(new Request(url));
// 401, www-authenticate: Bearer
```

## What to store

- **Server:** the JWK, in your secret store. Nothing per token: the token carries everything `verify` needs.
- **Client:** the token string, sent back on each request. Keep it in memory; a browser app that needs it across reloads is better served by an `httpOnly` cookie session, see [Rotate refresh tokens](/examples/refresh-token-pattern).
- **Revocation:** with nothing stored, a token stays valid until its `exp`. That is why the lifetime is 15 minutes. If you must cut a token off sooner, add a `jti` claim and keep a deny list of revoked `jti` values until their `exp` passes.

## When it fails

Every failure is a [`JWTError`](/errors). `requireUser` maps `ERR_JWT_EXPIRED` to its own description so the client knows to refresh, answers every other `JWTError` with a 401, and rethrows anything else as a server fault. The run produced:

| Case                                      | `code`                      | `message`                                                                                                |
| ----------------------------------------- | --------------------------- | -------------------------------------------------------------------------------------------------------- |
| `exp` passed                              | `ERR_JWT_EXPIRED`           | `JWT "exp" (Expiration Time) Claim validation failed: Token has expired (exp: 2026-10-15T12:48:38.000Z)` |
| Payload edited, or signed by another key  | `ERR_JWS_SIGNATURE_INVALID` | `JWS signature verification failed.`                                                                     |
| Signed with the same key as a plain `JWT` | `ERR_JWS_INVALID`           | `Invalid JWS: "typ" (Type) Header Parameter mismatch. Expected "at+jwt", got "JWT".`                     |
| `aud` names another API                   | `ERR_JWT_CLAIM_INVALID`     | `Invalid JWT "aud" (Audience) Claim: Expected https://api.example.com, got https://admin.example.com`    |
| No `exp`                                  | `ERR_JWT_CLAIM_MISSING`     | `Missing required JWT Claims: exp`                                                                       |
| Header says `alg: "none"`                 | `ERR_JWS_ALG_NOT_ALLOWED`   | `"none" is not a valid signing algorithm`                                                                |

On `ERR_JWT_EXPIRED`, `error.cause` carries the decoded `{ jti, iat, exp }`, which is enough to log which token expired. The response never echoes `error.message`; it names the [RFC 6750 §3.1](https://www.rfc-editor.org/rfc/rfc6750#section-3.1) error code and stays quiet otherwise. A request with no token gets a bare `Bearer` challenge, as the same section asks.

## Why these choices

- **`algorithms: ["HS256"]`.** The `alg` header is chosen by whoever wrote the token. Pinning it means a token can only be checked the way you issued it ([RFC 8725 §3.1](https://www.rfc-editor.org/rfc/rfc8725#section-3.1)). `none` is refused before the allow-list is read.
- **`typ: "at+jwt"`.** Explicit typing ([RFC 8725 §3.11](https://www.rfc-editor.org/rfc/rfc8725#section-3.11)) stops a token minted for another purpose with the same key, such as an email-verification link, from opening the API. `at+jwt` is the media type [RFC 9068 §2.1](https://www.rfc-editor.org/rfc/rfc9068#section-2.1) registers for access tokens. The comparison follows media-type rules, so a header of `application/AT+JWT` matches too.
- **`iss` and `aud`.** A verifier that checks both refuses a token issued by, or meant for, another service that shares the key ([RFC 8725 §3.8 and §3.9](https://www.rfc-editor.org/rfc/rfc8725#section-3.8)). Configuring `audience` also makes `aud` mandatory.
- **15-minute `exp`, required.** A bearer token works for whoever holds it, so its lifetime is the window a stolen copy stays useful ([RFC 6750 §5.3](https://www.rfc-editor.org/rfc/rfc6750#section-5.3)). `requiredClaims` refuses a token that would never expire.
- **A thumbprint `kid`.** To rotate, sign with the new key and verify against both until the old tokens have expired. The header `kid` picks the key. A set of `oct` keys is accepted only with `allowSymmetricJWKSet`, because a set is treated as public keys by default:

```ts
await verify(token, { keys: [current, previous] }, { algorithms: ["HS256"], typ: "at+jwt" });
// ERR_JWK_KEY_NOT_FOUND: No key found in JWK Set with kid "Xk7_vHtg35wF…".
await verify(
  token,
  { keys: [current, previous] },
  {
    algorithms: ["HS256"],
    typ: "at+jwt",
    allowSymmetricJWKSet: true,
  },
);
// verified with `previous`
```
