# JWT

> A JWT carries claims from one system to another, either signed so anyone can read it and no one can change it (JWS), or encrypted so only the key holder can read it (JWE).

::note
**ELI5.** A JWT is a note you hand to someone. A signed note (JWS) is written in plain ink with your seal at the bottom. Anyone can read it, and anyone who knows your seal can tell whether the note was changed after you sealed it. An encrypted note (JWE) is locked in a box. Only the holder of the right key can open it, and the box shows any attempt to tamper with it. Use the seal when the reader needs to trust the note. Use the box when the content itself must stay private.
::

## Which one do I want

| What you need                                                           | Use                                                                                   |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| The receiver must trust who issued the claims (sessions, access tokens) | [JWS](/jwt/jws)                                                                       |
| The client may read its own token (user id, role, expiry)               | [JWS](/jwt/jws)                                                                       |
| Other services check tokens with a public key you publish               | [JWS](/jwt/jws) with an asymmetric key and a [JWKS endpoint](/examples/jwks-endpoint) |
| The payload holds personal data or secrets the client must not read     | [JWE](/jwt/jwe)                                                                       |
| Private content that is also provably yours                             | Sign, then encrypt the signed token (a nested JWT, shown below)                       |

A JWE made with a shared key (`dir`, `A256KW`, a password) also proves the sender held that key, because decryption checks an authentication tag. A JWE made with a public key (`RSA-OAEP-256`, `ECDH-ES+A256KW`) proves nothing about the sender, since anyone with the public key can encrypt. Sign first whenever the sender matters.

## Compact and JSON forms

Every token takes one of two shapes.

The **compact** form is one URL-safe string of base64url segments joined by dots. It fits in a cookie, an `Authorization` header or a query string. A compact JWS has three segments and a compact JWE has five:

```
JWS  <header>.<payload>.<signature>
JWE  <header>.<encrypted key>.<iv>.<ciphertext>.<tag>
```

The **JSON** forms are objects. The General form carries several signatures over one payload, or one ciphertext readable by several recipients. The Flattened form is the same object with exactly one signer or recipient. The compact form always has exactly one.

| Shape                     | JWS                                                            | JWE                                                          |
| ------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------ |
| Compact string            | [`sign`](/jwt/jws/sign), [`verify`](/jwt/jws/verify)           | [`encrypt`](/jwt/jwe/encrypt), [`decrypt`](/jwt/jwe/decrypt) |
| General or Flattened JSON | [`signMulti`, `verifyMulti`, `verifyMultiAll`](/jwt/jws/multi) | [`encryptMulti`, `decryptMulti`](/jwt/jwe/multi)             |

Import from `unjwt/jws` and `unjwt/jwe`, or every function flat from `unjwt`.

## How they fit together

One shared key signs, another wraps an encryption key. The JWS payload is readable by anyone who decodes the middle segment. The JWE payload is not.

```ts
import { sign, verify } from "unjwt/jws";
import { encrypt, decrypt } from "unjwt/jwe";
import { generateJWK } from "unjwt/jwk";
import { base64UrlParse } from "unjwt/utils";

// Signed: readable by anyone, changeable by no one
const signingKey = await generateJWK("HS256");
const jws = await sign({ sub: "user_1", role: "admin" }, signingKey, { expiresIn: "15m" });
jws.split(".").length; // 3

const [, payloadSegment] = jws.split(".");
base64UrlParse(payloadSegment);
// '{"sub":"user_1","role":"admin","iat":1792068456,"exp":1792069356}'

const { payload: claims } = await verify(jws, signingKey);
// { sub: "user_1", role: "admin", iat: 1792068456, exp: 1792069356 }

// Encrypted: readable only with the key
const encryptionKey = await generateJWK("A256KW");
const jwe = await encrypt({ sub: "user_1", email: "ada@example.com" }, encryptionKey);
jwe.split(".").length; // 5

const { payload: secret, protectedHeader } = await decrypt(jwe, encryptionKey);
// secret:          { sub: "user_1", email: "ada@example.com" }
// protectedHeader: { kid: "5mfJTJ8C…", alg: "A256KW", enc: "A256GCM", typ: "JWT" }
```

The algorithm came from each key's `alg`, and the `kid` from the key's thumbprint set by [`generateJWK`](/jwk/generate). `verify` checked `exp` on its own because the payload is a JSON object.

### Sign, then encrypt

A nested JWT signs the claims, then encrypts the signed token as the JWE payload. Set `cty: "JWT"` on the outer header so the receiver knows the plaintext is itself a token ([RFC 7519 §5.2](https://www.rfc-editor.org/rfc/rfc7519#section-5.2)).

```ts
import { sign, verify } from "unjwt/jws";
import { encrypt, decrypt } from "unjwt/jwe";
import { generateJWK } from "unjwt/jwk";

const issuerKeys = await generateJWK("ES256");
const recipientKeys = await generateJWK("ECDH-ES+A256KW");

const inner = await sign({ sub: "user_1", plan: "pro" }, issuerKeys.privateKey, {
  expiresIn: "1h",
});
const outer = await encrypt(inner, recipientKeys.publicKey, { protectedHeader: { cty: "JWT" } });

const opened = await decrypt(outer, recipientKeys.privateKey, { payload: "string" });
opened.protectedHeader.cty; // "JWT"

const { payload } = await verify(opened.payload, issuerKeys.publicKey);
// { sub: "user_1", plan: "pro", iat: 1792068462, exp: 1792072062 }
```

The outer header carries no `typ`, because the JWE payload is a string. `decrypt` needs `payload: "string"` here, since its default expects a JSON object.

## Shared options

The producers (`sign`, `encrypt`, `signMulti`, `encryptMulti`) share the time options. Each one only applies to an object payload, and a claim already in the payload is kept as given.

| Option        | Type       | What it does                                                       |
| ------------- | ---------- | ------------------------------------------------------------------ |
| `expiresIn`   | `Duration` | Sets `exp` to `iat` plus the duration. Exclusive with `expiresAt`. |
| `expiresAt`   | `Date`     | Sets `exp` to that instant.                                        |
| `notBeforeIn` | `Duration` | Sets `nbf` to `iat` plus the duration (`0` means `nbf = iat`).     |
| `notBeforeAt` | `Date`     | Sets `nbf` to that instant.                                        |
| `currentDate` | `Date`     | The moment used for `iat`. Defaults to now.                        |

A `Duration` is a number of seconds or a string such as `"30s"`, `"10m"`, `"2h"`, `"7D"`, `"1W"`, `"3M"`, `"1Y"`, with long forms like `"7days"` also accepted. `iat` is added whenever one of these options sets a claim.

The consumers (`verify`, `decrypt` and their multi variants) share the `payload` mode, claim validation, the `typ` check, `crit` handling and the JWK Set rules. [`verify()`](/jwt/jws/verify) documents them in full and [`decrypt()`](/jwt/jwe/decrypt) lists what differs.

Every failure is a [`JWTError`](/errors) with a `code`. Branch on it with `isJWTError(error, "ERR_JWT_EXPIRED")`.
