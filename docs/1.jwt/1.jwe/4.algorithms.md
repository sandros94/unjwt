# JWE algorithms

> The key management algorithms (`alg`) and content encryption algorithms (`enc`) that `encrypt` and `decrypt` accept, with their keys, defaults, limits and inference rules.

```ts
import { encrypt, decrypt } from "unjwt/jwe";
import { generateJWK } from "unjwt/jwk";

const { publicKey, privateKey } = await generateJWK("ECDH-ES+A256KW");
const token = await encrypt({ sub: "user_1" }, publicKey); // alg from the key, enc defaults to A256GCM
await decrypt(token, privateKey);
```

## Key management (`alg`)

| `alg` | Key | What happens to the content key | Encrypted key segment |
| --- | --- | --- | --- |
| `dir` | the content key itself, `kty: "oct"` | none; your key is the content key | empty |
| `A128KW`, `A192KW`, `A256KW` | AES key of 16, 24 or 32 bytes | wrapped with AES Key Wrap | content key plus 8 bytes |
| `A128GCMKW`, `A192GCMKW`, `A256GCMKW` | AES key of 16, 24 or 32 bytes | encrypted with AES-GCM; header gets `iv` and `tag` | content key length |
| `RSA-OAEP`, `RSA-OAEP-256`, `RSA-OAEP-384`, `RSA-OAEP-512` | RSA key pair, 2048-bit modulus or more | encrypted with RSA-OAEP (SHA-1, SHA-256, SHA-384, SHA-512) | modulus length |
| `ECDH-ES` | EC (`P-256`, `P-384`, `P-521`) or `X25519` key pair | derived by key agreement with a fresh ephemeral key (`epk`) | empty |
| `ECDH-ES+A128KW`, `ECDH-ES+A192KW`, `ECDH-ES+A256KW` | same as `ECDH-ES` | random, wrapped with AES Key Wrap under the agreed key | content key plus 8 bytes |
| `PBES2-HS256+A128KW`, `PBES2-HS384+A192KW`, `PBES2-HS512+A256KW` | a password string | random, wrapped with AES Key Wrap under a PBKDF2-derived key | content key plus 8 bytes |

`RSA-OAEP` (SHA-1 inside OAEP) stays for systems that only speak it. Pick `RSA-OAEP-256` for new keys.

`dir` and bare `ECDH-ES` produce one content key per recipient, so [`encryptMulti`](/jwt/jwe/multi) refuses both.

### PBES2

| Parameter | Default on `encrypt` | Accepted on `encrypt` | Accepted on `decrypt` |
| --- | --- | --- | --- |
| `p2c` (count) | `600_000` | 1000 to 600,000 | `minIterations` (1000) to `maxIterations` (600,000) |
| `p2s` (salt) | 16 random bytes | 8 bytes or more | 8 bytes or more |

The floors come from [RFC 7518 §4.8.1](https://www.rfc-editor.org/rfc/rfc7518#section-4.8.1). The ceiling stops a token from asking your server for unbounded PBKDF2 work, and `decrypt`'s `limits.pbes2Iterations` (2,400,000) caps the total per call. The salt sent in `p2s` is prefixed with the `alg` name before derivation, as the RFC requires.

### ECDH-ES

The sender makes a fresh ephemeral key pair on the recipient's curve and puts its public half in the header as `epk`. Both sides derive the same key from their own private key and the other's public key, through the Concat KDF of [RFC 7518 §4.6](https://www.rfc-editor.org/rfc/rfc7518#section-4.6).

- `apu` and `apv` (`ecdh.partyUInfo` and `ecdh.partyVInfo` on `encrypt`) feed the KDF. Each is at most 1024 bytes on both sides. An empty one is left out of the header.
- The `epk` is wire data. `decrypt` takes only `kty`, `crv` and the coordinates from it, refuses one carrying `d`, and requires the recipient's curve.
- `X25519` is supported. `X448` is not: `generateJWK` refuses it with `ERR_JWK_UNSUPPORTED`.

## Content encryption (`enc`)

| `enc`           | Content key | IV       | Tag      | Construction                  |
| --------------- | ----------- | -------- | -------- | ----------------------------- |
| `A128GCM`       | 16 bytes    | 12 bytes | 16 bytes | AES-GCM                       |
| `A192GCM`       | 24 bytes    | 12 bytes | 16 bytes | AES-GCM                       |
| `A256GCM`       | 32 bytes    | 12 bytes | 16 bytes | AES-GCM, the default          |
| `A128CBC-HS256` | 32 bytes    | 16 bytes | 16 bytes | AES-128-CBC with HMAC-SHA-256 |
| `A192CBC-HS384` | 48 bytes    | 16 bytes | 24 bytes | AES-192-CBC with HMAC-SHA-384 |
| `A256CBC-HS512` | 64 bytes    | 16 bytes | 32 bytes | AES-256-CBC with HMAC-SHA-512 |

`decrypt` checks the IV and tag lengths before decrypting, so a tag cannot be shortened or the ciphertext re-split. The 192-bit variants need a runtime whose Web Crypto supports 192-bit AES keys; Chromium-based browsers do not.

```ts
const cek = await generateJWK("A128CBC-HS256"); // 32 random bytes as an oct JWK
const token = await encrypt({ a: 1 }, cek);
// header: { kid: "vmKfa6-u…", alg: "dir", enc: "A128CBC-HS256", typ: "JWT" }   IV 16 bytes, tag 16 bytes
```

## Inference

`encrypt` picks `alg` and `enc` when you omit them:

| Key | `alg` | `enc` |
| --- | --- | --- |
| A password string | `PBES2-HS256+A128KW` | `A256GCM` |
| A JWK with a key management `alg` | that `alg` | the JWK's `enc`, else `A256GCM` |
| An `oct` JWK whose `alg` is an `enc` value | `dir` | that `enc` |
| A `CryptoKey` or raw bytes | none, pass `alg` | `A256GCM` (`dir` needs `enc`) |

`decrypt` builds its allow-list when you pass no `algorithms`:

| Key | Accepted `alg` |
| --- | --- |
| A password string | the three `PBES2-*` algorithms |
| A JWK with a key management `alg` | that `alg` only |
| An `oct` JWK whose `alg` is an `enc` value | `dir` |
| An EC JWK without `alg`, or an `X25519` one | all four `ECDH-ES*` |
| An `AES-KW` `CryptoKey` of N bits | `AnKW` and `dir` |
| An `AES-GCM` `CryptoKey` of N bits | `AnGCMKW` and `dir` |
| An `RSA-OAEP` `CryptoKey` | the `RSA-OAEP*` variant matching its hash |
| An `ECDH` or `X25519` `CryptoKey` | all four `ECDH-ES*` |
| Raw bytes | nothing; pass `algorithms` |
| A JWK Set | the union over its entries (`oct` skipped unless `allowSymmetricJWKSet`) |

`encryptionAlgorithms` is never inferred: without it, any `enc` in the table above is accepted. The same inference is exported as [`inferJWEAllowedAlgorithms`](/utils) from `unjwt/utils`.

### Key roles

An `oct` JWK's `alg` names one job, and the jobs do not mix:

- `A*KW` and `A*GCMKW` keys wrap content keys only.
- A key declared as an `enc` value is a content key for `dir`, and only for a token with that same `enc`.
- A key declared as `dir` serves any `enc` whose key length matches.

```ts
const gcmCek = await generateJWK("A256GCM");
await encrypt({ a: 1 }, gcmCek, { enc: "A128GCM" });
// JWTError ERR_JWK_INVALID: JWK "alg" is "A256GCM" but "dir" requires "dir" or the token's "enc".
await encrypt({ a: 1 }, gcmCek, { alg: "A256GCMKW" });
// JWTError ERR_JWK_INVALID: JWK "alg" is "A256GCM" but the operation requires "A256GCMKW".
```

## Not supported

- **`none`** as `alg`: `ERR_JWE_ALG_NOT_ALLOWED` (`"none" is not a valid key management algorithm`).
- **`RSA1_5`** (RSA PKCS#1 v1.5 encryption), which is open to padding-oracle attacks: `ERR_JWE_ALG_NOT_ALLOWED` (`Key management algorithm not supported: "RSA1_5"`).
- **Any other `enc`**: `ERR_JWE_INVALID` (`Invalid JWE: unsupported "enc" "A256CTR"`).
- **`zip`** compression: refused on both sides.
- **`X448`** for ECDH-ES.
- **Generating** a PBES2 or `dir` key with `generateJWK`: `ERR_JWK_UNSUPPORTED`. Pass a password string for PBES2, and generate an `enc` key (`generateJWK("A256GCM")`) for `dir`.
