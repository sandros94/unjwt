# JWS algorithms

> The fourteen signing algorithms `sign` and `verify` accept, the key each one needs, the size floors they enforce, and how `alg` is read from a key.

```ts
import { sign, verify } from "unjwt/jws";
import { generateJWK } from "unjwt/jwk";

const { privateKey, publicKey } = await generateJWK("Ed25519");
const token = await sign({ sub: "user_1" }, privateKey); // alg comes from the key
await verify(token, publicKey); // and so does the allow-list
```

## The table

| `alg`                     | Family          | Key                            | Size floor                         | Web Crypto algorithm |
| ------------------------- | --------------- | ------------------------------ | ---------------------------------- | -------------------- |
| `HS256`, `HS384`, `HS512` | HMAC            | shared secret, `kty: "oct"`    | 32, 48 or 64 bytes (the hash size) | `HMAC`               |
| `RS256`, `RS384`, `RS512` | RSA PKCS#1 v1.5 | RSA key pair, `kty: "RSA"`     | 2048-bit modulus                   | `RSASSA-PKCS1-v1_5`  |
| `PS256`, `PS384`, `PS512` | RSA-PSS         | RSA key pair, `kty: "RSA"`     | 2048-bit modulus                   | `RSA-PSS`            |
| `ES256`                   | ECDSA           | EC key pair, `crv: "P-256"`    | fixed by the curve                 | `ECDSA` with `P-256` |
| `ES384`                   | ECDSA           | EC key pair, `crv: "P-384"`    | fixed by the curve                 | `ECDSA` with `P-384` |
| `ES512`                   | ECDSA           | EC key pair, `crv: "P-521"`    | fixed by the curve                 | `ECDSA` with `P-521` |
| `EdDSA`, `Ed25519`        | EdDSA           | OKP key pair, `crv: "Ed25519"` | fixed by the curve                 | `Ed25519`            |

The number in an identifier is the hash size. `ES512` uses the curve `P-521`, which is not a typo. `EdDSA` ([RFC 8037](https://www.rfc-editor.org/rfc/rfc8037)) and `Ed25519` name the same signature over the same key. `EdDSA` is the spelling most other libraries emit.

`generateJWK` makes an HMAC key of the hash's block size (64 bytes for `HS256`, 128 for `HS384` and `HS512`) and RSA keys of 2048 bits unless you pass `modulusLength`.

## Size floors

The floors hold for every key input, at signing and at verification.

- **HMAC.** A secret shorter than the hash output is refused, as [RFC 7518 §3.2](https://www.rfc-editor.org/rfc/rfc7518#section-3.2) requires. This applies to raw bytes and to the `k` of an `oct` JWK.
- **RSA.** A modulus under 2048 bits is refused ([RFC 7518 §3.3](https://www.rfc-editor.org/rfc/rfc7518#section-3.3)). `generateJWK` refuses to make one.

```ts
await sign({ a: 1 }, new Uint8Array(32), { alg: "HS512" });
// JWTError ERR_JWK_INVALID: HS512 requires a key of at least 64 bytes (got 32)

await sign({ a: 1 }, rsa1024.privateKey, { alg: "RS256" });
// JWTError ERR_JWK_INVALID: RS256 requires a key modulusLength of at least 2048 bits

await generateJWK("RS256", { modulusLength: 1024 });
// JWTError ERR_INVALID_OPTION: modulusLength must be at least 2048 bits (RFC 7518 §3.3)
```

## How `alg` is read from a key

`sign` takes `alg` from the options, else from the JWK's `alg`. A `CryptoKey` or raw bytes need `alg` in the options, and `signMulti` also reads it from a `CryptoKey`'s algorithm.

`verify` builds its allow-list when you pass no `algorithms`:

| Key                                        | Accepted `alg`                                                           |
| ------------------------------------------ | ------------------------------------------------------------------------ |
| A JWK with `alg`                           | that `alg` only                                                          |
| An EC JWK without `alg`                    | from `crv`: `ES256`, `ES384` or `ES512`                                  |
| An OKP JWK without `alg`, `crv: "Ed25519"` | `EdDSA` and `Ed25519`                                                    |
| An RSA or `oct` JWK without `alg`          | nothing; pass `algorithms`                                               |
| An `HMAC` `CryptoKey`                      | `HS*` from its hash                                                      |
| An RSA `CryptoKey`                         | `RS*` or `PS*` from its algorithm and hash                               |
| An `ECDSA` or `Ed25519` `CryptoKey`        | from its curve, as for JWKs                                              |
| Raw bytes                                  | nothing; pass `algorithms`                                               |
| A JWK Set                                  | the union over its entries (`oct` skipped unless `allowSymmetricJWKSet`) |

`EdDSA` and `Ed25519` are two names for one signature, so a key generated under either name signs and verifies under both. The header carries the name you asked for, and an explicit `algorithms` list is still exact:

```ts
const key = await generateJWK("Ed25519");
const token = await sign({ a: 1 }, key.privateKey, { alg: "EdDSA" }); // header alg: "EdDSA"

await verify(token, key.publicKey); // ok
await verify(token, key.publicKey, { algorithms: ["EdDSA"] }); // ok
await verify(token, key.publicKey, { algorithms: ["Ed25519"] });
// JWTError ERR_JWS_ALG_NOT_ALLOWED: Algorithm not allowed: EdDSA
```

Every other `alg` is binding: a key declaring one algorithm is refused for another, at signing too:

```ts
const p384 = await generateJWK("ES384");
await sign({ a: 1 }, p384.privateKey, { alg: "ES256" });
// JWTError ERR_JWK_INVALID: JWK "alg" is "ES384" but the operation requires "ES256".
```

The same inference is exported as [`inferJWSAllowedAlgorithms`](/utils) from `unjwt/utils`.

## Not supported

- **`none`.** Refused by `sign` and `verify` as `ERR_JWS_ALG_NOT_ALLOWED` (`"none" is not a valid signing algorithm`), before any key is read ([RFC 8725 §3.1](https://www.rfc-editor.org/rfc/rfc8725#section-3.1)).
- **`Ed448`.** No key on that curve can be generated (`ERR_JWK_UNSUPPORTED`) or imported (`ERR_JWK_INVALID`).
- **`ES256K`** (secp256k1) and any other name outside the table. `sign` and `verify` refuse it with `ERR_JWS_ALG_NOT_ALLOWED` (`Algorithm not supported: "ES256K"`).

## Choosing

- **One service signs and checks its own tokens.** `HS256` with a generated key. Fast, one secret to guard.
- **Others verify with a public key.** `EdDSA` or `ES256`. Small keys and signatures, no parameters to get wrong.
- **RSA is required by a partner or a regulation.** `PS256`. Use `RS256` only when the other side requires PKCS#1 v1.5.
- **Several algorithms at once,** such as during a migration. Sign with each in [`signMulti`](/jwt/jws/multi).

Publish public keys through a [JWKS endpoint](/examples/jwks-endpoint) so verifiers pick them up by `kid`.
