# JWS

> A JSON Web Signature keeps the payload readable and makes any change to it detectable, so a receiver can trust who issued it.

::note **ELI5.** Signing is a tamper seal. You write the claims in the open, then run them through a key to produce a short code that only that key could have made from those exact bytes. The receiver runs the same check. If one character of the token changed, or the code came from another key, the check fails. Nothing is hidden: anyone holding the token can decode and read the claims. A shared secret key (HMAC) lets the same party sign and check. A key pair lets one party sign with the private half while anyone checks with the public half. ::

::card-group ::card{title="sign()" icon="i-lucide-pen-line" to="/jwt/jws/sign"} Turn a payload and a key into a compact token. :: ::card{title="verify()" icon="i-lucide-badge-check" to="/jwt/jws/verify"} Check the signature, the header and the claims, and get the payload back. :: ::card{title="Multi-signature" icon="i-lucide-users" to="/jwt/jws/multi"} `signMulti()`, `verifyMulti()`, `verifyMultiAll()` for the General and Flattened JSON forms. :: ::card{title="Algorithms" icon="i-lucide-list" to="/jwt/jws/algorithms"} `HS*`, `RS*`, `PS*`, `ES*` and `EdDSA`, with key sizes and inference rules. :: ::

## Which function do I want

| The question you are answering                            | The function                                 |
| --------------------------------------------------------- | -------------------------------------------- |
| How do I issue a token for a session or an API call?      | [`sign`](/jwt/jws/sign)                      |
| Is this incoming token genuine, current and meant for me? | [`verify`](/jwt/jws/verify)                  |
| Which key from a published JWK Set signed this token?     | [`verify`](/jwt/jws/verify) with the JWK Set |
| Do several parties need to sign one document?             | [`signMulti`](/jwt/jws/multi)                |
| Is one valid signature among several enough?              | [`verifyMulti`](/jwt/jws/multi)              |
| Must every signer, or a quorum of them, be checked?       | [`verifyMultiAll`](/jwt/jws/multi)           |
| Which algorithm and key size should I pick?               | [Algorithms](/jwt/jws/algorithms)            |

## How they fit together

A key pair from [`generateJWK`](/jwk/generate) carries its `alg` and `kid`. `sign` reads both from the private key. `verify` reads the allowed algorithm from the public key and checks `exp` because the payload is a JSON object.

```ts
import { sign, verify, signMulti, verifyMulti } from "unjwt/jws";
import { generateJWK } from "unjwt/jwk";

const { privateKey, publicKey } = await generateJWK("ES256");

const token = await sign(
  { sub: "user_1", iss: "https://auth.example.com", aud: "api" },
  privateKey,
  {
    expiresIn: "1h",
  },
);

const result = await verify(token, publicKey, {
  issuer: "https://auth.example.com",
  audience: "api",
});
// {
//   payload: { sub: "user_1", iss: "https://auth.example.com", aud: "api", iat: 1792068732, exp: 1792072332 },
//   protectedHeader: { kid: "kQZFJTTl…", alg: "ES256", typ: "JWT" },
// }

// Two signers on one payload, as a General JSON object
const alice = await generateJWK("ES256", { kid: "alice" });
const notary = await generateJWK("Ed25519", { kid: "notary" });

const jws = await signMulti({ doc: "contract-42" }, [
  { key: alice.privateKey },
  { key: notary.privateKey },
]);
const { signerIndex } = await verifyMulti(jws, notary.publicKey); // 1
```

## What a signature does not do

- **It does not hide the payload.** The middle segment is base64url text. Put nothing there you would not show the token holder. Encrypt with [JWE](/jwt/jwe) when the content is private.
- **It does not stop replay.** A stolen token stays valid until `exp`. Keep lifetimes short and pair long sessions with a [refresh token](/examples/refresh-token-pattern).
- **It does not check `aud` unless asked.** `verify` checks the audience only when you pass `audience`. Set it on every verifier that serves one audience ([RFC 8725 §3.9](https://www.rfc-editor.org/rfc/rfc8725#section-3.9)).

## What the library refuses

- `alg: "none"`, on both sides, before any key work.
- A string as a signing or verifying key. Pass an `oct` JWK or a `Uint8Array` secret, or import PEM text with [`importPEM`](/jwk/pem).
- An HMAC secret shorter than its hash (32 bytes for `HS256`) and an RSA key under 2048 bits.
- A private JWK passed to `verify`, and a public JWK passed to `sign`.
- A header `alg` the key was not made for. A JWK that declares `alg` serves that algorithm only.

Each refusal is a [`JWTError`](/errors) with a stable `code`, listed on the function pages.
