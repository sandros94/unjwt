# Sessions on Elysia

> Put a signed session on every Elysia request with the `jwsSession` plugin, and let the `requireSession` guard answer 401 for the routes that need a user.

The plugin opens the session before your handler runs and puts it on the context as `session`, so routes read `session.data` the way they read `body`. It also adds a guard, `requireSession`, that a route opts into. The session is a JWS, a token with a signature across it: the server can tell whether it wrote the cookie, and the user can read what's inside. [Concepts](/getting-started/concepts) has the vocabulary.

## Before you start

- Install both packages:

  ```sh
  bun add elysia unjwt
  ```

- A session key that survives restarts. Generate it once, in your project folder:

  ```sh
  bun -e 'import { generateJWK } from "unjwt/jwk"; console.log(JSON.stringify(await generateJWK("HS256")))'
  ```

  It prints one line of JSON, `{"alg":"HS256","kty":"oct","k":"…","kid":"…"}`. Store that whole line as `SESSION_KEY` in your secret manager, or in a `.env` file you never commit; Bun reads `.env` by itself. Whoever holds it can sign a session for any user. Replacing it signs everyone out.

- HTTPS, or `localhost` while you develop. The cookie is called `__Host-elysia-jws` and carries `Secure`, so a browser drops it on plain HTTP anywhere else.

## Sign users in and out

<!-- automd:region src="../../examples/recipes/elysia.ts" -->

```ts [elysia.ts]
import { Elysia, t } from "elysia";
import { jwsSession } from "unjwt/adapters/elysia";

const SESSION_KEY = process.env.SESSION_KEY;
if (!SESSION_KEY) throw new Error("SESSION_KEY is not set");

const app = new Elysia()
  .use(
    jwsSession<{ user: string }, "1h">({
      key: JSON.parse(SESSION_KEY),
      maxAge: "1h",
      rolling: "15m",
    }),
  )
  .post(
    "/login",
    async ({ session, body }) => {
      await session.update({ user: body.user });
      return { user: session.data.user };
    },
    { body: t.Object({ user: t.String() }) },
  )
  .get("/me", ({ session }) => session.data, { requireSession: true })
  .post("/logout", async ({ session }) => {
    await session.clear();
    return { ok: true };
  });
```

<!-- /automd -->

Start it with `app.listen(3000)` on Bun, or hand `app.handle` to any runtime that takes a fetch handler. What each part does:

- **Start-up check**: without `SESSION_KEY` the module throws before the server listens, so a forgotten variable stops the deploy instead of the first sign-in.
- **The plugin**: `jwsSession()` reads the cookie on every request and gives each handler `session`. Reading sets no cookie; `update()` and `clear()` do, on the response Elysia builds.
- **Body schema**: `t.Object({ user: t.String() })` lets Elysia refuse a login without a user before the handler runs, and types `body.user` as a string.
- **No session yet**: `session.id` stays `undefined` until `update()` signs a first token. `{ requireSession: true }` on `/me` answers 401 in that case, before the handler runs.
- **Lifetime**: `maxAge: "1h"` ends a token an hour after it was signed. `rolling: "15m"` signs a fresh hour on the first request that finds the token at least 15 minutes old, so an active user stays in.
- **Readable data**: the cookie is `HttpOnly`, so page scripts can't read it, but the user can decode it. Keep secrets out of `update()`, or use `jweSession` (see Going further).

## Guard a group of routes

The plugin names its guard after the context key: `session` gives `requireSession`. Pass it to `guard()` and every route inside needs a session:

<!-- automd:region src="../../examples/recipes/elysia.ts" name="guard" -->

```ts [elysia.ts]
app.guard({ requireSession: true }, (account) =>
  account
    .get("/account/profile", ({ session }) => ({
      user: session.data.user,
      expiresAt: session.expiresAt,
    }))
    .post(
      "/account/rename",
      async ({ session, body }) => {
        await session.update({ user: body.user });
        return { user: session.data.user };
      },
      { body: t.Object({ user: t.String() }) },
    ),
);
```

<!-- /automd -->

- **A status, not a throw**: the guard returns Elysia's `status(401)`, so typed clients and OpenAPI see the 401 as a response of the route.
- **Updates in place**: `update()` merges into the session and signs a new token, so a renamed user gets a fresh cookie on the same response.
- **More than one session**: give each plugin its own `contextKey` and `name`, and the guards follow the keys (`requireAccess`, `requireRefresh`). See [Elysia plugin](/sessions/elysia).

## When it fails

| Situation                                            | What happens                                                                                                                                                |
| ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `SESSION_KEY` unset or empty                         | The module throws `SESSION_KEY is not set` at start-up.                                                                                                     |
| `SESSION_KEY` is not JSON                            | `JSON.parse` throws a `SyntaxError` at start-up. Store the line `generateJWK` printed, quotes included.                                                     |
| JSON that is not a signing key, such as a public JWK | `jwsSession` throws `ERR_SESSION_KEY_INVALID` at start-up, and the app doesn't start. See [Handle errors](/safety/errors).                                  |
| An `HS256` JWK whose `k` doesn't decode              | Every request answers 500, because the plugin opens the session first: it throws `ERR_SESSION_KEY_INVALID`.                                                 |
| Plain HTTP on a host other than `localhost`          | `/login` answers 200 with the cookie, the browser refuses a `Secure` cookie over HTTP, and `/me` stays 401. Serve over HTTPS.                               |
| Request without the cookie                           | `requireSession` answers 401 on `/me` and every route in the guard.                                                                                         |
| Token older than `maxAge`                            | The session opens empty, the guard answers 401, and the response drops the cookie. The [`onExpire` hook](/sessions/hooks) fires.                            |
| Cookie signed with another key, or changed by hand   | Same 401 and cookie drop. The `onError` hook gets `ERR_SESSION_TOKEN_INVALID`; nothing is thrown.                                                           |
| `/login` without a `user` string                     | Elysia answers 422 from the body schema, and no cookie is set.                                                                                              |
| `update()` in `onAfterResponse`                      | It resolves, but the response has already left, so the cookie never reaches the client. Update the session in the handler, `beforeHandle` or `afterHandle`. |

## Going further

- **Hide the data**: `jweSession` encrypts the token, so the user can't read it either. It takes an `oct` key such as `generateJWK("A256GCM")`; see [Configure a session](/sessions/configure).
- **API clients**: set `sessionHeader` to read a bearer token from a header before the cookie. See [Configure a session](/sessions/configure).
- **Your own resolve**: `defineJWSSession` from the same entry gives `use({ cookie, request })` for a `derive` or a guard you write yourself, plus `issue()` and `open()` for tokens outside a request. See [Elysia plugin](/sessions/elysia).
- **Revocation and audit**: hooks run when a session is read, updated, cleared or expires; on Elysia they receive `context` instead of `event`. See [Hooks](/sessions/hooks).
