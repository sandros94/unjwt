# Introduction

> unjwt is a low-level JWT toolkit on the Web Crypto API: signed and encrypted tokens, keys, and cookie sessions, with one typed error.

`unjwt` creates and reads JSON Web Tokens. It signs them ([JWS](/jwt/jws)), encrypts them ([JWE](/jwt/jwe)), manages the keys behind both ([JWK](/jwk)), and keeps a user's session in a cookie on [Web standards, H3 and Elysia](/frameworks).

Everything runs on the [Web Crypto API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Crypto_API). There are no runtime dependencies and no Node built-ins, so the same code runs in Node, Bun, Deno, Cloudflare Workers and browsers.

::note **ELI5.** A JWT is a short string that carries a few facts, such as "this is user 42, and this expires at noon". Your server writes it and hands it to a client. When the client sends it back, the server needs to know two things: that nobody changed the facts, and sometimes that nobody else could read them. A signature answers the first question and encryption answers the second. Both need a key, and the server must refuse anything it did not expect. unjwt does those checks for you and tells you, with a specific error code, which one failed. ::

## Rules that run through everything

**Every error is a `JWTError` with a `code`.** Signing, verifying, encrypting, decrypting, key handling and sessions all throw [`JWTError`](/errors). Branch on `error.code`, or narrow with `isJWTError(error, "ERR_JWT_EXPIRED")`. The base64 codecs in `unjwt/utils` throw the bundled `UnsecureError` instead, which `unjwt/utils` also exports.

**Algorithms come from the key unless you say otherwise.** A JWK that carries `alg` decides which algorithm `sign` and `encrypt` use, and which one `verify` and `decrypt` accept. Raw bytes, a `CryptoKey` or a JWK without `alg` needs an explicit `alg` to sign or encrypt. To verify or decrypt, unjwt infers the allowed algorithms from the key's shape where it can, and asks for `algorithms` where it cannot, as with raw bytes. A string is accepted only as a PBES2 password for JWE, never as a signing secret.

**Verification is strict by default.** `verify` and `decrypt` refuse `alg: "none"`, any algorithm outside the allowed list, a `crit` header they do not understand, padded or non-canonical base64url, and an expired or not-yet-valid token. Pass `typ` and the token must carry that `typ` in its protected header.

**The payload mode decides the return type.** `payload: "json"` is the default and returns a validated claims object. `payload: "string"` returns the text and `payload: "bytes"` returns a `Uint8Array`. The token never chooses for you, and a typed call such as `verify<MyClaims>(…)` names the claims shape.

## What it looks like

```ts
import { sign, verify } from "unjwt/jws";
import { generateJWK } from "unjwt/jwk";

const key = await generateJWK("HS256");
// { alg: "HS256", kty: "oct", k: "aV1kaiMK…", kid: "gOyc7uMK…" }

const token = await sign({ sub: "user_1", role: "admin" }, key, { expiresIn: "1h" });
// "eyJraWQiOiJnT3ljN3VNS2tQNTFTRDgy…"

const { payload, protectedHeader } = await verify(token, key);
// payload:         { sub: "user_1", role: "admin", iat: 1792068434, exp: 1792072034 }
// protectedHeader: { kid: "gOyc7uMK…", alg: "HS256", typ: "JWT" }
```

The key names its own algorithm, so neither call repeats it. The `kid` is the key's [RFC 7638](https://www.rfc-editor.org/rfc/rfc7638) thumbprint, and `sign` copies it into the header so a verifier holding many keys can find this one.
