# Installation

> Install unjwt with any package manager, choose between the barrel and the subpaths, and add a peer dependency only for the adapter you use.

`unjwt` is published to npm as [`unjwt`](https://npmx.dev/package/unjwt).

## Install

<!-- automd:pm-i -->
<!-- /automd -->

Or let [`nypm`](https://github.com/unjs/nypm) detect the package manager for you:

```sh
npx nypm install unjwt
```

## Agent skill

An [Agent Skill](https://claude.com/blog/skills) covers the public API for Claude Code and compatible coding agents. It ships the same reference the library is kept in sync with:

```sh
npx skills add sandros94/unjwt
```

Once installed, a question about unjwt, JWS, JWE or JWK loads the reference files from [`skills/unjwt`](https://github.com/sandros94/unjwt/tree/main/skills/unjwt).

## Requirements

- **Node.js 24.17 or later.** Any other runtime works as long as the [Web Crypto API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Crypto_API) is available as a global: Bun, Deno, Cloudflare Workers, browsers.
- **ESM only.** The package ships pure ECMAScript modules.
- **Zero runtime dependencies.** The base64 and sanitize primitives come from [unsecure](https://unsecure.s94.dev), which is bundled into the package at build time.

The library touches one global, `crypto`, through `crypto.subtle` and `crypto.getRandomValues`.

## Entry points

Every core module is published twice: inside the barrel at `unjwt`, and as its own subpath. Both hold the same code, and the package is `sideEffects: false`, so a bundler tree-shakes the barrel down to what you call.

```ts
// Barrel: one import site, every core export
import { sign, verify, generateJWK } from "unjwt";

// Subpaths: one module per import
import { sign, verify } from "unjwt/jws";
import { generateJWK } from "unjwt/jwk";
```

| Import from             | What it gives you                                                            | Peer dependency |
| ----------------------- | ---------------------------------------------------------------------------- | --------------- |
| `unjwt`                 | Every export of `jws`, `jwe`, `jwk` and `utils`, flat                        | none            |
| `unjwt/jws`             | `sign`, `verify` and the JSON serialisation functions                        | none            |
| `unjwt/jwe`             | `encrypt`, `decrypt` and the JSON serialisation functions                    | none            |
| `unjwt/jwk`             | Key generation, import and export, PEM, wrapping, password derivation, cache | none            |
| `unjwt/utils`           | base64url codecs, type guards, claim validation, random bytes                | none            |
| `unjwt/internal`        | JOSE plumbing for tests and tooling, with no semver guarantee                | none            |
| `unjwt/adapters/h3v1`   | Sessions for H3 v1 (Nuxt 4, Nitro 2)                                         | `h3` v1         |
| `unjwt/adapters/h3v2`   | Sessions for H3 v2 (Nuxt 5, Nitro 3)                                         | `h3` v2         |
| `unjwt/adapters/elysia` | Session plugins for Elysia                                                   | `elysia`        |

The peer dependencies are optional. Install them only for the adapter you import, at the versions your framework already uses: `h3` `^1.15.4 || ^2.0.1`, `elysia` `^1.4.29`.

`unjwt/internal` is not part of the barrel. Read [unjwt/internal](/utils/internal) before depending on it.

## From a CDN

Each subpath is its own bundle, so a browser downloads only the module named in the URL.

```ts
import { sign, verify } from "https://esm.sh/unjwt/jws";
import { generateJWK } from "https://esm.sh/unjwt/jwk";
```

Pin a version in production, as with any other CDN import:

```ts
import { verify } from "https://esm.sh/unjwt@0.8.0/jws";
```

::warning
A CDN import of the barrel, `https://esm.sh/unjwt`, downloads every core module. Name the subpath you need.
::

## Types

Types ship with the package; there is no `@types/unjwt`. Every type is exported from `unjwt`, and each subpath exports the types of its own functions. A handful show up across the whole API:

- `JWK`: a JSON Web Key, the union of every key shape (`oct`, `RSA`, `EC`, `OKP`, public and private). `JWKSet` is `{ keys: JWK[] }`. See [JWK](/jwk).
- `JWTClaims`: the registered claims (`iss`, `sub`, `aud`, `exp`, `nbf`, `iat`, `jti`) plus any other member. It is the default payload type of `verify` and `decrypt`. Extend it for your own claims and pass it as `verify<MyClaims>(…)`.
- `JOSEPayloadMode`: `"json" | "string" | "bytes"`, the values of the `payload` option on `verify` and `decrypt`. The return type follows it. See [Concepts](/getting-started/concepts#payload-modes).
- `JWTError`: the one error class, with a `code` such as `"ERR_JWS_SIGNATURE_INVALID"`. `isJWTError(error, code)` narrows to it. See [Errors](/errors).

```ts
import type { JWK, JWTClaims, JOSEPayloadMode } from "unjwt";
import { JWTError, isJWTError } from "unjwt";
```
