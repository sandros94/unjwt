# Migrating to 0.8

> Every breaking change between 0.7 and 0.8, each with the code before and after, and the deprecations that go away in 0.9.

Work through the sections that name a function or option you call. Anything not listed here behaves as it did in 0.7.

## Payload mode is declared

In 0.7, `verify` and `decrypt` looked at the payload: JSON came back parsed and anything else came back as a string. In 0.8 the caller declares the mode with `payload`, and the default is `"json"`, a claims object that must be a JSON object.

```ts
// 0.7
const { payload } = await verify(token, key, { forceUint8Array: true });
const { payload: text } = await verify(textToken, key); // "hello"

// 0.8
const { payload } = await verify(token, key, { payload: "bytes" });
const { payload: text } = await verify(textToken, key, { payload: "string" }); // "hello"
```

A text token read with the default mode throws `ERR_JWS_INVALID` (`ERR_JWE_INVALID` for `decrypt`). `forceUint8Array` still works until 0.9; passing it together with a `payload` that contradicts it is `ERR_INVALID_OPTION`. See [payload modes](/getting-started/concepts#payload-modes).

## A string is a password, never a secret key

0.7 turned a string key into HMAC secret bytes. In 0.8 a string is accepted only as a PBES2 password for JWE. Everywhere else it throws `ERR_JWK_INVALID`.

```ts
// 0.7
await sign(claims, "my-secret", { alg: "HS256" });

// 0.8: a JWK, or a Uint8Array secret
const key = await generateJWK("HS256");
await sign(claims, key);

const secret = crypto.getRandomValues(new Uint8Array(32));
await sign(claims, secret, { alg: "HS256" });
await verify(token, secret, { algorithms: ["HS256"] });
```

PEM text goes through [`importPEM`](/jwk/pem). A password that must become a key goes through [`deriveJWKFromPassword`](/jwk/password).

## A JWK Set holds public keys

An `oct` entry in a JWK Set is skipped, so a set fetched from the network cannot carry an HMAC secret. Opt in only for a set your application builds.

```ts
// 0.7: oct entries were candidates
await verify(token, { keys: [hmacKey] });

// 0.8
await verify(token, { keys: [hmacKey] }, { allowSymmetricJWKSet: true });
```

## A key's `alg` is binding

A JWK's `alg` names the one thing the key is for. A key with `alg: "A256KW"` only wraps keys, and asking it for another algorithm is `ERR_JWK_INVALID`. A key used with `alg: "dir"` must say `dir`, or carry the content algorithm (`A256GCM`, …) it is a key for. Raw `Uint8Array` keys are never guessed.

```ts
// 0.7
await verify(token, secretBytes);
await decrypt(jwe, cekBytes);

// 0.8
await verify(token, secretBytes, { algorithms: ["HS256"] });
await decrypt(jwe, cekBytes, { algorithms: ["dir"], encryptionAlgorithms: ["A256GCM"] });
```

Without `algorithms`, a raw key is `ERR_JWS_ALG_NOT_ALLOWED` or `ERR_JWE_ALG_NOT_ALLOWED`.

## Options objects and removed aliases

The key-management functions take the subject first and the algorithm inside the options object.

```ts
// 0.7
await wrapKey("A256KW", cek, kek);
await unwrapKey("A256KW", encryptedKey, kek, { format: "raw" });
await deriveKeyFromPassword(password, "PBES2-HS256+A128KW", { salt, iterations });
await deriveJWKFromPassword(password, "PBES2-HS256+A128KW", { salt, iterations });

// 0.8
await wrapKey(cek, kek, { alg: "A256KW" });
await unwrapKey(encryptedKey, kek, { alg: "A256KW", format: "raw" });
await deriveKeyFromPassword(password, { alg: "PBES2-HS256+A128KW", salt, iterations });
await deriveJWKFromPassword(password, { alg: "PBES2-HS256+A128KW", salt, iterations });
```

The aliases deprecated in 0.6 and 0.7 are removed:

| Removed                                                | Use                                             |
| ------------------------------------------------------ | ----------------------------------------------- |
| `getJWKFromSet(jwks, kid)`                             | `getJWKsFromSet(jwks, (k) => k.kid === kid)[0]` |
| `importFromPEM(pem, pemType, alg, opts)`               | `importPEM(pem, alg, { pemType, ...opts })`     |
| `exportToPEM(jwk, pemFormat, alg)`                     | `exportPEM(jwk, { pemFormat, alg })`            |
| `computeExpiresInSeconds`, `computeMaxTokenAgeSeconds` | `computeDurationInSeconds`                      |

## Sessions (H3 v1, H3 v2, Elysia)

A session `key` must be key material, a JWK or a `CryptoKey`. A string throws `ERR_SESSION_KEY_INVALID`. Derive a key once from your secret and pass the JWK.

```ts
// 0.7
useJWESession(event, { key: process.env.SESSION_SECRET });

// 0.8
const key = await deriveJWKFromPassword(process.env.SESSION_SECRET, {
  alg: "PBES2-HS256+A128KW",
  salt: "app-session-salt",
  iterations: 600_000,
});
useJWESession(event, { key });
```

`jti`, `iat`, `exp` and `nbf` belong to the adapter. They are dropped from the data passed to `update()`. Set a one-off lifetime with the second argument.

```ts
// 0.7
await session.update({ userId, exp: Math.floor(Date.now() / 1000) + 300 });

// 0.8
await session.update({ userId }, { maxAge: "5m" });
```

`unjwt/adapters/h3` now resolves to the h3 v2 adapter (Nuxt 5, Nitro 3). Import `unjwt/adapters/h3v1` for h3 v1.

The other session changes need no code edit, but they change what is accepted:

- Session tokens carry `typ: "session+jwt"` ([RFC 8725 §3.11](https://www.rfc-editor.org/rfc/rfc8725#section-3.11)), and a token without it is not a session. A `typ` you configure in `protectedHeader` still wins. Tokens issued by 0.7 carry `typ: "JWT"`, so every existing session signs out once after the upgrade.
- The cookie is read first, the session header second.
- A token's own `exp` decides when it expires. A token without `exp` is refused when the session has a `maxAge`.
- Every error is a `JWTError` with an `ERR_SESSION_*` code, configuration mistakes included.
- A session name cannot end in a dot and digits (`app.1`), the spelling of a chunk cookie. It throws `ERR_SESSION_CONFIG_INVALID`.
- `update()` takes a plain object or an updater function; anything else is `ERR_INVALID_OPTION`.
- A `kid` set in `protectedHeader` wins over the key's own `kid`, as with `sign`.
- JWS `verifyOptions` accept the same core options as JWE `decryptOptions` (`limits`, `allowSymmetricJWKSet`). Options the adapter owns stay out of reach.
- Clearing a session writes `Max-Age=0` and an epoch `Expires` on every adapter ([RFC 6265 §5.2.2](https://www.rfc-editor.org/rfc/rfc6265#section-5.2.2)).

## Session hooks and rolling

Hooks receive the session manager, not a copy of its state, so a hook can `update()` or `clear()` the session it is looking at. `onRead` fires once per request, when the token is read; later reads in the same request are silent. `onUpdate` gains `trigger`, and the new `rolling` option replaces the hand-written sliding expiry.

```ts
// 0.7: reissue from the hook, dedupe repeated reads yourself
hooks: {
  async onRead({ event, session, config }) {
    if (session.expiresAt - Date.now() < 15 * 60_000) await updateJWSSession(event, config);
  },
}

// 0.8
{ key, maxAge: "20m", rolling: "15m" }
```

See [Hooks](/adapters/hooks).

## Stricter on the wire

- base64url is canonical. A segment with `=` padding is refused ([RFC 7515 §2](https://www.rfc-editor.org/rfc/rfc7515#section-2)).
- `crit` and `b64` must sit in the protected header, and every `crit` entry must name a parameter that header carries.
- `cty` is no longer added to a plain JWT ([RFC 7519 §5.2](https://www.rfc-editor.org/rfc/rfc7519#section-5.2)). Set it yourself when you nest tokens.

  ```ts
  // 0.7: sign({ sub }, key) wrote { …, typ: "JWT", cty: "application/json" }
  // 0.8: it writes { kid, alg, typ: "JWT" }; a nested token says so itself
  await sign(innerToken, key, { protectedHeader: { cty: "JWT" } });
  ```

- PBES2 `p2c` is capped at 600 000 on both sides, so the library never mints a token it would refuse to open. A higher `p2c` option is `ERR_INVALID_OPTION`; a token carrying one is `ERR_JWE_INVALID`.
- `verifyMulti` and `decryptMulti` return in `protectedHeader` only what was protected. `alg` and `enc` may sit in the unprotected tiers ([RFC 7515 §7.2.1](https://www.rfc-editor.org/rfc/rfc7515#section-7.2.1), [RFC 7516 §7.2.1](https://www.rfc-editor.org/rfc/rfc7516#section-7.2.1)); read them from `signerHeader`, `sharedUnprotectedHeader` or `recipientHeader`. See [header tiers](/getting-started/concepts#header-tiers).
- Ed448 and X448 are removed. `generateJWK("Ed448")` is `ERR_JWK_UNSUPPORTED`.
- `wrapKey` for ECDH-ES behaves like `encrypt`: a minimal `epk`, `ECDH-ES+A*KW` allowed on an ephemeral JWK, and `apu`/`apv` at most 1024 bytes, omitted when empty.
- `strictSignerMatch` treats `kid` as a hint for a single key, so a `CryptoKey` or raw key is still tried. With a JWK Set, the header `kid` selects the candidates ([RFC 7515 §4.1.4](https://www.rfc-editor.org/rfc/rfc7515#section-4.1.4)).

## JOSE plumbing moved to `unjwt/internal`

Payload parsing, time-claim computation and `crit` checks moved from `unjwt/utils` to [`unjwt/internal`](/utils/internal), which carries no semver guarantee. The old names stay on `unjwt/utils` as deprecated aliases until 0.9.

```ts
// 0.7
import { decodePayloadFromBytes } from "unjwt/utils";
const claims = decodePayloadFromBytes(bytes);

// 0.8
import { parsePayloadBytes } from "unjwt/internal";
const claims = parsePayloadBytes<MyClaims>(bytes);
```

## Return types follow the options

Payload modes and key shapes are typed through maps. A literal option gives the exact type; a variable gives the union. These changes are type-level only:

```ts
// A variable typed JWSVerifyOptions now yields JWTClaims | string | Uint8Array
const options: JWSVerifyOptions<"json"> = { audience: "api" }; // keeps JWTClaims

// verify<MyClaims>(token, key, { payload: "string" }) is a type error: drop the type argument
await verify(token, key, { payload: "string" }); // payload: string

// generateKey<A, { toJWK: true }> becomes generateKey<A, true>
const pair = await generateKey<"ES256", true>("ES256", { toJWK: true });
```

- `importKey(octJwk)` is typed `Uint8Array`, as it always returned.
- `WrapKeyResult.epk` and the ECDH `ephemeralKey` options are `EC | OKP`; narrow on `kty`.
- New exported types: `JOSEPayloadTypeMap`, `PayloadOf`, `GeneratedKeyMap`, `GeneratedJWKMap`, `ImportedKeyMap`, `ImportedKey`.
