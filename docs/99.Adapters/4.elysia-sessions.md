# Elysia sessions

Cookie-based JWT session management for [Elysia](https://elysiajs.com). The adapter ships as two
plugins — `jwsSession` (signed) and `jweSession` (encrypted) — that attach a ready-to-use session
manager to the request context, plus a guard macro for protected routes.

```ts
import { jwsSession, jweSession } from "unjwt/adapters/elysia";
```

::note
Peer dep: `elysia` (`>=1.4.0`). The adapter is Web-Standard and runs anywhere Elysia's
`app.handle(Request)` does — Bun, Node (via `@elysiajs/node` for the server, not needed for
`handle`), Deno, Workers.
::

## Basic usage

`.use()` the plugin, then read `ctx.session` in any route below it:

```ts [basic.ts]
import { Elysia, t } from "elysia";
import { jweSession, deriveJWKFromPassword } from "unjwt/adapters/elysia";

// Derive once, at boot — the adapter takes key material, never a password.
const key = await deriveJWKFromPassword(process.env.SESSION_SECRET!, {
  alg: "PBES2-HS256+A128KW",
  salt: process.env.SESSION_SALT!,
  iterations: 600_000,
});

const app = new Elysia()
  .use(jweSession({ key, maxAge: "7D" }))
  .post(
    "/login",
    async ({ session, body }) => {
      await session.update({ userId: body.userId });
      return { id: session.id };
    },
    { body: t.Object({ userId: t.String() }) },
  )
  .get("/me", ({ session }) => session.data);
```

`session` is fully typed — `session.data`, `session.update()`, `session.clear()`, `session.id`, etc.
No need to call anything to obtain it; the plugin's scoped `resolve` populates it per request.

### Signed session (JWS)

```ts [jws.ts]
import { Elysia } from "elysia";
import { jwsSession, generateJWK } from "unjwt/adapters/elysia";

const keys = await generateJWK("RS256"); // persist these!

const app = new Elysia()
  .use(jwsSession({ key: keys, maxAge: "1h" }))
  .get("/me", ({ session }) => session.data); // JWS payload is client-readable
```

See [JWE vs JWS](/adapters) for when to choose which. Cookie defaults match the rest of the library:
JWE `httpOnly: true`, JWS `httpOnly: false` (the signed payload is meant to be readable).

## Protecting routes — the guard macro

Each plugin registers a guard macro named after its context key. The default key `"session"` yields
`requireSession`. Opt a route (or a `.guard` group) in, and unauthenticated requests get `401`
before the handler runs:

```ts [guard.ts]
const app = new Elysia()
  .use(jwsSession({ key: keys, maxAge: "1h" }))
  .get("/me", ({ session }) => session.data) // open
  .guard(
    { requireSession: true },
    (app) => app.get("/admin", ({ session }) => session.data), // 401 without a valid session
  );
```

The guard returns Elysia's `status(401)` (idiomatic — correct HTTP status and Eden/OpenAPI types),
it does not throw or redirect.

## Multiple sessions on one app

Run several sessions side by side — e.g. a short-lived **access** token (JWS, client-readable) and a
long-lived **refresh** token (JWE, opaque). Give each plugin a distinct `contextKey` **and** `name`:

```ts [access-refresh.ts]
const app = new Elysia()
  .use(jwsSession({ key: accessKey, contextKey: "access", name: "at", maxAge: "10m" }))
  .use(jweSession({ key: refreshKey, contextKey: "refresh", name: "rt", maxAge: "7D" }))
  .get("/me", ({ access, refresh }) => ({ user: access.data, sub: refresh.data.sub }));
```

- **`contextKey`** — the context property the session is exposed under (`ctx.access`, `ctx.refresh`).
  Defaults to `"session"`.
- **`name`** — the cookie name (and the default `x-<name>-session` header). Distinct names keep the
  cookies separate.

The guard macro is named per context key, so guards don't collide:

```ts
.guard({ requireAccess: true },  (app) => app.get("/api", ...))   // checks ctx.access
.guard({ requireRefresh: true }, (app) => app.get("/renew", ...)) // checks ctx.refresh
```

The macro name is `require` + the capitalized context key: `requireSession`, `requireAccess`,
`requireRefresh`, etc.

::warning
When combining plugins you **must** set distinct `contextKey` and `name` on each. With defaults they
would both expose `ctx.session` (the later one wins) and reuse default cookie names. Each plugin's
Elysia identity is derived from its `name` and `contextKey`, so two differently-named sessions
register side by side rather than deduplicating into one.
::

A `name` spells one cookie, and one cookie carries one token, so on any one request a name belongs
to one session — including across families. A second family under a name already bound on the
same request throws `ERR_SESSION_CONFIG_INVALID` rather than silently writing over the first
session's cookie:

```ts
const jws = await createJWSSession(context, { name: "app", key: signingKeys });
await createJWESession(context, { name: "app", key: sealingKey });
// JWTError [ERR_SESSION_CONFIG_INVALID]: [unjwt/elysia] Session name "app" is already
// used by a JWS session on this request; a name is one cookie, so give this session a
// "name" of its own.
```

Re-creating the same family under the same name — a hook re-reading its own session, or a second
`createJWSSession` on one request — is the same session and is always allowed. Every binding of
it on that request shares one state: a hook that calls `clear()` leaves `ctx.session` empty (so
`requireSession` rejects the request), and one that calls `update()` hands the handler the new
session.

## Configuration

### JWS — `SessionConfigJWS`

```ts
interface SessionConfigJWS<T, MaxAge, TContext> {
  key:
    | CryptoKey // requires jws.signOptions.alg
    | JWK_oct<JWK_HMAC> // symmetric (HMAC) JWK
    | {
        privateKey: JWSAsymmetricPrivateJWK | CryptoKey;
        publicKey: JWSAsymmetricPublicJWK | JWSAsymmetricPublicJWK[] | JWKSet | CryptoKey;
      };

  maxAge?: MaxAge; // ExpiresIn duration; sets exp + cookie lifetime
  name?: string; // cookie name (default: "elysia-jws")
  contextKey?: string; // context property (default: "session")
  cookie?: false | (CookieAttributes & { chunkMaxLength?: number });
  sessionHeader?: false | string; // default: x-<name>-session; a "Bearer " prefix is stripped
  generateId?: () => string; // default: crypto.randomUUID()

  jws?: {
    // JWSSignOptions minus expiresIn / expiresAt / notBeforeIn / notBeforeAt;
    // set `alg` to pin the algorithm, `protectedHeader.typ` to set the session
    // `typ` (default "JWT") every incoming token must carry
    signOptions?: SessionSignOptions;
    // JWTClaimValidationOptions minus maxTokenAge and typ
    verifyOptions?: SessionVerifyOptions;
  };

  hooks?: SessionHooksJWS<T, MaxAge, TContext>;
}
```

### JWE — `SessionConfigJWE`

```ts
interface SessionConfigJWE<T, MaxAge, TContext> {
  key:
    | CryptoKey // requires jwe.encryptOptions.alg and enc
    | JWEEncryptJWK // symmetric or public asymmetric JWK
    | { privateKey: JWEAsymmetricPrivateJWK; publicKey?: JWEAsymmetricPublicJWK };

  maxAge?: MaxAge;
  name?: string; // default: "elysia-jwe"
  contextKey?: string; // default: "session"
  cookie?: false | (CookieAttributes & { chunkMaxLength?: number });
  sessionHeader?: false | string;
  generateId?: () => string;

  jwe?: {
    // JWEEncryptOptions minus expiresIn / expiresAt / notBeforeIn / notBeforeAt;
    // set `alg` + `enc` to pin, `protectedHeader.typ` to set the session `typ`
    // (default "JWT") every incoming token must carry
    encryptOptions?: SessionEncryptOptions;
    // JWEDecryptOptions minus what the session owns (algorithms,
    // encryptionAlgorithms, typ, validateClaims, forceUint8Array)
    decryptOptions?: SessionDecryptOptions;
  };

  hooks?: SessionHooksJWE<T, MaxAge, TContext>;
}
```

::note
**Pin algorithms** for production: set `jws.signOptions.alg` (or `jwe.encryptOptions.alg` + `enc`).
Signing/sealing uses them and verification/unsealing then accepts only those values. Without them,
allowed algorithms are inferred from the key's metadata.
::

## The session manager

```ts
interface SessionManager<T, ConfigMaxAge> {
  readonly id: string | undefined; // from jti — undefined until update() is called
  readonly createdAt: number; // from iat, in ms
  readonly expiresAt: ConfigMaxAge extends ExpiresIn ? number : number | undefined;
  readonly data: SessionData<T>; // payload (excludes jti/iat/exp/nbf)
  readonly token: string | undefined;

  update: (
    update?: SessionUpdate<T>,
    options?: { maxAge?: ExpiresIn },
  ) => Promise<SessionManager<T, ConfigMaxAge>>;
  clear: () => Promise<SessionManager<T, ConfigMaxAge>>;
}

type SessionUpdate<T> =
  Partial<SessionData<T>> | ((oldData: SessionData<T>) => Partial<SessionData<T>> | undefined);
```

Sessions are **lazy** — `session.id` is `undefined` until `session.update()` is first called.
Reading `ctx.session` without updating sets no cookie.

```ts [update.ts]
await session.update({ theme: "dark" }); // partial merge
await session.update((d) => ({ count: (d.count ?? 0) + 1 })); // updater fn
await session.update(); // rotate token (new jti/iat/exp), same data
await session.update({ step: "mfa" }, { maxAge: "5m" }); // one token, own lifetime
await session.clear(); // expire the cookie + reset state, fires onClear
```

`clear()` (explicit termination) is distinct from token expiry — they fire `onClear` vs `onExpire`.

::warning
**Update before the response is built.** Elysia serializes the cookie jar into `Set-Cookie` when it
builds the response, and its lifecycle context looks the same before and after that point —
`response` and `responseValue` are both set as soon as the handler returns — so the adapter cannot
tell an `onAfterHandle` write from an `onAfterResponse` one. An `update()` or `clear()` made once the
response is built resolves and changes the in-memory session, but its cookie never reaches the
client. Make session writes in the handler, a `resolve`/`beforeHandle` step, or `onAfterHandle`.
::

::note
**Reserved claims.** `jti`, `iat`, `exp` and `nbf` belong to the adapter. They are stripped from every
`update()` payload (both the object and the updater-function form) and never read back out of
`session.data`, so a token's lifetime comes only from `maxAge` — on the config, or on the single
`update()` call; `jws.signOptions` / `jwe.encryptOptions` take no `expiresIn`, `expiresAt`,
`notBeforeIn` or `notBeforeAt`. On read, a token's own `exp` decides whether it is still live, so a
token issued with `update(data, { maxAge })` keeps that lifetime even past the config's `maxAge`.
Update data must be a plain object — a string, an array or a class instance throws
`ERR_INVALID_OPTION`, as does a `__proto__`, `constructor` or `prototype` key.
::

Session data travels as JSON. In the request that wrote it, `session.data` holds the values as
given; every later read gets their JSON round trip — a `Date` comes back as its ISO string, `NaN`
and `±Infinity` as `null`, and `undefined` members are dropped.

`onUpdate` runs once the new token is committed — state and cookie. A hook that throws makes
`update()` reject with that error while the new session stays in place; rollback covers only a
token that cannot be issued or a cookie that cannot be written.

## Cookies

Defaults: JWE `path: "/", secure: true, httpOnly: true, sameSite: "lax"`; JWS the same but
`httpOnly: false`. Override via `cookie`:

```ts [cookie-opts.ts]
jweSession({
  key,
  maxAge: "7D",
  cookie: { sameSite: "strict", domain: ".example.com", chunkMaxLength: 3000 },
});
```

Large tokens (common for JWE with sizeable payloads) are transparently **chunked**: the base cookie
holds `__chunked__<count>` and the token follows in `name.1`, `name.2`, … `name.<count>`, reassembled
on read (default 4000 bytes/chunk, override via `cookie.chunkMaxLength`, at most 16 chunks). The
layout matches the H3 adapters, so a cookie written by one is readable by the others. Pass
`cookie: false` for header-only mode. A name ending in a dot and digits (`app.1`) spells a chunk
cookie of another session and throws `ERR_SESSION_CONFIG_INVALID`.

A session with a lifetime — a `maxAge`, or `update(data, { maxAge })` — sets the cookie's `expires`
to the token's `exp` and drops a configured `cookie.maxAge`, which takes precedence over `Expires`
(RFC 6265 §5.3) and would keep sending a token that no longer opens. Without a lifetime,
`cookie.expires` and `cookie.maxAge` are written as configured.

::tip
**Prefer a `__Host-` name** (`name: "__Host-session"`). A sibling subdomain can plant a cookie of the
same name for the parent domain, and the adapter reads the first one the request carries, so a junk
cookie can shadow the session. Browsers accept a `__Host-` cookie only when it is `Secure`, has
`Path=/` and no `Domain`; the defaults qualify, so keep `secure` on and set neither `cookie.domain`
nor `cookie.path`. The default header becomes `x-__host-session-session`.
::

## Header-based tokens

For clients that can't use cookies, the token is read from a header whenever the cookie carries none
(the default header is `x-<name>-session`; a leading `Bearer ` is stripped, case-insensitively):

```ts
jweSession({ key, sessionHeader: "authorization" });
```

`sessionHeader: false` disables header reads. With both enabled the **cookie is read first**, and the
header only when the cookie yields no token. The header carries the bare token or `Bearer <token>`;
any other value — empty or whitespace-only, another scheme such as `Basic …`, a `Bearer` with no
token — carries none, so it never hides a cookie and never reaches `onError`. Disabling both leaves
the session with nowhere to read from and throws `ERR_SESSION_CONFIG_INVALID` on first use, as does
a `sessionHeader` that is not a header name (RFC 7230 token characters only).

## Lifecycle hooks

`config.hooks` accepts the same set as the H3 adapters — `onRead`, `onUpdate`, `onClear`,
`onExpire`, `onError`, plus key-lookup hooks `onVerifyKeyLookup` (JWS) / `onUnsealKeyLookup` (JWE).

::note
These are unjwt **session hooks** (`config.hooks.*`), not Elysia's request **lifecycle hooks**
(`onRequest`, `beforeHandle`, …). The names are unrelated.
::

Each hook receives `{ session, context, config }` (the Elysia `context`, not an H3 `event`).
`onRead`/`onExpire`/`onError` are mutually exclusive per incoming token; `onRead` fires again on every
later read of the session during the same request (dedupe on `session.id`); `onUpdate` fires after every
successful sign/seal (including a data-less token refresh) with a deep-cloned `oldSession`.

```ts [hooks.ts]
jweSession({
  key,
  maxAge: "7D",
  hooks: {
    onUpdate: ({ session }) => db.sessions.upsert(session.id!, session.expiresAt),
    onExpire: ({ session }) => db.sessions.revoke(session.id), // session.id from error.cause.jti
  },
});
```

## Lower-level: manual `resolve` wiring

The plugins are built on `createJWSSession` / `createJWESession`, which take a minimal context
(`{ cookie, request }`) and return a `SessionManager`. Use them directly when you want to wire the
session into your own `resolve`/`derive`:

```ts [manual.ts]
import { createJWSSession } from "unjwt/adapters/elysia";

const app = new Elysia()
  .resolve(async ({ cookie, request }) => ({
    session: await createJWSSession({ cookie, request }, { key: keys, maxAge: "1h" }),
  }))
  .get("/me", ({ session }) => session.data);
```

::warning
You must **destructure** `{ cookie, request }` in the `resolve` signature (rather than taking the
whole `ctx`). Elysia provisions context fields by statically scanning the hook source — if `cookie`
isn't referenced there, it won't be populated and the session can't read or write it. A `cookie`
object that holds no reactive cookie throws `ERR_SESSION_CONFIG_INVALID` on the first write.
::

## Typing session data

```ts [typed.ts]
interface MyData {
  userId: string;
  role: "admin" | "user";
}

const app = new Elysia().use(jweSession<MyData>({ key })).get("/me", ({ session }) => {
  session.data.userId; // string
  session.data.role; // "admin" | "user"
});
```

The generic threads through `update()` and every hook payload.
