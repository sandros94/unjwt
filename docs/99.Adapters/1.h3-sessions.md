# H3 sessions

Cookie-based JWT session management for [H3](https://h3.dev) applications. Sessions are stored as encrypted (JWE) or signed (JWS) tokens in chunked cookies, and read from a session header when the cookie carries none.

Import paths (pick the one that matches your H3 version):

```ts
import { useJWESession, useJWSSession } from "unjwt/adapters/h3v2";
// or "unjwt/adapters/h3v1" for H3 v1 / Nuxt v4 / Nitro v2
```

## Basic usage

### Encrypted session (JWE)

```ts [basic-jwe.ts]
import { useJWESession, deriveJWKFromPassword } from "unjwt/adapters/h3v2";

// Derive once, at boot — the adapters take key material, never a password.
const key = await deriveJWKFromPassword(process.env.SESSION_SECRET!, {
  alg: "PBES2-HS256+A128KW",
  salt: process.env.SESSION_SALT!,
  iterations: 600_000,
});

app.get("/", async (event) => {
  const session = await useJWESession(event, {
    key, // symmetric JWK, asymmetric keypair, or CryptoKey
    maxAge: "7D",
  });

  if (!session.id) {
    // No active session yet — create one
    await session.update({ userId: "123", email: "user@example.com" });
  }

  return { user: session.data };
});
```

### Signed session (JWS)

```ts [basic-jws.ts]
import { useJWSSession, generateJWK } from "unjwt/adapters/h3v2";

const keys = await generateJWK("RS256"); // persist these!

app.get("/", async (event) => {
  const session = await useJWSSession(event, {
    key: keys,
    maxAge: "1h",
  });

  return { data: session.data };
});
```

## Configuration

### JWE — `SessionConfigJWE`

```ts
interface SessionConfigJWE<T, MaxAge, TEvent> {
  key:
    | CryptoKey // requires jwe.encryptOptions.alg and enc
    | JWEEncryptJWK // symmetric or public asymmetric JWK (alg in the JWE family)
    | { privateKey: JWEAsymmetricPrivateJWK; publicKey?: JWEAsymmetricPublicJWK }; // asymmetric pair

  maxAge?: MaxAge; // ExpiresIn duration
  name?: string; // cookie name (default: "h3-jwe")
  cookie?: false | (CookieSerializeOptions & { chunkMaxLength?: number });
  sessionHeader?: false | string; // e.g. "Authorization"
  generateId?: () => string; // default: crypto.randomUUID()

  jwe?: {
    // JWEEncryptOptions minus expiresIn / expiresAt / notBeforeIn / notBeforeAt;
    // protectedHeader.typ sets the session `typ` (default "session+jwt"), which
    // every incoming token must then carry
    encryptOptions?: SessionEncryptOptions;
    // every JWEDecryptOptions field the adapter does not own itself — so
    // minIterations / maxIterations / clockTolerance / issuer / audience are
    // yours, while algorithms, encryptionAlgorithms, typ, validateClaims and
    // forceUint8Array are set by the session
    decryptOptions?: SessionDecryptOptions;
  };

  hooks?: SessionHooksJWE<T, MaxAge, TEvent>;
}
```

### JWS — `SessionConfigJWS`

```ts
interface SessionConfigJWS<T, MaxAge, TEvent> {
  key:
    | CryptoKey // requires jws.signOptions.alg
    | JWK_oct<JWK_HMAC> // symmetric (HMAC) JWK
    | {
        privateKey: JWSAsymmetricPrivateJWK | CryptoKey;
        publicKey: JWSAsymmetricPublicJWK | JWSAsymmetricPublicJWK[] | JWKSet | CryptoKey;
      };

  maxAge?: MaxAge;
  name?: string; // default: "h3-jws"
  cookie?: false | (CookieSerializeOptions & { chunkMaxLength?: number });
  sessionHeader?: false | string;
  generateId?: () => string;

  jws?: {
    // JWSSignOptions minus expiresIn / expiresAt / notBeforeIn / notBeforeAt;
    // protectedHeader.typ sets the session `typ` (default "session+jwt"), which
    // every incoming token must then carry
    signOptions?: SessionSignOptions;
    // JWTClaimValidationOptions minus maxTokenAge and typ
    verifyOptions?: SessionVerifyOptions;
  };

  hooks?: SessionHooksJWS<T, MaxAge, TEvent>;
}
```

## The session manager

Both adapters return the same shape:

```ts
interface SessionManager<T, ConfigMaxAge> {
  readonly id: string | undefined;
  readonly createdAt: number;
  readonly expiresAt: ConfigMaxAge extends ExpiresIn ? number : number | undefined;
  readonly data: SessionData<T>;
  readonly token: string | undefined;

  update: (
    update?: SessionUpdate<T>,
    options?: { maxAge?: ExpiresIn },
  ) => Promise<SessionManager<T, ConfigMaxAge>>;
  clear: () => Promise<SessionManager<T, ConfigMaxAge>>;
}

type SessionUpdate<T> =
  Partial<SessionData<T>> | ((oldData: SessionData<T>) => Partial<SessionData<T>> | undefined);
```

### Lazy by design

`session.id` is `undefined` until `session.update()` is first called. This is intentional — it aligns with OAuth and spec-compliant flows where a session should only exist once a valid operation has created it. Calling `useJWESession(event, config)` alone doesn't set a cookie.

### `update()` forms

```ts [update.ts]
// Partial merge
await session.update({ theme: "dark" });

// Updater function
await session.update((oldData) => ({ count: (oldData.count ?? 0) + 1 }));

// Token rotation (new jti/iat/exp) without changing data
await session.update();

// One token with a lifetime of its own — `expiresAt` and the cookie follow it
await session.update({ step: "mfa" }, { maxAge: "5m" });
```

`jti`, `iat`, `exp` and `nbf` belong to the adapter. They are stripped from both `update()` forms and
never read back out of `session.data`, so the only way to change a token's lifetime is `maxAge`.
Options that would mint them through `jws.signOptions` / `jwe.encryptOptions` (`expiresIn`,
`expiresAt`, `notBeforeIn`, `notBeforeAt`) are not accepted either. On read, a token's own `exp`
decides whether it is still live, so a token issued with `update(data, { maxAge })` keeps that
lifetime even when it outlasts the config's `maxAge`.
Update data must be a plain object — a string, an array or a class instance throws
`ERR_INVALID_OPTION`, as does a `__proto__`, `constructor` or `prototype` key.

Session data travels as JSON. In the request that wrote it, `session.data` holds the values as
given; every later read gets their JSON round trip — a `Date` comes back as its ISO string, `NaN`
and `±Infinity` as `null`, and `undefined` members are dropped. Store what JSON carries as-is:
strings, finite numbers, booleans, `null`, arrays and plain objects.

### `clear()` — explicit termination

```ts [clear.ts]
await session.clear();
// Session emptied in the event context; cookie expired in the response.
// A later useJWESession/useJWSSession on the same event sees no session —
// the request cookie does not bring the cleared one back.
```

`clear()` is semantically different from "token expired" — they trigger different hooks (`onClear` vs. `onExpire`). See [Hooks](/adapters/hooks).

## Cookies

By default:

- JWE: `path: "/", secure: true, httpOnly: true, sameSite: "lax"`.
- JWS: `path: "/", secure: true, httpOnly: false, sameSite: "lax"` (the payload is meant to be readable).

Customize via `cookie`:

```ts [cookie-opts.ts]
const session = await useJWSSession(event, {
  key: keys,
  maxAge: "1h",
  cookie: {
    sameSite: "strict",
    domain: ".example.com",
    path: "/app",
    chunkMaxLength: 3000, // split into chunks if the token exceeds this many bytes
  },
});
```

Pass `cookie: false` to disable cookie writing entirely (header-only mode — see below).

### Cookie lifetime

A session with a lifetime — a `maxAge`, or `update(data, { maxAge })` — sets the cookie's `expires`
to the token's `exp` and drops a configured `cookie.maxAge`: `Max-Age` takes precedence over
`Expires` (RFC 6265 §5.3), so it would keep sending a token that no longer opens. A session without
a lifetime writes `cookie.expires` and `cookie.maxAge` as configured; leave both out for a cookie
that lasts the browser session.

### Prefer a `__Host-` name

A sibling subdomain can set a cookie for the parent domain under your session's name, and every
adapter reads the first cookie of a name the request carries — so a planted junk cookie can shadow
the session and sign the user out. Name the session with the `__Host-` prefix
(`name: "__Host-session"`): browsers accept such a cookie only when it is `Secure`, has `Path=/` and
no `Domain`, so no other host can set it, chunks included. The defaults already qualify; keep
`secure` on and set neither `cookie.domain` nor `cookie.path`. The default header is derived from
the name without its cookie prefix: `__Host-session` (or `__Secure-session`) reads
`x-session-session`.

### One `name`, one session

A `name` spells one cookie, and one cookie carries one token, so on any one request a name belongs to a single session — including across families. Binding a JWE session under a name a JWS session already bound on the same request throws `ERR_SESSION_CONFIG_INVALID`:

```ts
const jws = await useJWSSession(event, { name: "app", key: signingKeys });
await useJWESession(event, { name: "app", key: sealingKey });
// JWTError [ERR_SESSION_CONFIG_INVALID]: [unjwt/h3] Session name "app" is already
// used by a JWS session on this request; a name is one cookie, so give this
// session a "name" of its own.
```

Give each session its own name (`"at"` and `"rt"`, say). Reading the same family and name again — a second `useJWSSession` on the same request, or a hook re-reading its own session — is the same session and is always allowed.

A name ending in a dot and digits, such as `app.1`, throws `ERR_SESSION_CONFIG_INVALID` as well: it spells the cookie holding a chunk of the session named `app` (see [Chunking](#chunking)).

### Chunking

JWE tokens can easily exceed the 4KB cookie limit when the session payload is large. The base cookie then holds the marker `__chunked__<count>` and the token follows in `name.1`, `name.2`, … `name.<count>`, reassembled transparently on read. Default chunk size is 4000 bytes, overridable via `cookie.chunkMaxLength`; at most 16 chunks, beyond which the write throws `ERR_SESSION_CONFIG_INVALID`. Both H3 adapters and the Elysia adapter write the same layout, so a cookie set by one is readable by the others.

## Header-based tokens

For API clients (mobile, SPA, service-to-service) that can't use cookies, the token is read from a header whenever the cookie carries none:

```ts [header.ts]
const session = await useJWESession(event, {
  key, // the derived JWK from above
  sessionHeader: "Authorization", // accepts "Bearer <token>" or the bare token
});
```

Custom header name:

```ts
sessionHeader: "X-Session-Token",
```

Pass `sessionHeader: false` to disable header reads (cookies only).

With both enabled, the **cookie is read first** and the header is consulted only when the cookie
yields no token. The header carries either the bare token or `Bearer <token>`, the scheme matched
case-insensitively (RFC 7235). Any other value — empty or whitespace-only, another scheme such as
`Basic …`, a `Bearer` with no token — carries no token: it never hides a cookie and never reaches
`onError`. Set `cookie: false` to force header-only behaviour. Disabling both leaves the session
with nowhere to read from and throws `ERR_SESSION_CONFIG_INVALID` on first use, as does a
`sessionHeader` that is not a header name (RFC 7230 token characters only).

## Typing session data

```ts [typed.ts]
interface MyData {
  userId: string;
  role: "admin" | "user";
  preferences?: { theme: "dark" | "light" };
}

app.get("/", async (event) => {
  const session = await useJWESession<MyData>(event, config);
  session.data.userId; // string
  session.data.role; // "admin" | "user"
});
```

The generic threads through `update()` and all hook payloads, so type errors catch drift between your setter and getter.

## Differences from h3's `useSession`

These adapters started as a fork of h3's own `useSession`, with the iron seal replaced by a JWS or JWE. The token format changes what a session _is_, so the two have drifted on purpose. Keep this list in mind when porting code or expectations between them.

| Topic              | h3 `useSession`                                             | unjwt sessions                                                                                                                                                                                                                                                                                                                                                              |
| ------------------ | ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Token              | iron seal (opaque, symmetric)                               | compact JWS (RFC 7515) or JWE (RFC 7516); JWE is opaque, JWS is client-readable                                                                                                                                                                                                                                                                                             |
| Session identity   | `id` and `createdAt` are fixed for the session's life       | every `update()` issues a **new JWT**: fresh `jti`, `iat` and `exp`. Per RFC 7519 a `jti` identifies one token and `iat` is the moment _that_ token was issued; reusing them across issues would make a rotated token indistinguishable from a compromised one                                                                                                              |
| `maxAge`           | absolute, from first creation                               | from the latest issue, so writing the session extends it. Tracking a token's lineage across rotations is an application concern (for example, record the previous `jti` in `onUpdate`)                                                                                                                                                                                      |
| Sliding expiration | opt-in `idleTimeout`, resealed on read past half the window | not built in. Re-issue on read is a policy you own: call `session.update()` from `onRead` when `expiresAt - Date.now()` drops under your threshold                                                                                                                                                                                                                          |
| First cookie       | `useSession` persists immediately                           | lazy — no cookie until the first `update()` (see [Lazy by design](#lazy-by-design))                                                                                                                                                                                                                                                                                         |
| Expired token      | replaced silently by a new session                          | `onExpire` fires with the expired claims, the cookie is deleted and `session.token` reset, then a fresh lazy session is started                                                                                                                                                                                                                                             |
| Foreign tokens     | n/a                                                         | a token is only a session when it carries the session `typ` — `session+jwt` unless `protectedHeader.typ` sets another (RFC 8725 §3.11); with a `maxAge` set it must also carry `exp`, and that `exp` alone bounds its life. A JWT minted elsewhere with the same key is rejected as `ERR_SESSION_TOKEN_INVALID` — expired or not, so it reaches `onError`, never `onExpire` |
| Errors             | swallowed; a bad seal becomes a new session                 | `onError` fires for read-path failures other than expiry and for sign/encrypt or cookie failures on write, where `update()` rejects and rolls the in-memory session back. `onUpdate` runs once the new token is committed, so a hook that throws makes `update()` reject with that error while the new session and its cookie stay in place                                 |
| Hooks              | none                                                        | `onRead`, `onUpdate`, `onClear`, `onExpire`, `onError`, `onVerifyKeyLookup` / `onUnsealKeyLookup` (see [Hooks](/adapters/hooks))                                                                                                                                                                                                                                            |
| Header transport   | `x-<name>-session`, raw value                               | same header, with an optional case-insensitive `Bearer ` prefix so `Authorization` works as-is (any other scheme carries no token); consulted only when the cookie carries no token                                                                                                                                                                                         |
| Cookie defaults    | `secure`, `httpOnly`, `sameSite: "lax"`                     | same for JWE; JWS sets `httpOnly: false` because its payload is readable by design                                                                                                                                                                                                                                                                                          |
| Key material       | a password string                                           | a JWK, a `{ privateKey, publicKey }` pair, or a `CryptoKey`; a string `key` throws `ERR_SESSION_KEY_INVALID`                                                                                                                                                                                                                                                                |
| Error responses    | session cookies mirrored into `res.errHeaders`              | same behaviour, so a handler that throws still persists or clears the session — unless an h3 v2 `onError` returns a `Response` of its own, which h3 sends as-is without `res.errHeaders`. h3 v1 writes the error onto the same Node response, so cookies set before a throw reach the client without extra handling                                                         |
| Late writes        | n/a                                                         | once the response is sent, `update()` and `clear()` throw `ERR_SESSION_READONLY_EVENT` and leave the session as it was — on h3 v1, and on h3 v2 under Node (`headersSent` / `writableEnded`). Other h3 v2 runtimes expose no such signal: a write made after the response was built is accepted but never sent                                                              |

`typ` is compared as a media type, so `application/session+jwt` matches too. Tokens issued before 0.8 carry `typ: "JWT"` and are refused, so every existing session signs out once after the upgrade.
