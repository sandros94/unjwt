# Adapters

unjwt ships cookie-based **session adapters** for [H3](https://h3.dev) — the tiny universal HTTP framework behind [Nuxt](https://nuxt.com) and [Nitro](https://nitro.build) — and for [Elysia](https://elysiajs.com), the bun-first Web-Standard framework.

Import paths:

| Path                    | Framework                                                    |
| ----------------------- | ------------------------------------------------------------ |
| `unjwt/adapters/h3v1`   | **H3 v1** — Nuxt v4, Nitro v2                                |
| `unjwt/adapters/h3v2`   | **H3 v2** — Nuxt v5, Nitro v3                                |
| `unjwt/adapters/h3`     | Alias for `h3v1` (will flip to v2 in a future major release) |
| `unjwt/adapters/elysia` | **Elysia** (`^1.4.29`)                                       |

The H3 adapters expose `useJWESession` / `useJWSSession` (called inside a handler); the Elysia
adapter exposes `jweSession` / `jwsSession` **plugins** that attach an ambient `ctx.session`. All
share the same session model and security defaults.

::note
Peer deps: `h3` — `^1.15.4 || ^2.0.1`; `elysia` — `^1.4.29`. Each is optional, install only the one(s) you use.
::

## JWE vs JWS sessions

Each adapter provides two entry points:

| Function                                 | Session storage                        |
| ---------------------------------------- | -------------------------------------- |
| [`useJWESession`](/adapters/h3-sessions) | JWE — encrypted, opaque to the client. |
| [`useJWSSession`](/adapters/h3-sessions) | JWS — signed, readable by the client.  |

|                 | JWE (encrypted)                                | JWS (signed)                                   |
| --------------- | ---------------------------------------------- | ---------------------------------------------- |
| Data visibility | Encrypted, not readable by client              | Base64URL-encoded, readable by anyone          |
| Default cookie  | `httpOnly: true, secure: true`                 | `httpOnly: false, secure: true`                |
| Key types       | Symmetric JWK, asymmetric keypair, `CryptoKey` | Symmetric JWK, asymmetric keypair, `CryptoKey` |
| Use when        | Session data is sensitive                      | Data is non-sensitive; clients need to read it |

Rule of thumb:

- **Login / refresh tokens** — JWE. The client shouldn't inspect them, and they often contain user-identifiable data.
- **Session data the UI should render from** — JWS. Things like role, display name, theme — readable, tamper-evident.
- **Mixing both** — common in practice. See the [refresh-token pattern](/examples/refresh-token-pattern).

## The session manager

Both `useJWESession` and `useJWSSession` return a `SessionManager`:

```ts
interface SessionManager<T, ConfigMaxAge> {
  readonly id: string | undefined; // from jti — undefined until update() is called
  readonly createdAt: number; // from iat, in ms
  readonly expiresAt: ConfigMaxAge extends ExpiresIn ? number : number | undefined;
  readonly data: SessionData<T>; // session payload (excludes jti/iat/exp/nbf)
  readonly token: string | undefined; // current raw JWT token
  update: (
    update?: SessionUpdate<T>,
    options?: { maxAge?: ExpiresIn }, // lifetime for this one token
  ) => Promise<SessionManager<T, ConfigMaxAge>>;
  clear: () => Promise<SessionManager<T, ConfigMaxAge>>;
}
```

Sessions are **lazy** — `session.id` is `undefined` until you call `session.update()`. This is intentional: it matches OAuth and spec-compliant flows where a session only exists once a valid operation has created it.

Every `update()` issues a **new token** with a fresh `jti`, `iat` and `exp`. `jti`, `iat`, `exp` and
`nbf` belong to the adapter: they are stripped from any `update()` payload and never read back out of
`session.data`. To give one token a lifetime of its own, pass it on the call:

```ts
await session.update({ user: "alice" }, { maxAge: "5m" });
```

## Keys

Adapters take **key material**, never a password: a JWK, one of the `{ privateKey, publicKey }`
shapes, or a `CryptoKey`. A string `key` is rejected with `ERR_SESSION_KEY_INVALID`. Turn a password
into a key once, at boot:

```ts
import { deriveJWKFromPassword } from "unjwt/jwk";

const key = await deriveJWKFromPassword(process.env.SESSION_SECRET!, {
  alg: "PBES2-HS256+A128KW",
  salt: process.env.SESSION_SALT!,
  iterations: 600_000,
});
```

A `CryptoKey` carries no algorithm of its own, so it also needs `jws.signOptions.alg` (or
`jwe.encryptOptions.alg` and `enc`); without them the adapter throws `ERR_SESSION_CONFIG_INVALID`.

A configured JWK is imported when the session is opened, so key material the session cannot use —
a `k` that does not decode, an AES key of the wrong length for its `alg` — throws
`ERR_SESSION_KEY_INVALID` (with the import failure as `cause`) out of that call, instead of turning
every incoming token into an `onError`.

Each half of a `{ privateKey, publicKey }` pair must be the half it is named after: a `privateKey`
that is not a private JWK or `CryptoKey`, or a `publicKey` that is not a public JWK or `CryptoKey`
— for JWS, also a non-empty list or JWK Set whose every entry is a public JWK — throws
`ERR_SESSION_KEY_INVALID` naming that half, whichever of them the call was about to use.

A `kid` set in `signOptions.protectedHeader` / `encryptOptions.protectedHeader` is written as
given; without one, the token carries the key's own `kid`, as `sign()` and `encrypt()` do.

## Errors

Everything the adapters throw is a `JWTError` — check it with `isJWTError`:

| Code                         | Raised when                                                                        |
| ---------------------------- | ---------------------------------------------------------------------------------- |
| `ERR_SESSION_TOKEN_INVALID`  | an incoming token failed verification or decryption; `cause` is the original error |
| `ERR_SESSION_READONLY_EVENT` | `update()` / `clear()` once the response can no longer take a `Set-Cookie`         |
| `ERR_SESSION_KEY_INVALID`    | the configured `key` is missing, a password string, the wrong shape, or unusable   |
| `ERR_SESSION_CONFIG_INVALID` | a config combination that cannot work (no token source, unpinned `CryptoKey`, …)   |
| `ERR_INVALID_OPTION`         | `update()` data is not a plain object, or carries a `__proto__`-like key           |
| `ERR_JWT_EXPIRED`            | the token's `exp` has passed — surfaced through `onExpire`, not thrown             |

`ERR_SESSION_TOKEN_INVALID` keeps the failure that caused it:

```ts
if (
  isJWTError(error, "ERR_SESSION_TOKEN_INVALID") &&
  isJWTError(error.cause, "ERR_JWS_SIGNATURE_INVALID")
) {
  // the token was signed with a key this session does not accept
}
```

## What else the adapters do

- **Automatic cookie chunking** for large tokens (essential for JWE with claims that exceed 4KB): the base cookie holds `__chunked__<count>` and the parts follow as `<name>.1` … `<name>.<count>`, up to 16 chunks. The layout is identical across all three adapters.
- **Header-based token extraction** as a fallback when the cookie carries no token (`x-<name>-session`, `<name>` without a `__Host-` / `__Secure-` prefix, with an optional case-insensitive `Bearer ` prefix; any other scheme carries no token).
- **Explicit typing** ([RFC 8725 §3.11](https://www.rfc-editor.org/rfc/rfc8725#section-3.11)) — every token carries `typ: "session+jwt"` (set another through `jws.signOptions.protectedHeader.typ` / `jwe.encryptOptions.protectedHeader.typ`) and an incoming token must carry it, so no other JWT signed or sealed with the session key reads as a session. Tokens issued before 0.8 carry `typ: "JWT"` and are refused, so every existing session signs out once after the upgrade.
- **Cookie lifetime from the token** — a session with a lifetime sets the cookie's `expires` to the token's `exp` and drops a configured `cookie.maxAge`. Name sessions with the `__Host-` prefix so no sibling subdomain can plant a cookie that shadows them.
- **Lifecycle hooks** — `onRead`, `onUpdate`, `onClear`, `onExpire`, `onError`.
- **Key-lookup hooks** — `onVerifyKeyLookup` (JWS) / `onUnsealKeyLookup` (JWE) for key rotation.
- **Lower-level helpers** — H3: `getJWESession`, `sealJWESession`, `unsealJWESession`, etc.; Elysia: `createJWESession` / `createJWSSession` for manual `resolve` wiring — when you need manual control.
- **Re-exported helpers** — `generateJWK`, `thumbprint`, `importPEM`, `exportPEM`, `deriveJWKFromPassword` for convenience.
